# EIP-7906: Transaction Assertions via State Diff Opcode

> **Spec target:** ethereum/EIPs `EIPS/eip-7906.md` @ commit `614ed450`, the bogota-devnet-2
> revision: `TXDIFF` is removed, `EVENTDATACOPY` moves to `0xb7`, the `POST_TX` frame mode is
> renamed `ASSERT`, and `TXTRACE` gains the `codes_changed` and `nonces_changed` tables, with its
> params renumbered. The `POST_TX_EXEMPT` frame flag proposed in ethereum/EIPs#12304 is still open
> and is not implemented.
>
> **Reference implementation:** execution-specs#3895 (`8b5eb7fbe`), which carries the EIP-7906
> changes for bogota-devnet-2 on the previous EIP-8141 transaction format.

Implementation notes for EIP-7906 in ethrex. It extends [EIP-8141](./eip-8141.md) frame
transactions and activates with them at `Fork::Hegota`.

## Overview

EIP-7906 lets a transaction assert its own outcome. It adds a frame mode, `ASSERT`, and two
opcodes that only work inside it:

| Opcode | Byte | Reads |
|---|---|---|
| `TXTRACE` | `0xb6` | one value of the transaction's state diff, by table and index |
| `EVENTDATACOPY` | `0xb7` | the non-indexed data of one event, into memory |

`ASSERT` frames run last, read-only. If one reverts or halts, everything the frames after the
validation prefix did is reverted, the remaining frames are skipped, and the transaction stays
valid with its gas paid. A wallet can therefore bound what a transaction may do: "no token
balance of mine drops by more than X", "no approval is granted", and so on.

## How to use it

1. Build the transaction as usual: a validation prefix that approves execution and payment,
   then the frames doing the work.
2. Append one or more `ASSERT` frames. Each targets an assertion contract, has flags 0 and
   value 0, and runs with `ENTRY_POINT` as the caller under `STATICCALL` rules.
3. In the assertion contract, read the diff and revert when an expectation fails.

For example, an assertion that the transaction changed exactly one storage slot. `TXTRACE`
takes `param` on top of the stack and the index below it:

```text
PUSH1 0x00   ; index
PUSH1 0x01   ; param 0x01: slots_changed
TXTRACE      ; 0xb6
PUSH1 0x01
EQ
PUSH1 <ok>
JUMPI
PUSH1 0x00
PUSH1 0x00
REVERT       ; the assertion fails: the execution body is reverted
<ok>: JUMPDEST
STOP
```

The frame receipts tell the outcome. A failing assertion has status `0`. The body frames keep
their status and execution gas, with no logs and no state gas. Any later `ASSERT` frame has
status `2` and no gas.

## `TXTRACE` params

| Param | Index | Value |
|---|---|---|
| `0x00`–`0x03` | 0 | the number of entries in `balances_changed`, `slots_changed`, `codes_changed`, `nonces_changed` |
| `0x04`–`0x06` | balance entry | address, balance before, balance after |
| `0x07`–`0x0A` | slot entry | address, value before, value after, slot key |
| `0x0B`–`0x0D` | code entry | address, code hash before, code hash after |
| `0x0E`–`0x10` | nonce entry | address, nonce before, nonce after |
| `0x11` | 0 | the number of events |
| `0x12`–`0x18` | event | emitter, topic count, topics 0 to 3, data length |
| `0x19` | 0 | the payer's escrow, EIP-8141's `max_cost` |
| `0x1A` | 0 | the payer, zero before payment approval |

Every state-change table lists address, before and after in that order, sorted by address (and
slots of one address by key). A code change is any change of the code hash as stored, so it
covers deployments, whose before value is the empty-code hash, and EIP-7702 delegation indicators
installed, changed or cleared. A nonce change includes the sender when payment approval increments
its account nonce; a keyed EIP-8250 transaction leaves the account nonce, and so the table,
alone. Any other param, a non-zero index where the table above says 0, or an index past its
table halts.

## Architecture

```text
Static validity (crates/common/types/transaction.rs, validate_static_constraints)
  mode 3 = ASSERT; modes 4-255 reserved
  ASSERT frames form a trailing suffix
  no atomic batch flag on an ASSERT frame, nor on the frame before one

Frame loop (crates/vm/levm/src/vm.rs, execute_frame_tx)
  ASSERT: caller ENTRY_POINT, static, default code behaves as for SENDER/DEFAULT
  the frame that sets the payer ends the validation prefix:
    capture ExecutionBody = substate level, state-gas counter, approvals,
                            prefix receipts' state gas, log count, BAL checkpoint
    every later frame's first-seen originals are absorbed into its backup
  an ASSERT frame fails:
    revert the body substate, restore the cache and BAL from the body backup,
    zero the body receipts' logs and state gas, skip the remaining frames
  APPROVE in an ASSERT frame halts (OpcodeNotAllowedInStaticContext)

Diff (crates/vm/levm/src/db/gen_db.rs, crates/vm/levm/src/opcode_handlers/tx_assertion.rs)
  tx_prestate: each account and slot as the transaction first touched it,
               installed by VM::new only for a transaction with an ASSERT frame
  tables built on the first read from tx_prestate and the live cache, then kept in
  VM::assertion_diff for the rest of the transaction:
    balances_changed, slots_changed, codes_changed, nonces_changed
      (ascending address, then slot)
    events = logs of the completed frames, in receipt order
```

The diff cannot change once the `ASSERT` frames start: they are static and emit no logs, and a
failing one skips every frame after it. Building it once makes every later `TXTRACE` and
`EVENTDATACOPY` a constant-time lookup, so their flat prices hold however much state the
execution body touched.

Every `TXTRACE` param costs `WARM_STORAGE_READ_COST` (100). `EVENTDATACOPY` is priced like
`CALLDATACOPY`, but halts on a range past the end of the data instead of zero-padding. Neither
reads live state, so neither warms anything nor adds to the block access list.

## Design decisions

- **The prestate is recorded on first touch.** Each account and slot enters `tx_prestate` the first
  time the transaction resolves it, on every resolution path: cache hit, the block-level baseline,
  the block access list overlay, the shared base or the store. The cache outlives one
  transaction, so its entries cannot serve as the prestate. Only accounts and slots the
  transaction touched can differ, so iterating that map enumerates the diff. execution-specs
  iterates the transaction's write sets instead. The two could only disagree on a storage wipe
  during the transaction, which the EIP leaves to the fork's creation rules: ethrex applies
  EIP-7610's storage collision rule to `CREATE`, so a creation never wipes storage here, and the
  removal of an empty account happens after the last frame.
- **Seeding from the block access list does not record.** On the parallel import path a partially
  covered account is loaded from its pre-block base before the access-list prefix is overlaid. The
  capture is suspended for that nested load, so the prestate is the account as earlier
  transactions left it.
- **`param` is on top of the stack** for `TXTRACE`, as the EIP states. `FRAMEPARAM` takes its index
  from the top instead, so the two orders differ.
- **The rollback point follows the payer.** The body begins after the frame that sets `payer`, so
  everything that frame did survives a failing assertion, including EIP-8250's nonce
  consumption, which EIP-8250 forbids a restore that discards the execution body to revert.
- **The body backup is separate from the batch machinery.** No batch can contain or end on an
  `ASSERT` frame, so no batch is open when one fails, and the body's substate level sits directly
  below the failing frame's. Transactions without `ASSERT` frames capture nothing.
