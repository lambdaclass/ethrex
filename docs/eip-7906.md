# EIP-7906: Transaction Assertions via State Diff Opcode

> **Spec target:** ethereum/EIPs `EIPS/eip-7906.md` @ commit `4be9e59ff8` (2026-10-09,
> ethereum/EIPs#12463, block access list recording for `TXDIFF` and a `POST_TX` rollback). It
> includes ethereum/EIPs#12454, which assigns the opcode bytes `0xb6` to `0xb8` and adds `POST_TX`
> to the valid frame modes, and ethereum/EIPs#12461, which fixes the diff semantics, operand order
> and gas accounting. The `POST_TX_EXEMPT` frame flag proposed in ethereum/EIPs#12304 is still open
> and is not implemented.
>
> **Reference implementation:** execution-specs `devnets/frames/1`, released as
> `tests-frames-devnet@v1.0.0`.

Implementation notes for EIP-7906 in ethrex. It extends [EIP-8141](./eip-8141.md) frame
transactions and activates with them at `Fork::Hegota`.

## Overview

EIP-7906 lets a transaction assert its own outcome. It adds a frame mode, `POST_TX`, and three
opcodes that only work inside it:

| Opcode | Byte | Reads |
|---|---|---|
| `TXTRACE` | `0xb6` | one value of the transaction's state diff, by table and index |
| `TXDIFF` | `0xb7` | one keyed lookup: a slot, balance or code hash before and after, or a per-address or per-topic view |
| `EVENTDATACOPY` | `0xb8` | the non-indexed data of one event, into memory |

`POST_TX` frames run last, read-only. If one reverts or halts, everything the frames after the
validation prefix did is reverted, the remaining frames are skipped, and the transaction stays
valid with its gas paid. A wallet can therefore bound what a transaction may do: "no token
balance of mine drops by more than X", "no approval is granted", and so on.

## How to use it

1. Build the transaction as usual: a validation prefix that approves execution and payment,
   then the frames doing the work.
2. Append one or more `POST_TX` frames. Each targets an assertion contract, has flags 0 and
   value 0, and runs with `ENTRY_POINT` as the caller under `STATICCALL` rules.
3. In the assertion contract, read the diff and revert when an expectation fails.

For example, an assertion that the transaction changed exactly one storage slot. `TXTRACE`
takes `param` on top of the stack and the index below it:

```text
PUSH1 0x00   ; index
PUSH1 0x01   ; param 0x01: slots_changed
TXTRACE      ; 0xb6
PUSH1 0x01
EQ
PUSH1 <ok>
JUMPI
PUSH1 0x00
PUSH1 0x00
REVERT       ; the assertion fails: the execution body is reverted
<ok>: JUMPDEST
STOP
```

The frame receipts tell the outcome. A failing assertion has status `0`. The body frames keep
their status and execution gas, with no logs and no state gas. Any later `POST_TX` frame has
status `2` and no gas.

## Architecture

```text
Static validity (crates/common/types/transaction.rs, validate_static_constraints)
  mode 3 = POST_TX; modes 4-255 reserved
  POST_TX frames form a trailing suffix
  no atomic batch flag on a POST_TX frame, nor on the frame before one

Frame loop (crates/vm/levm/src/vm.rs, execute_frame_tx)
  POST_TX: caller ENTRY_POINT, static, default code behaves as for SENDER/DEFAULT
  the frame that sets the payer ends the validation prefix:
    capture ExecutionBody = substate level, state-gas counter, approvals,
                            prefix receipts' state gas, log count, BAL checkpoint
    every later frame's first-seen originals are absorbed into its backup
  a POST_TX frame fails:
    revert the body substate, restore the cache and BAL from the body backup,
    zero the body receipts' logs and state gas, skip the remaining frames
  APPROVE in a POST_TX frame halts (OpcodeNotAllowedInStaticContext)

Diff (crates/vm/levm/src/db/gen_db.rs, crates/vm/levm/src/opcode_handlers/tx_assertion.rs)
  tx_prestate: each account and slot as the transaction first touched it,
               installed by VM::new only for a transaction with a POST_TX frame
  tables recomputed per read from tx_prestate and the live cache:
    balances_changed, slots_changed, contracts_deployed  (ascending address, then slot)
    events = logs of the completed frames, in receipt order
```

`TXDIFF` params `0x00` to `0x05` may read a key the transaction never touched. They are priced
like `SLOAD` and `BALANCE` (warm or cold under EIP-2929, at the fork's EIP-8038 values), warm the
key, and record it in the block access list. Every other param of both opcodes costs
`WARM_STORAGE_READ_COST` (100). `EVENTDATACOPY` is priced like `CALLDATACOPY`, but halts on a
range past the end of the data instead of zero-padding.

## Design decisions

- **The prestate is recorded on first touch.** Each account and slot enters `tx_prestate` the first
  time the transaction resolves it, on every resolution path: cache hit, the block-level baseline,
  the block access list overlay, the shared base or the store. The cache outlives one
  transaction, so its entries cannot serve as the prestate. Only accounts and slots the
  transaction touched can differ, so iterating that map enumerates the diff. execution-specs
  iterates the transaction's write sets instead. The two could only disagree on a storage wipe
  during the transaction, which the EIP leaves to the fork's creation rules: ethrex applies
  EIP-7610's storage collision rule to `CREATE`, so a creation never wipes storage here, and the
  removal of an empty account happens after the last frame.
- **Seeding from the block access list does not record.** On the parallel import path a partially
  covered account is loaded from its pre-block base before the access-list prefix is overlaid. The
  capture is suspended for that nested load, so the prestate is the account as earlier
  transactions left it.
- **`param` is on top of the stack** for both `TXTRACE` and `TXDIFF`, as ethereum/EIPs#12461
  states. `FRAMEPARAM` takes its index from the top instead, so the two orders differ.
- **The rollback point follows the payer.** The body begins after the frame that sets `payer`, so
  everything that frame did survives a failing assertion, including EIP-8250's nonce
  consumption, which EIP-8250 forbids a restore that discards the execution body to revert.
- **The body backup is separate from the batch machinery.** No batch can contain or end on a
  `POST_TX` frame, so no batch is open when one fails, and the body's substate level sits directly
  below the failing frame's. Transactions without `POST_TX` frames capture nothing.
