# EIP-8312: UTXO Frame

> **Spec target:** nerolation/EIPs `EIPS/eip-8312.md` @ commit `a5da3f608c6dfbf353bea264054d99fc164ab10c` (2026-07-11; Draft, Standards Track: Core; requires EIP-2780, EIP-8037, EIP-8038, EIP-8141).
>
> Stamp a COMMIT, never a date — a Draft's text moves under you.

Implementation notes for EIP-8312 in ethrex. Builds on EIP-8141 frame transactions and composes with EIP-8250, EIP-8272, EIP-8037, EIP-7928 and EIP-7708. Unlike the rest of that family it does **not** activate at `Fork::Hegota` — see [Activation](#activation).

## Overview

A UTXO is a one-shot payment object. Anyone creates one by depositing to a vault system contract at `0x8312` with a 20-byte recipient as calldata; the protocol assigns a global index and, at the end of the block, commits the block's creations to an openings Merkle root in the vault's storage. Spending is a new frame mode that runs **no EVM code**: the frame carries Merkle proofs of the openings, the protocol verifies them against the stored roots, sets an irreversible spent bit, enforces value conservation including fees, and settles the payouts after all frames execute.

The only permanent state per UTXO is one bit. Because gas payment is part of the frame's conservation rule, a recipient can spend while holding no ETH.

For what this buys and where it does not help, see [EIP-8312 use cases](eip-8312-use-cases.md).

## Life of a UTXO

```
  CREATE (any tx)                    BLOCK END                      SPEND (frame mode 5)
  ───────────────                    ─────────                      ────────────────────
  CALL 0x8312                        collect UtxoCreated            frame carries:
    value: 1 ETH          ──────▶      receipt logs         ──────▶   openings + Merkle proofs
    data:  <recipient>               order by index                   actor signatures
                                     ring[N % 8192] = root           outputs + fee caps
  vault assigns index N              batch[N / 8192] = root                  │
  emits UtxoCreated                    (at boundaries)                       ▼
  (no account leaf                                                  protocol verifies proofs
   for the recipient)               the opening itself is            against a stored root,
                                    NOT stored on chain —            sets spent bit,
                                    the owner keeps it               checks conservation,
                                                                     runs no EVM code
                                                                            │
                                                                            ▼
                                                                    SETTLEMENT (after all frames)
                                                                    change = spent − out − fee
                                                                    pay account outs from vault
```

Four properties of that shape carry the design, and each is load-bearing rather than incidental:

1. **An opening is off-chain data.** On-chain there is only a Merkle root per block plus one spent bit per consumed UTXO. Losing an opening loses the funds — this is the trade the design makes for shrinking permanent state, and it is why the recipient of a UTXO needs a wallet that stores something.
2. **A witness is refreshable by anyone.** The spend hash covers the opening's identity (`index`, `creation_block`) but not the proof bytes, so a proof against a ring root can be swapped for one against a batch root after the ring wraps, without a new signature. This is what makes a signed spend survive time.
3. **The fee can come out of the payment.** Because a spend is a frame, conservation is checked before any fee is collected, so a self-funded spend needs `spent ≥ signed_out + max_cost` and no prior balance. An opcode-based design cannot express this: gas is already prepaid by the time an opcode runs.
4. **The spent bit must outlive every revert.** Everything above is undone by a normal rollback; the spent bit must not be, or the same UTXO could be replayed inside one transaction. Hence the durable-write tier — see the *Durable spent bits* row below.

## Implemented (this branch)

| Piece | Detail |
|-------|--------|
| Frame mode `UTXO` | Wire byte **5** (see divergence 1). Executes no EVM code; dispatched natively in the frame loop before any target or delegation resolution, because the vault carries real runtime code and a target-based interception would make semantics depend on code that must never run for a spend. |
| Spend payload | `Frame.data` is the strict RLP of `[actors, inputs, utxo_outs, account_outs, change_index, payer, max_fee_per_gas, max_priority_fee_per_gas, max_gas_limit]` (`crates/common/types/utxo.rs`). Trailing bytes — after the payload or inside any nested list — are rejected. |
| Spend hash | `keccak256(0x81 ‖ rlp([chain_id, actors, [[index, creation_block]…], utxo_outs, account_outs, change_index, payer, fees, max_gas_limit]))`. Per-input witness fields are excluded, so anyone can refresh a witness (e.g. upgrade a ring proof to a batch proof) without invalidating a signature. `0x81` is outside the EIP-2718 type space, so a spend-hash preimage cannot collide with any transaction's signing payload. |
| Actor signatures | Each actor needs an EIP-8141 signature entry with a protocol-validated scheme (ARBITRARY does **not** qualify), resolved signer equal to the actor, and explicit `msg` equal to the spend hash. |
| Vault predeploy | `0x8312`, nonce 1, the spec's pinned 76-byte runtime verbatim (`crates/vm/system_contracts.rs`). Installed idempotently at activation on **both** the build path (`Evm::apply_system_calls`) and the import path (`LEVM::prepare_block`); a one-sided install would diverge builder from importer. A pre-existing balance is preserved as inert surplus (conservation bounds every frame's outflows by its proven inputs, so surplus can never be spent). |
| Openings tree | `leaf = keccak256(index_be8 ‖ source ‖ recipient ‖ value_be32)`; `merkle_root` appends **zero leaves until the count is a power of two** (see divergence 5), folds with `keccak256(left ‖ right)`; `fold` takes sibling order from the position bits. One definition in ethrex-common, shared by root construction, proof verification and mempool policy — the EIP-8272 forged-roots hole came from duplicating commitment logic. |
| Storage layout | `SLOT_NEXT_INDEX = 0`; ring `1 + N % 8192`; batch roots `2**128 + N/8192`; spent bits `2**129 + (index >> 8)`, bit `index & 0xFF`. Regions are provably disjoint for `index, block < 2**64`. |
| Block-end roots | `LEVM::write_openings_roots` collects leaves from the block's `UtxoCreated` **receipt logs** (the EIP-6110 pattern), orders by index, writes the ring root unconditionally — including the all-zeros root of an empty block, which *clears* the entry from one ring length ago — and seals the batch root at each batch boundary. Protocol-direct write, no gas, manually BAL-recorded. Wired into all four paths: build, sequential import, pipeline, parallel-BAL import. |
| Durable spent bits | Staged on the VM during the frame loop and flushed once at transaction commit (`crates/vm/levm/src/vm.rs`). Durability comes from **ordering**, not a special write: a staged write is absent from the cache while the loop runs, so every scope revert (frame failure, atomic-batch unroll) restores a cache that never contained it. The flush uses the ordinary journaled path, so the write stays reversible by `undo_last_tx` and is BAL-recorded exactly once, with no checkpoint left that could demote it to a read. |
| Gas | Every constant derived from EIP-8038/2780/8037 primitives with compile-time asserts against the EIP's published totals: `GAS_UTXO_FRAME 13000`, `GAS_UTXO_INPUT 16048`, `GAS_UTXO_SIBLING 42`, `GAS_UTXO_OUT 2012`, `GAS_UTXO_ACCOUNT_OUT 9000`; state components `GAS_UTXO_SPENT_STATE` = ⌈`state_gas_storage_set`/256⌉ = 383 and `GAS_NEW_ACCOUNT_STATE` = `state_gas_new_account` = 183,600, both taken from the live EIP-8037 values rather than literals. An under-provisioned frame invalidates the transaction (not merely the frame). |
| 2D gas | Spent-bit state gas accumulates in a dedicated counter excluded from the per-frame, per-batch and body state-gas resets — those reset on the premise "reverted state ⇒ no state grew", which durable writes falsify — and is folded into the transaction's state gas after the loop. |
| Settlement | Two phases, per the spec's ordering requirement. Phase 1 (before gas finalization) returns the `GAS_NEW_ACCOUNT_STATE` reserve for account outputs whose recipient already exists, evaluated before any of this transaction's transfers. Phase 2 (after the fee is known) computes `change = spent − signed_out − fee`, creates UTXO outputs (allocating from the same counter deposits use) and credits account outputs from the vault balance. Settlement cannot fail: execution proved every frame solvent. |
| Logs | `UtxoCreated` (LOG3 from the vault, `data = index ‖ value`) for each created UTXO, plus the EIP-7708 transfer log for each account output — whose 1,756-gas cost is priced into `GAS_UTXO_ACCOUNT_OUT`. Settlement logs are appended to the **originating UTXO frame's** receipt entry, per the spec, and to the transaction aggregate the header/receipt blooms derive from. |
| Payer | Self-funded (`payer` empty): conservation requires `spent ≥ signed_out + max_cost`, then the vault becomes the payer and is debited `max_cost` at frame execution exactly as `APPROVE(APPROVE_PAYMENT)` debits a paymaster; the standard end-of-transaction refund returns `charged − owed`, so the vault is debited precisely the actual fee — which is what settlement subtracts from the change. Sponsored: conservation excludes the fee, and the payer comes from the ordinary APPROVE flow. |
| Vault-sender carve-outs | A transaction whose sender is the vault: no nonce keys required, `nonce_seq` must be zero, blobs forbidden **at consensus level** (nothing signs the envelope, so an unenforced field would be freely malleable), must contain at least one UTXO frame (otherwise nothing prevents replay), and the `sender_approved` precondition of `APPROVE(APPROVE_PAYMENT)` is waived — the vault's code never calls APPROVE, so without the waiver no sponsor could ever pay for a spend. |
| Mempool | `MAX_UTXO_VERIFY_GAS = 400_000` (`--mempool.max-utxo-verify-gas`), a lane disjoint from `max_verify_gas`; a self-funded spend is recognized as its own validation prefix with no EVM simulation; each UTXO frame's inputs are pre-verified against head state by native vault-storage reads (openings/batch root and spent bit), ordered after static validation, signature auth and the statically-computable budget check so per-input reads cannot be provoked cheaply; UTXO input indices are tracked in a **global** per-index map (one pending transaction per index, since two spends of one index conflict whoever submitted them), and vault-sender transactions are kept out of every per-sender map — they all share sender `0x8312`, so per-sender keying would cap the network at one pending spend. A build failure whose input is not spendable *yet* is typed (`UtxoNotYetSpendable`) and keeps the transaction pooled; every other UTXO failure evicts. |

## Divergences from the spec

1. **Frame mode 5, not 3.** The spec specifies `UTXO_MODE = 3`. ethrex places UTXO at 5 instead, leaving 3 unassigned and 4 reserved for EIP-8288's deferred DEP_VERIFY. Recorded as a divergence rather than adopted as written because a wire byte a client or tool may already treat specially is not free to repurpose retroactively; leaving 3 unassigned keeps mode resolution independent of any such history. **This is an upstream problem** — EIP-8141 needs a shared frame-mode registry for the EIPs that extend it — and has been raised with the authors.

2. **Activation is a dedicated timestamp, not `Fork::Hegota`.** EIP-8312's fork assignment is undecided upstream, so pinning it to Hegota would assert something unknown. See [Activation](#activation). A future timestamp also makes the upgrade state-preserving, which is what lets a running chain adopt it with no new genesis.

3. **`payer` is length-tested, never compared to numeric zero.** The spec's pseudocode writes `len(spend.payer) in (0, 20)` and then `if spend.payer == 0`, which makes 20 zero bytes readable either as self-funded or as sponsor `address(0)` — the same bytes valid on one client and invalid on another. ethrex treats self-funded as *empty* only and rejects a 20-byte zero address outright. Reported upstream.

4. **`merkle_root` pads to a power of two, per the spec's pseudocode.** Recorded because the natural paraphrase ("pad odd levels with a zero") is a *different* algorithm: the two agree up to four leaves and diverge from five on. Pinned by a test that computes both and asserts they differ.

5. **Blob asymmetry is enforced as written.** Only vault-sender transactions are forbidden blobs; a sponsor-as-sender transaction carrying UTXO frames may carry blobs, uncapped by any signed spend field. Flagged upstream as probably-unintended rather than changed unilaterally.

Further items raised with the authors but not diverged on (they concern the spec text, not our behavior) are collected outside the repo with the change's planning notes: the undefined `tx_gas_limit`, the undefined gas dimension of the reserve return, the unstated canonical-RLP requirement, the forgeable leaf-set definition, the fee-cap-is-the-fee economics of unsigned envelopes, and the spent-bit charge being exact only at spend-fraction 1.

## Activation

EIP-8312 has its own chain-config timestamp, `utxoFramesTime`, and `ChainConfig::is_utxo_frames_activated` is the single predicate every gate derives from: frame-mode admissibility, execution dispatch, vault provisioning, the openings-root block-end operation, and mempool admission. Two gate sites resolving activation differently is a documented stall class on this codebase — do not reintroduce it.

Activation additionally requires Hegota, because a UTXO frame is a frame inside an EIP-8141 frame transaction. The field is absent on every existing network and fixture, so the implementation is entirely inert until a chain opts in: mode 5 stays reserved, no vault is provisioned, no openings roots are written, no UTXO transaction is admissible.

The live-devnet rollout procedure, including the point past which rollback is no longer
possible, is [in the upgrade guide](../scripts/hegota-devnet/UPGRADE-GUIDE.md).

Two consequences worth stating:

- **The upgrade is state-preserving.** With a future timestamp, every already-produced block re-executes byte-identically, so a running chain adopts EIP-8312 without a new genesis.
- **The field is invisible to ForkId** (like the branch's other config-scheduled behavior), so there is no peer-level protection at the boundary. Every execution node must run the EIP-8312 binary with the timestamp configured before it arrives. A node running the binary against a config with no timestamp behaves as if EIP-8312 were unscheduled — it never falls back to a fork — so an un-patched node degrades by rejecting UTXO transactions, never by rewriting history.

## Composition with the rest of the family

- **EIP-8250 (atomic batches).** A UTXO frame must have `flags == 0` and must not immediately follow a flagged frame. That is exactly the batch-terminator defense: a frame after a flagged frame is the batch's terminator and reverts with the batch, which irreversible spent bits forbid. The spec's own placement rule already encodes this. The durable-write tier is also the mechanism EIP-8250's mandated nonce durability needs (a known unimplemented gap here); retrofitting it is future work.
- **EIP-8272 (recent roots).** Disjoint addresses and namespaces, no interaction. Patterns adopted from it: the single-definition rule for commitment logic, admission-time native predeploy reads, and the transient-vs-permanent failure split that keeps the builder from evicting transactions the next block would make valid.
- **EIP-7928 (block access lists).** Every write outside the EVM is recorded by hand: the vault install, the durable spent-bit flush, and the block-end root writes. The parallel importer derives the state root *from* the BAL, so an unrecorded write is a state-root divergence even when execution is correct.
- **EIP-8037 (2D gas).** Frame transactions get no state-gas reservoir, so a UTXO frame's state components are drawn from the frame's `gas_limit` alongside the regular ones — users must budget both dimensions inside each frame's limit.
- **EIP-7708 (transfer logs).** Settlement's account-output credits emit transfer logs, whose cost is priced into `GAS_UTXO_ACCOUNT_OUT`. Vault deposits emit theirs through the ordinary CALL path.

## Verified on a devnet

Exercised on the Hegotá devnet configuration — `fixtures/networks/hegota-devnet.yaml` with only
the EL image tag and the published port bases changed, so the fork schedule, the EIP-8282 builder
predeploys and the frame-tx-aware Dora are the ones that network runs. Three independent ethrex
instances, so agreement demonstrates determinism across the build and import paths, not
cross-client interop (no other client implements EIP-8312).

`utxoFramesTime` was scheduled two epochs after Hegotá and patched into each EL's chain config
post-boot, per [Path 2's generator-cannot-emit variant](../scripts/hegota-devnet/UPGRADE-GUIDE.md).
Results, from [`scripts/hegota-devnet/utxo_itest.py`](../scripts/hegota-devnet/utxo_itest.py):

- **7/7 cases pass, and pass again on a re-run** against a chain that already carries UTXO
  history — the suite derives throwaway accounts per run so it stays idempotent.
- **Activation was clean.** The vault appeared at the first block past the timestamp, the chain
  never paused, and all three ELs stayed in consensus across both fork boundaries.
- **The upgrade is state-preserving.** Restarting an EL after activation re-executed its replay
  tail across the boundary with zero `World State Root does not match` — which is the property
  the whole no-re-genesis upgrade path rests on.
- No errors in any EL log through activation and the UTXO traffic.

Two things this still does **not** establish. It was a fresh chain, not an in-place upgrade of the
long-running devnet, so the production rollout is rehearsed but not performed. And batch-proof
spends remain unit-tested only: they need a chain older than `BATCH_SIZE` (8,192) blocks, about
14 hours at 6-second slots.

Measured from receipts on that chain, not from the spec's estimates:

| Flow | Gas | Permanent state |
|------|-----|-----------------|
| Vault deposit (create one UTXO) | 36,334 | none |
| Spend (1 input, depth-1 proof, 1 account output + change) | 56,094 | one spent bit |
| Full cycle | 92,428 | ~0.3 B |
| Plain transfer to a fresh account, same chain | 204,600 | ~120 B account leaf |

Figures are from one measured run; spend gas varies by a few tens of gas with the recipient
address's zero-byte count in the frame's calldata.

The full cycle costs ~2.2× less gas than one fresh-account transfer, and the gap in the *state*
dimension — which is what saturates a block first under EIP-8037 — is far larger. A recipient
holding zero wei spent successfully, with the fee drawn from the payment.

Two bugs surfaced only on a live chain and are worth recording, because both were invisible to
unit tests by construction:

- A protocol-direct storage write that skipped the initial-storage bookkeeping made blocks
  unbuildable at the first openings-root write — the chain halted with no EL-side error, only the
  consensus client's engine call failing. Any protocol write must go through a path that records
  the pre-state it read.
- A second, redundant derivation of the validation prefix rejected every valid self-funded spend.
  It was masked in testing because forged-proof transactions were rejected earlier, so only
  *correct* spends reached the broken check. Duplicated classification logic is the recurring
  failure mode on this branch; both sites now share one predicate.
