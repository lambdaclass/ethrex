# EIP-8288: Frame Type for PQ Sig and STARK Aggregation

> **Spec target:** ethereum/EIPs `EIPS/eip-8288.md` @ commit `ef1abf4b6d` (2026-09-09; Draft, Standards Track: Core; requires EIP-2718, EIP-8141).

Implementation notes for EIP-8288 in ethrex. Builds on EIP-8141 frame transactions; activates under `Fork::Hegota` alongside the rest of that family.

## Overview

EIP-8288 adds one frame mode to EIP-8141. A frame with mode `DEP_VERIFY_FRAME_MODE` (`3`) carries no code and is never executed. Its `data` is a list of 96-byte `(scheme, data_hash, verification_key_hash)` triples, each naming a post-quantum signature (leanSPHINCS) or a STARK (leanSTARK) that **something else** must prove. The proof does not travel with the transaction: the block carries a single recursive STARK in its header that proves every dependency declared by every transaction in it at once. That is the whole point — a hash-based signature costs 2-3 kB and 150k-200k gas to verify individually, and aggregating thousands of them into one recursive proof is what makes them affordable.

The execution layer's job is therefore narrow: recognise the frame, validate its shape, charge for it, expose it to EVM introspection, and compute the dependency set the block's proof is checked against.

## Scope: what is implemented, and what cannot be

The EIP is a draft whose proving half is not yet specifiable. `AGGREGATED_VK` is literally `TBD` in the constants table, the Reference Implementation section is `TBD`, and the recursive proof is defined in terms of Lean Ethereum tooling that has no released verifier to link against. Nothing that depends on those can be written yet, by anyone.

**Implemented and tested here:**

| Piece | Detail |
|-------|--------|
| Frame mode | `FrameMode::DepVerify = 3`. An earlier note in this repository put it at 4 while the EIP was unpublished; `ef1abf4b6d` assigns 3. |
| Triple | `DependencyTriple { scheme, data_hash, verification_key_hash }`, `encode()` / `from_bytes()` over the 96-byte form: 31 zero bytes, the scheme byte, then two 32-byte hashes. Parsing rejects non-zero padding and unassigned scheme bytes. |
| Static validity | In `validate_static_constraints`: data is a whole number of well-formed triples, count in `1..=256`, `target` absent, `flags == 0`, `limits.state == 0`, and `limits.execution` exactly the verification-gas sum. |
| Dependency sets | `Frame::dependency_triples`, `FrameTransaction::dependencies` (deduplicated and sorted), `FrameTransaction::declared_dependency_count` (not deduplicated, for gas). |
| `block_deps_hash` | `dependencies_hash`: BLAKE3-256 over the concatenated 96-byte triples of a normalised list. |
| Execution | The frame completes without running: no target resolution, no frame-entry access charge, a frame receipt with `status = 1`, `gas_used.execution = limits.execution`, `gas_used.state = 0`, no logs. Its declared execution gas is consumed in full and is not refundable. |
| Introspection | Unchanged. `FRAMEPARAM` `0x02` reports mode `3`, `0x04` reports `len(data)`, and `FRAMEDATACOPY` / `FRAMEDATALOAD` read the triples, because the frame keeps its index and its receipt entry. |
| Prefix transparency | `validation_prefix` skips dependency frames from any position, so a transaction may put one before the approving VERIFY frame, as the EIP's own test cases do. Their gas is **not** counted toward `MAX_VERIFY_GAS`. |
| Mempool limits | `MAX_SIGS_PER_TX` (16) and `MAX_STARKS_PER_TX` (1) at admission, over the deduplicated set, as peer policy rather than block validity. |
| Atomic batches | A dependency frame may not sit inside one. `flags == 0` bars it from being a member; without this it could still *terminate* a batch. |

**Not implemented, and why:**

| Piece | Blocker |
|-------|---------|
| Recursive STARK generation and verification | `AGGREGATED_VK` is `TBD`; no Lean Ethereum verifier exists to link. |
| `recursive_stark` header field | Its payload is the proof above. Adding the field without a verifier would let any bytes satisfy block validity, which is worse than not having it. |
| Block validity rule 2 (proof verifies) | Same. Rule 1, the `block_deps_hash` match, is computable today and the machinery for it is in place. |
| Mempool wrapper object, modes 0 and 1 | Both carry proofs. |
| Recursive mempool aggregation | Requires a prover. |
| FOCIL `recursive_stark` extension | Requires a prover. |
| `recursive_stark_gas` | Has no defined payer or mechanism; see notes item 10. |

## Where the spec was ambiguous

Twelve questions had to be answered before any of this could be written. They are argued in full, with suggested spec text, in [`scripts/hegota-testnet/NOTES-FOR-8288-AUTHOR.md`](../scripts/hegota-testnet/NOTES-FOR-8288-AUTHOR.md). The readings this implementation adopts:

| Question | Reading adopted | Notes item |
|---|---|---|
| The EIP names `FRAMEDATASIZE` as an EIP-8141 instruction | No such instruction exists; `FRAMEPARAM` `0x04` gives `len(data)` | 1 |
| "The frame's `gas_limit`" — frames have `limits = [execution, state]` | The sum binds `limits.execution`; `limits.state` must be `0` | 2 |
| "`target` must be `None` (address `0x00...00`)" | `target` absent. In EIP-8141 an absent target resolves to `tx.sender` and an explicit zero address does not, so the gloss contradicts the requirement | 3 |
| What `FRAMEPARAM` `0x05`/`0x0A`/`0x0B` return for a frame that never executed | The frame completes and gets a receipt: `status = 1`, `gas_used.execution = limits.execution`, `gas_used.state = 0` | 4 |
| "Gas is still fully charged" vs EIP-8141's refund of unused frame gas | Consumed in full, not refundable | 5 |
| Are `MAX_SIGS_PER_TX` / `MAX_STARKS_PER_TX` consensus or mempool rules | Mempool only; a block carrying more is valid | 7 |
| Which hash function | BLAKE3-256, named only in Security Considerations | 8 |
| Sort order for `deduplicate_and_sort` | Lexicographic over the 96-byte encoding, not over the tuple | 9 |
| Where a dependency frame may sit | Anywhere; transparent to prefix matching, which is the only reading under which the EIP's own Test Cases 1 and 2 are valid transactions | 12 |
| Atomic batches, which the EIP never mentions | A dependency frame may not sit inside one. `flags == 0` already bars it from being a member, but would let it *terminate* a batch, putting the commit on a frame with no outcome | 13 |
| Does a dependency frame's gas count toward `MAX_VERIFY_GAS` | No; it executes nothing | 12 |

Every one of these is a place where a different choice produces a different chain. If the spec resolves one the other way, the tests named in the next section are where to start.

## Gas

A dependency verification frame declares exactly

```
limits.execution = sum(3_000 if t.scheme == LEANSPHINCS else 30_000 for t in triples)
limits.state     = 0
```

and consumes all of it. Because EIP-8141 already sums every frame's declared limits into `standard_gas_limit`, the charge reaches the transaction's gas total with no special case; what needed adding is the non-refundability, since a frame that runs nothing would otherwise have its whole budget returned.

Duplicate declarations are charged per declaration and deduplicated in the dependency set, so `declared_dependency_count()` (gas) and `dependencies().len()` (the set) differ for a transaction that repeats a triple. Both are exercised by `duplicate_declarations_are_charged_but_deduplicated`.

## Tests

`test/tests/common/eip8288_tests.rs`. The constants are asserted against the EIP's published table rather than against each other, so an upstream repricing fails loudly instead of silently re-tuning gas. Tests that pin an ambiguous reading name the notes item they settle.
