# EIP-8288: Frame Type for PQ Sig and STARK Aggregation

> **Spec target:** ethereum/EIPs `EIPS/eip-8288.md` @ commit `ef1abf4b6d` (2026-09-09; Draft, Standards Track: Core; requires EIP-2718, EIP-8141).
>
> **Fork:** J\* (`Fork::JStar`, between Hegotá and LStar). Not part of the Hegotá testnet rule set.

Implementation notes for EIP-8288 in ethrex. Builds on EIP-8141 frame transactions.

## Overview

EIP-8288 adds one frame mode to EIP-8141. A frame with mode `DEP_VERIFY_FRAME_MODE` (`3`) carries no code and is never executed. Its `data` is a list of 96-byte `(scheme, data_hash, verification_key_hash)` triples, each naming a post-quantum signature (leanSPHINCS) or a STARK (leanSTARK) that **something else** must prove. The proof does not travel with the transaction: the block carries a single recursive STARK in its header that proves every dependency declared by every transaction at once. That is the point — verifying a hash-based signature individually costs 150k-200k gas, and aggregating many into one recursive proof is what makes them affordable.

## Status: the proving half is real, not stubbed

An earlier revision of this document recorded the proving half as unimplementable because the EIP lists `AGGREGATED_VK` as `TBD`. That was wrong in an important way. The spec says TBD, but [the tooling it names](https://github.com/leanEthereum/leanVM) exists and works: leanVM is Rust, edition 2024 like ethrex, and exposes `EthereumProof::verify`, `to_bytes`/`from_bytes` and `aggregate`. All twelve of its crates build against ethrex's stable toolchain.

So the aggregation here is **real**. `a_real_aggregate_verifies_against_the_dependencies_it_proves` produces an actual recursive proof over two leanSPHINCS dependencies and verifies it, and asserts that a proof over a different set — or a strict subset — does not satisfy the block.

| Piece | State |
|-------|-------|
| `DEP_VERIFY` frame mode, triples, static validity, gas, introspection | Implemented |
| `dependencies(tx)` / `dependencies(block)`, BLAKE3 `block_deps_hash` | Implemented |
| `recursive_stark` header field, fork-gated at J\* | Implemented |
| Block-validity rule 1 (digest matches the body) | Implemented, needs no backend |
| Block-validity rule 2 (the proof discharges the set) | Implemented, needs a backend |
| Aggregation backend (leanVM) | Implemented, behind the `leanvm` feature |
| Mempool wrapper object, modes 0 and 1, and their receive checks | Implemented |
| Mempool wrapper **transport** | Not implemented — the EIP specifies none. `Blockchain::ingest_wrapper` is the entry point a transport would call |
| Witness store, gating admission and feeding the builder | Implemented |
| leanSTARK (`0x11`) dependencies | No counterpart in leanVM. Refused admission to the mempool, and a block already carrying one is "cannot verify" rather than "invalid" |
| Re-aggregation loop, FOCIL `recursive_stark` | Not implemented |
| `recursive_stark_gas`, the block-level charge | Not implemented. It has no payer, no counter and no stated interaction with EIP-1559. `declared_dependency_count` exists to feed it if the EIP resolves that |
| Proving inside block production | Implemented. `finalize_payload` aggregates from the witness store over exactly the set the block declares. A block declaring nothing carries an empty proof and pays nothing, so a chain nobody uses this on never runs a prover |
| Rule 2 inside the stateless guest program | Not implemented. Rule 1 runs there, since `validate_block_pre_execution` is called in the guest and needs only the body. Rule 2 would mean verifying a leanVM STARK inside SP1 or RISC Zero — a proof of a proof — which is far outside this scope. A stateless proof therefore attests that the header's digest matches the body, not that the aggregate discharges it. |

## Architecture: one seam

`ethrex-dep-aggregation` holds the `DependencyAggregator` trait and both implementations. Nothing outside that crate names a leanVM type, because leanVM restructures its crate layout between revisions — the revision `ethlambda` pins exports crate names that no longer exist upstream.

- **`UnavailableAggregator`** is the default and **fails closed**. A node with no backend still enforces rule 1, which is computed from the block's own transactions, but must reject a block carrying a proof rather than wave it through. This is deliberately the opposite of `ExecBackend` in `crates/prover/`, whose `verify` returns `Ok` and warns — right for a developer convenience, wrong for a consensus rule.
- **`LeanVmAggregator`** is behind the off-by-default `leanvm` feature, pinned to leanVM `7f9777da6a`.

`LEANVM_AGGREGATOR` mirrors `ethrex_crypto::NATIVE_P256_BACKEND` so a test can assert which backend it is exercising, rather than a stub silently standing in for a verifier.

**leanVM must be built optimised.** Its own cargo aliases are `test --release`; under a debug profile its circuit builder panics on an overflow check during warm-up. The workspace carries `[profile.dev.package.*]` overrides for its crates.

## Costs, measured

leanVM's published figures (M4 Max) and what they imply here:

| | |
|---|---|
| Verification | ~4 ms steady state, after a one-off circuit build that `LeanVmAggregator::new` pays up front |
| Proof size | ~300 KiB, about 4% of the 8 MiB `MAX_RLP_BLOCK_SIZE` |
| Proving | ~1 s at 9-11 GiB peak resident memory, for a large aggregate |

That last figure is why EIP-8288's proving cost sits **in** the builder's critical path rather than beside it: the proof is inside the header, so it cannot be filled in afterwards without changing the block hash. `finalize_payload` therefore aggregates before the payload is published, and a block whose transactions declare nothing skips the run entirely.

## Where the spec is ambiguous, and what this implementation reads it as

EIP-8288 leaves a number of questions open that have to be answered before any of it
can be written. The load-bearing ones, and the reading adopted here:

| Question | Reading adopted |
|---|---|
| Block-validity rule 2 reads as one check against `block_deps_hash` | Two checks. The proof verifies, **and** the claims it proves equal `dependencies(block)`. A leanVM aggregate publishes claim lists and does not bind a caller's digest, so without the second step any valid aggregate satisfies any block |
| `AGGREGATED_VK` is `TBD` | So is the thing it would name: leanVM publishes no digest of its circuit. This binds to the pinned revision and says so |
| No bound on the proof, which rides in the header | Capped at 1 MiB, against EIP-7934's block limit |
| `verification_key_hash` names no hash function | BLAKE3-256, matching `block_deps_hash`. For leanSPHINCS the key is already exactly 32 bytes, so the indirection compresses nothing |
| "Cannot verify" versus "invalid" | Separate errors with separate fork-choice and engine-API outcomes. A node with no verifier must not tell its consensus client that a chain everyone follows is bad |
| Wrapper limits | Enforced as published, and pinned by a test — at 16 per wrapper and 16 per transaction, one maximally-loaded transaction fills a wrapper, and no wrapper ever carries more than 16 signatures however they are spread |
| Wrapper transport | None invented. The EIP specifies no devp2p message |
| A wrapper may name transactions by hash | Rejected. Rule 1 needs the transaction, and with no wrapper transport there is nothing to resolve a hash against; the EIP defines no resolution or miss behaviour either |
| The empty dependency set | An empty `dependencies(block)` is discharged by an empty `stark_proof`, and rule 2 short-circuits before reaching a backend. Without this a build with no backend could not follow a J\* chain at all, since the header entry is mandatory from J\* on |
| Which activation predicate governs | The fork **ordinal**, not `jstarTime` alone. A schedule naming a later fork without a `jstarTime` otherwise makes the frame mode legal while the header field and both block rules stay off |
| `FRAMEDATASIZE`, `frame.gas_limit`, `target == None (0x00…00)`, the frame's receipt, gas refundability, sort order, atomic batches, header field position | Each is settled by a test in `test/tests/common/eip8288_tests.rs` that names the ambiguity it decides |

## Where this is stricter than the spec, and why that is a risk

Most of the table above resolves silence in the EIP. Two rules go further: they
**reject something the spec, read literally, permits**. Each is defensible on its own
terms, and each is a consensus split waiting for a second client — a block or
transaction another implementation accepts and this one does not is a chain split, not
a policy difference. They are listed here so the divergence is visible rather than
buried in a validation function, and both need to land in the EIP text or a second
implementation will not have them.

| Rule | What the spec permits | What this does |
|---|---|---|
| A dependency frame may not sit inside an atomic batch, as member **or terminator** | EIP-8288 requires `flags == 0`, which excludes a flagged member but leaves a dep-verify frame a legal *terminator* of an EIP-8141 atomic batch. EIP-8288 never mentions batches | Reject the transaction |
| `stark_proof` is capped at 1 MiB, checked at header decode | The EIP bounds the proof nowhere. A larger proof that verifies is a valid block by the text | Refuse the header before the proof is ever read |

Three further restrictions are **local policy, not consensus**, and are safe for that
reason. A build with no backend refuses dependency-bearing transactions at mempool
admission, since it could not prove them; leanSTARK (`0x11`) dependencies are refused
for the same reason, no backend supporting the scheme; and a dependency whose witness
this node has not verified is refused, because admitting an unchecked claim would both
let a transaction's approval rest on a signature nobody established and leave the
builder unable to produce the proof its own block needs. None of the three affects
whether a block already produced is valid.

## Admission, and why it is deliberately closed

A transaction declares a dependency; nothing in it proves the named signature exists.
The proof travels separately, in a mempool wrapper. Two things follow.

- A node that tracked nothing would let a transaction whose approval rests on a
  declared signature pass validation-prefix simulation without ever establishing that
  the signature is real.
- A builder that included such a transaction would have to publish a proof
  discharging it, and could not build one.

`DependencyWitnessStore` answers both: a dependency is admissible only once its
witness has been verified, and the builder aggregates from the same material.
Witnesses enter through `Blockchain::ingest_wrapper`, which runs the EIP's receive
checks and keeps what a mode-0 wrapper establishes. Mode 1 yields nothing reusable —
one recursive proof over a whole set cannot be split back into per-claim material for
a later, different set.

Since EIP-8288 specifies no wrapper transport, nothing calls `ingest_wrapper` on its
own yet, so in practice a node admits no dependency-bearing transactions at all. That
is the safe direction, and it is the honest state of the feature rather than a
placeholder.

## Tests

Every test lives in the `test/` workspace, so none of it compiles into a node binary.

- `test/tests/common/eip8288_tests.rs` — triples, static validity, dependency sets, the header field's RLP and hash participation, and rule 1 driven through `validate_block_pre_execution` rather than through its parts.
- `test/tests/blockchain/eip8288_rule_tests.rs` — rule 2's arms (the empty set, the fork gate, no backend, an unsupported scheme) and the fork-choice mapping that keeps "invalid" and "cannot verify" apart.
- `test/tests/blockchain/eip8288_witness_tests.rs` — the witness store: what it keeps, what it refuses, and that a partial set is unusable.
- `test/tests/common/dep_aggregation_tests.rs` — the seam, fail-closed behaviour, the proof bound.
- `test/tests/common/eip8288_wrapper_tests.rs` — the wrapper object and its limits.
- `test/tests/common/leanvm_aggregator_tests.rs` — the real aggregate round trip, behind the `leanvm` feature, with the proving tests `#[ignore]`d for their memory cost:

```
cargo test -p ethrex-test --features leanvm -- --ignored leanvm_aggregator
```
