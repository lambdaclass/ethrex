# EIP-8288: Frame Type for PQ Sig and STARK Aggregation

> **Spec target:** ethereum/EIPs `EIPS/eip-8288.md` @ commit `ef1abf4b6d` (2026-09-09; Draft, Standards Track: Core; requires EIP-2718, EIP-8141).
>
> **Fork:** J\* (`Fork::JStar`, between Hegotá and LStar). Not part of the Hegotá testnet rule set.

Implementation notes for EIP-8288 in ethrex. Builds on EIP-8141 frame transactions.

## Overview

EIP-8288 adds one frame mode to EIP-8141. A frame with mode `DEP_VERIFY_FRAME_MODE` (`3`) carries no code and is never executed. Its `data` is a list of 96-byte `(scheme, data_hash, verification_key_hash)` triples, each naming a post-quantum signature (leanSPHINCS) or a STARK (leanSTARK) that **something else** must prove. The proof does not travel with the transaction: the block carries a single recursive STARK in its header that proves every dependency declared by every transaction at once. That is the point — verifying a hash-based signature individually costs 150k-200k gas, and aggregating many into one recursive proof is what makes them affordable.

## Status: the proving half is real, not stubbed

An earlier revision of this document recorded the proving half as unimplementable because the EIP lists `AGGREGATED_VK` as `TBD`. That was wrong in an important way. The spec says TBD, but [the tooling it names](https://github.com/leanEthereum/leanVM) exists and works: leanVM is Rust, edition 2024 like ethrex, and exposes `EthereumProof::verify`, `to_bytes`/`from_bytes` and `aggregate`. All twelve of its crates build against ethrex's stable toolchain.

So the aggregation here is **real**. `a_real_aggregate_verifies_against_the_dependencies_it_proves` produces an actual recursive proof over two leanSPHINCS dependencies and verifies it, and asserts that a proof over a different set — or a strict subset — does not satisfy the block.

| Piece | State |
|-------|-------|
| `DEP_VERIFY` frame mode, triples, static validity, gas, introspection | Implemented |
| `dependencies(tx)` / `dependencies(block)`, BLAKE3 `block_deps_hash` | Implemented |
| `recursive_stark` header field, fork-gated at J\* | Implemented |
| Block-validity rule 1 (digest matches the body) | Implemented, needs no backend |
| Block-validity rule 2 (the proof discharges the set) | Implemented, needs a backend |
| Aggregation backend (leanVM) | Implemented, behind the `leanvm` feature |
| Mempool wrapper object, modes 0 and 1, and their receive checks | Implemented |
| Mempool wrapper **transport** | Not implemented — the EIP specifies none (item 21) |
| leanSTARK (`0x11`) dependencies | No counterpart in leanVM. Refused admission to the mempool, and a block already carrying one is "cannot verify" rather than "invalid" (items 19 and 29) |
| Re-aggregation loop, FOCIL `recursive_stark` | Not implemented |
| `recursive_stark_gas`, the block-level charge | Not implemented. It has no payer, no counter and no stated interaction with EIP-1559, argued as item 10. `declared_dependency_count` exists to feed it if the EIP resolves that |
| Proving inside block production | Not implemented. `finalize_payload` sets the digest and leaves the proof empty, which is a **valid** block for as long as its transactions declare no dependencies — the empty-set arm of rule 2, and the reason a build with no backend can follow a J\* chain at all. A build that admits dependency-bearing transactions would produce a block it cannot prove, so wiring aggregation to the builder is a precondition for admitting them. Producing a real aggregate costs ~1 s and 9-11 GiB, which does not belong in `finalize_payload` |
| Rule 2 inside the stateless guest program | Not implemented. Rule 1 runs there, since `validate_block_pre_execution` is called in the guest and needs only the body. Rule 2 would mean verifying a leanVM STARK inside SP1 or RISC Zero — a proof of a proof — which is far outside this scope. A stateless proof therefore attests that the header's digest matches the body, not that the aggregate discharges it. |

## Architecture: one seam

`ethrex-dep-aggregation` holds the `DependencyAggregator` trait and both implementations. Nothing outside that crate names a leanVM type, because leanVM restructures its crate layout between revisions — the revision `ethlambda` pins exports crate names that no longer exist upstream.

- **`UnavailableAggregator`** is the default and **fails closed**. A node with no backend still enforces rule 1, which is computed from the block's own transactions, but must reject a block carrying a proof rather than wave it through. This is deliberately the opposite of `ExecBackend` in `crates/prover/`, whose `verify` returns `Ok` and warns — right for a developer convenience, wrong for a consensus rule.
- **`LeanVmAggregator`** is behind the off-by-default `leanvm` feature, pinned to leanVM `7f9777da6a`.

`LEANVM_AGGREGATOR` mirrors `ethrex_crypto::NATIVE_P256_BACKEND` so a test can assert which backend it is exercising, rather than a stub silently standing in for a verifier.

**leanVM must be built optimised.** Its own cargo aliases are `test --release`; under a debug profile its circuit builder panics on an overflow check during warm-up. The workspace carries `[profile.dev.package.*]` overrides for its crates.

## Costs, measured

leanVM's published figures (M4 Max) and what they imply here:

| | |
|---|---|
| Verification | ~4 ms steady state, after a one-off circuit build that `LeanVmAggregator::new` pays up front |
| Proof size | ~300 KiB, about 4% of the 8 MiB `MAX_RLP_BLOCK_SIZE` |
| Proving | ~1 s at 9-11 GiB peak resident memory, for a large aggregate |

Proving stays off the block-production path for that last reason: `finalize_payload` sets the digest and leaves the proof empty.

## Where the spec was ambiguous, and what we chose

Twenty-two questions had to be answered before this could be written. They are argued in full, with suggested spec text, in [`scripts/hegota-testnet/NOTES-FOR-8288-AUTHOR.md`](../scripts/hegota-testnet/NOTES-FOR-8288-AUTHOR.md). The load-bearing ones:

| Question | Reading adopted | Item |
|---|---|---|
| Block-validity rule 2 reads as one check against `block_deps_hash` | Two checks. The proof verifies, **and** the claims it proves equal `dependencies(block)`. A leanVM aggregate publishes claim lists and does not bind a caller's digest, so without the second step any valid aggregate satisfies any block | 14 |
| `AGGREGATED_VK` is `TBD` | So is the thing it would name: leanVM publishes no digest of its circuit. We bind to the pinned revision and say so | 15 |
| No bound on the proof, which rides in the header | Capped at 1 MiB, against EIP-7934's block limit | 16 |
| `verification_key_hash` names no hash function | BLAKE3-256, matching `block_deps_hash`. For leanSPHINCS the key is already exactly 32 bytes, so the indirection compresses nothing | 17 |
| "Cannot verify" versus "invalid" | Separate errors with separate fork-choice outcomes. A node with no verifier must not tell its consensus client that a chain everyone follows is bad | 19 |
| Wrapper limits | Enforced as published, and pinned by a test — at 16 per wrapper and 16 per transaction, one maximally-loaded transaction fills a wrapper, and no wrapper ever carries more than 16 signatures however they are spread | 20 |
| Wrapper transport | None invented. The EIP specifies no devp2p message | 21 |
| A wrapper may name transactions by hash | Rejected. Rule 1 needs the transaction, and with no wrapper transport there is nothing to resolve a hash against; the EIP defines no resolution or miss behaviour either | 22 |
| `FRAMEDATASIZE`, `frame.gas_limit`, `target == None (0x00…00)`, the frame's receipt, gas refundability, sort order, atomic batches, header field position | See items 1-13 and 23 | 1-13, 23 |

## Where we are stricter than the spec, and why that is a risk

Most of the table above resolves silence in the EIP. Three rules go further: they
**reject something the spec, read literally, permits**. Each is defensible on its own
terms, and each is a consensus split waiting for a second client — a block or
transaction another implementation accepts and ethrex does not is a chain split, not a
policy difference. They are listed here, and argued upstream in the items named, so
that the divergence is visible rather than buried in a validation function.

| Rule | What the spec permits | What we do | Item |
|---|---|---|---|
| A dependency frame may not sit inside an atomic batch, as member **or terminator** | EIP-8288 requires `flags == 0`, which excludes a flagged member but leaves a dep-verify frame a legal *terminator* of an EIP-8141 atomic batch. EIP-8288 never mentions batches | Reject the transaction | 13 |
| `stark_proof` is capped at 1 MiB, checked at header decode | The EIP bounds the proof nowhere. A larger proof that verifies is a valid block by the text | Refuse the header before the proof is ever read | 16 |
| A block declaring no dependencies must carry an **empty** proof | Rule 2 as written asks whether the proof verifies against `block_deps_hash`; a proof over the empty set would be a legal, if pointless, thing to carry | Reject a non-empty proof outright, since nothing would read it and it is unaccounted bytes in a header every node stores and hashes | 25 |

The first two need to land in the EIP text — as a mode rule for batches and an explicit
length bound for the proof — or a second implementation will not have them. The third
falls out of item 25's question about what the empty dependency set means, which the EIP
does not currently answer at all.

Two further restrictions are **local policy, not consensus**, and are safe for that
reason: a build with no backend refuses to admit dependency-bearing transactions to its
mempool (it could not prove them), and leanSTARK (`0x11`) dependencies are refused
admission because no backend supports the scheme. Neither affects whether a block
already produced is valid.

- `crates/blockchain/eip8288.rs` — rule 2's arms: the empty set, the fork gate, and a dependency with no backend.
- `crates/blockchain/fork_choice.rs` — that "invalid" and "cannot verify" reach the consensus client as different answers (item 19).
- `crates/common/dep-aggregation/src/tests.rs` — the seam, fail-closed behaviour, the proof bound.
- `crates/common/dep-aggregation/src/wrapper_tests.rs` — the wrapper object and its limits.
- `crates/common/dep-aggregation/src/leanvm.rs` — the real aggregate round trip, `#[ignore]`d by default for its memory cost. Run with `cargo test -p ethrex-dep-aggregation --features leanvm -- --ignored`.
