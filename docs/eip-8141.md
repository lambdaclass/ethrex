Implementation notes for EIP-8141 in ethrex. Covers the architecture, where the spec required interpretation, and known limitations.

## Overview

Frame transactions (type `0x06`) replace the ECDSA signature of traditional transactions with a sequence of **frames** — independent execution steps that collectively authenticate and pay for the transaction. Authentication happens on-chain via the `APPROVE` opcode rather than off-chain via secp256k1.

This enables:

- **Abstract authentication**: Any on-chain verification scheme (WebAuthn/P256, multisig, social recovery) can authorize transactions.
- **Separated sender and payer**: One account proves identity, a different account pays for gas.
- **Batched execution**: Multiple operations in a single atomic transaction.

## Transaction Format

### Wire encoding

```
0x06 || rlp([chain_id, nonce_keys, nonce_seq, sender, frames,
             fees, blob_versioned_hashes])

frames = [[mode, flags, target, limits, value, data], ...]
limits = [execution, state]
fees = [max_fee, max_priority_fee_per_gas]
```

`max_fee` is the total, in wei, the sender will pay for all of the transaction's execution, state
and blob gas; see [Fee budget](#fee-budget).

`nonce_keys` and `nonce_seq` are EIP-8250's replacement for EIP-8141's single `nonce`; see
[EIP-8250](./eip-8250.md).

Each frame is RLP-encoded as a six-element tuple:

- `mode` — `DEFAULT` (0), `VERIFY` (1), `SENDER` (2), `ASSERT` (3, EIP-7906) or `PROOF` (4).
- `flags` — bits 0-1 the approval scope, bit 2 the atomic batch flag (both for non-proof frames),
  bit 3 `PROOF_COMMIT_FLAG` and bit 4 `PROOF_READ_FLAG` (proof frames only). A flag under the wrong
  mode, or any of bits 5-7, makes the transaction invalid.
- `target` — the address the frame calls, or empty for `tx.sender`.
- `limits` — the frame's execution-gas and EIP-8037 state-gas budgets, held in `gas_limit` and
  `state_gas_limit`.
- `value` — wei transferred from `sender`; must be zero unless the frame is SENDER.
- `data` — calldata for the frame's top-level call.

**Source**: `crates/common/types/transaction.rs` — `FrameTransaction`, `Frame`, their
`RLPEncode`/`RLPDecode` implementations (the golden RLP and signature-hash vectors were derived
outside the crate, from the EIP's pseudocode).

### Proof frames

A frame with `mode = 4` asserts a **claim** `(verifier, key, msg)`: the verifier, the frame's
resolved target, attests that `key` authorizes `msg`. Its data holds the claim and the proof:

```
data = key (32 bytes) || msg (32 bytes) || proof
```

A zero `msg` stands for the canonical signature hash. Static rules: proof frames are the first
frames of the transaction, `limits.state` and `value` are zero, the data holds at least the 64-byte
claim, `key` is not zero, and `PROOF_COMMIT_FLAG` requires an explicit `msg`.

A proof frame calls its verifier in the **pure context** with calldata `key || msg || proof`, the
signature hash in place of a zero `msg`. The claim holds if and only if the call succeeds. If it
does not, the transaction is invalid. The frame is charged its whole `limits.execution` and yields
a receipt like any other frame (success, that limit, no state gas, no logs).

- **Pure context** (`VM::proof_frame_claim_holds`, `VM::pure_opcode_table`): a static call from
  `ENTRY_POINT` with the frame's own EIP-2929 access sets, which hold only the precompiles, so a
  precompile verifier is warm, a contract verifier is cold, and nothing the frame touches is warm
  for later frames. Every instruction that reads the call's context, other accounts, the chain, the
  block, the transaction or storage halts, as do `CALL`, `CALLCODE`, `DELEGATECALL` and a
  `STATICCALL` to anything but a precompile. A verifier without code, or whose code is an EIP-7702
  delegation indicator, fails.
- **Verifier precompiles** (`precompiles.rs`), active from Hegota. Each takes
  `key || msg || proof`, returns the word 1 when the claim holds, and consumes all the gas it was
  given when it does not. The EIP has yet to assign their addresses; this branch uses the next
  three of the contiguous range.

| Verifier | Address | `key` | `proof` | Gas |
|----------|---------|-------|---------|-----|
| `SECP256K1_VERIFIER` | `0x12` | signer address, left-padded | `v \|\| r \|\| s` (65 bytes), `v` the bare recovery id, low `s` | 3000 |
| `P256_VERIFIER` | `0x13` | `keccak256(qx \|\| qy)[12:]`, left-padded | `r \|\| s \|\| qx \|\| qy` (128 bytes), low `s` | 6900 |
| `LEANSPHINCS_VERIFIER` | `0x14` | the public key, `PK.seed \|\| PK.root` | the signature (7740 bytes) | 13200 |

The leanSPHINCS verifier is linked only into native builds (the `leansphincs` feature of
`ethrex-levm`, enabled by `ethrex-blockchain`). A build without it, such as a zkVM guest, fails
every call to that precompile.

### Key differences from standard transactions

| Field | Standard TX | Frame TX |
|-------|-------------|----------|
| Authentication | ECDSA signature (v, r, s) | Proof frames + on-chain APPROVE opcode |
| Sender | Recovered from signature | Explicit `sender` field |
| Value | Transfer amount | Per-frame `value` (only SENDER frames may be non-zero) |
| Data | Single calldata blob | Per-frame data arrays |
| Gas limit | Single value | Intrinsic + per-frame cost + calldata cost + Σ(frame.gas_limit), proof frames included |
| Nonce consumption | Before execution | During APPROVE payment (scope 0x1 or 0x3): the account nonce for the empty key set, `NONCE_MANAGER` slots for keyed sets (EIP-8250) |
| Balance deduction | Before execution | During APPROVE payment (scope 0x1 or 0x3) |

### Signature hash (sig_hash)

The sig_hash is the canonical digest a proof with a zero `msg` is made over. It commits to the
entire transaction — including all frame data and flags — with one exception: the proof of every
proof frame is elided, because a proof over `compute_sig_hash` cannot commit to its own bytes.

```
sig_hash = keccak256(0x06 || rlp([chain_id, nonce_keys, nonce_seq, sender, elided_frames, ...]))
```

Where `elided_frames` is the frame list with the `data` of each proof frame replaced by the list
`[claim, len(proof)]`, the length as an unsigned integer, extended with `keccak256(proof)` when the
frame sets `PROOF_COMMIT_FLAG`. Committing to the length fixes what the payer is charged for the
proof, so the intrinsic cost prices those bytes as if all non-zero. The data of every other frame
(including VERIFY frames and expiry deadlines) is committed verbatim.

**Source**: `FrameTransaction::compute_sig_hash()` in `transaction.rs`.

## Frame Modes

### DEFAULT (mode = 0)

Regular execution. The caller (msg.sender) is `ENTRY_POINT` (`0x00..00aa`). Not static. Used for operations that don't need sender authority — deploying contracts via CREATE2, calling permissionless functions.

### VERIFY (mode = 1)

Validation execution. The caller is `ENTRY_POINT`. Executed in **static mode** — no state modifications allowed except via APPROVE. A VERIFY frame that **reverts** invalidates the entire transaction (whether or not it is part of an atomic batch). A VERIFY frame that **succeeds without calling APPROVE is valid** — the expiry verifier frame is exactly this case. APPROVE is how a VERIFY frame grants sender and/or payer approval, but it is not a requirement for the frame itself to be considered valid.

### SENDER (mode = 2)

Authorized execution. The caller is `tx.sender` — the contract sees the call as coming from the account itself. Not static. May carry a non-zero `value`. Requires that sender has already been approved (APPROVE with scope `APPROVE_EXECUTION` (0x2) or `APPROVE_EXECUTION_AND_PAYMENT` (0x3) called in a prior frame). Used for the actual operations: token transfers, contract calls, etc.

### ASSERT (mode = 3, EIP-7906)

Assertion execution. The caller is `ENTRY_POINT` and the frame is static, with no APPROVE exception. ASSERT frames form a trailing suffix of the frame list, are the only place `TXTRACE` and `EVENTDATACOPY` work, and a failing one reverts the execution body without invalidating the transaction. See [EIP-7906](./eip-7906.md).

**Source**: `vm.rs` frame loop for caller/static assignment and VERIFY enforcement.

## New Opcodes

The implementation adds six opcodes: APPROVE (0xAA), TXPARAM (0xB0),
FRAMEDATALOAD (0xB1), FRAMEDATACOPY (0xB2), FRAMEPARAM (0xB3), and PROOFPARAM
(0xB4). Outside a frame transaction, all six halt exceptionally (the
`frame_tx_context` is `None`), and so they do inside a proof frame's verifier.

**Source for opcode bytes**: `crates/vm/levm/src/opcodes.rs`.

### APPROVE (0xAA)

**Stack**: `[offset, length, scope]` (offset on top)

Exits the current frame's execution context successfully (like RETURN) and
updates transaction-scoped approval state based on the `scope` operand. `scope`
is a bitmask:

| Scope | Name | Effect |
|-------|------|--------|
| 0x0 | `APPROVE_NONE` | No approval allowed — APPROVE with this scope is rejected. When a frame's flags restrict the allowed scope to 0 (`APPROVE_SCOPE_NONE`), the frame may not approve anything; default code reverts/halts. |
| 0x1 | `APPROVE_PAYMENT` | Reverts the frame if `sender_approved == false` (payment cannot precede the sender's execution approval). Otherwise consumes the transaction's nonce set (EIP-8250), deducts the tx cost from the executing contract's balance, and records it as `payer`. |
| 0x2 | `APPROVE_EXECUTION` | Sets `sender_approved = true`. Requires `resolved_target == tx.sender`. |
| 0x3 | `APPROVE_EXECUTION_AND_PAYMENT` | Both payment and execution approval in one atomic step. Requires `resolved_target == tx.sender`. |

The deducted payment cost is the transaction's `max_cost`, the worst-case
base-fee charge plus the largest tip the `max_fee` budget allows (see
[Fee budget](#fee-budget)); whatever settlement does not burn or pay to the
coinbase is refunded to the payer at end-of-tx.
`APPROVE_SCOPE_MASK` is an alias for `0x3`.

The data at `memory[offset..offset+length]` becomes the frame's output (like
RETURN).

**Gas cost**: Memory expansion only (same as RETURN — no base opcode cost).

**Invariants enforced**:
- `scope` must be a non-zero value `≤ 3` and a subset of the frame's
  `flags`-derived allowed scope (bits 0-1). A zero or `> 3` scope, or a scope
  not permitted by the flags, is an exceptional halt.
- Cannot re-approve a scope already set (double payment via existing `payer`, or
  double execution via existing `sender_approved` → exceptional halt).
- Scopes 0x2 and 0x3 require `resolved_target == tx.sender` (a mismatch reverts
  the frame).
- The executing contract (call frame's `to` address) must equal the frame's
  resolved target.
- Payment scopes (0x1, 0x3) revert the frame if the payer balance underflows.
- `APPROVE_PAYMENT` (0x1) reverts the frame if `sender_approved == false` — payment
  approval must not precede the sender's execution approval. (`APPROVE_EXECUTION_AND_PAYMENT`
  (0x3) is exempt: it sets `sender_approved` in the same atomic step.)

**Source**: `crates/vm/levm/src/opcode_handlers/frame_tx.rs` (`OpApproveHandler`,
`apply_approve`).

### TXPARAM (0xB0)

**Stack input**: `[param_id]`
**Stack output**: `[value]`
**Gas cost**: 2

Pops a single `param_id` and pushes a 32-byte word for the requested
transaction-scoped parameter:

| param_id | Returns |
|----------|---------|
| 0x00 | `0x06` (transaction type) |
| 0x01 | `nonce_seq` (EIP-8250) |
| 0x02 | sender (right-aligned in 32 bytes) |
| 0x03 | max_priority_fee_per_gas |
| 0x04 | max_fee (the budget, not the `max_cost` collected from it) |
| 0x07 | len(blob_versioned_hashes) |
| 0x08 | sig_hash |
| 0x09 | len(frames) |
| 0x0A | currently executing frame index |
| 0x0B | number of proof frames, which are the first frames |
| 0x0C | state gas left in the executing frame's pool |
| 0x0D | the sender's account nonce before any frame ran (EIP-8250) |
| 0x0E | len(nonce_keys) (EIP-8250) |
| 0x0F | keccak256 of the length and the keys (EIP-8250) |
| 0x10 | nonce_keys[0], or 0 for the empty key set (EIP-8250) |

Any other `param_id` is an exceptional halt.

**Source**: `frame_tx.rs` (`OpTxParamHandler`, `load_tx_param`).

### FRAMEDATALOAD (0xB1)

**Stack input**: `[offset, frameIndex]` (offset on top)
**Stack output**: `[word]`
**Gas cost**: 3 (matches CALLDATALOAD)

Loads one 32-byte word from `frames[frameIndex].data` starting at byte `offset`,
zero-padding past the end (CALLDATALOAD semantics). An out-of-bounds
`frameIndex` is an exceptional halt. So is the data of a proof frame, unless that
frame sets `PROOF_READ_FLAG` and the executing frame is a VERIFY frame; the data is
read as encoded, so a zero `msg` stays zero and the proof begins at byte 64.

**Source**: `frame_tx.rs` (`OpFrameDataLoadHandler`).

### FRAMEDATACOPY (0xB2)

**Stack input**: `[memOffset, dataOffset, length, frameIndex]` (memOffset on top)
**Gas cost**: 3 + 3 × ceil(length / 32) + memory expansion (CALLDATACOPY model)

Copies `length` bytes from `frames[frameIndex].data` (starting at `dataOffset`)
into memory at `memOffset`, zero-padding past the end. An out-of-bounds
`frameIndex` and an unreadable proof frame (see `FRAMEDATALOAD`) are exceptional
halts (checked before the zero-length early return).

**Source**: `frame_tx.rs` (`OpFrameDataCopyHandler`).

### FRAMEPARAM (0xB3)

**Stack input**: `[param, frameIndex]` (frameIndex on top)
**Stack output**: `[value]`
**Gas cost**: 2

Returns a 32-byte word for the requested frame-scoped parameter of
`frames[frameIndex]`:

| param | Returns |
|-------|---------|
| 0x00 | resolved target (frame.target, or tx.sender if null) |
| 0x01 | gas_limit |
| 0x02 | mode |
| 0x03 | flags |
| 0x04 | len(data) |
| 0x05 | status (0 = failure, 1 = success, 2 = skipped) — exceptional halt for the current or a future frame |
| 0x06 | allowed_scope (`flags & 0x03`) |
| 0x07 | atomic_batch flag (`(flags >> 2) & 1`, returns 0 or 1) |
| 0x08 | value |

Any other `param`, or an out-of-bounds `frameIndex`, is an exceptional halt.

**Source**: `frame_tx.rs` (`OpFrameParamHandler`).

### PROOFPARAM (0xB4)

**Stack input**: `[param, frameIndex]` (frameIndex on top)
**Stack output**: `[value]`
**Gas cost**: 2

Returns part of the claim of the proof frame `frames[frameIndex]`:

| `param` | Value |
|---------|-------|
| 0x00 | `key` |
| 0x01 | the verifier, the frame's resolved target |
| 0x02 | `msg` as encoded, zero for the canonical signature hash |

Any other `param`, an out-of-bounds `frameIndex`, and a frame that is not a proof frame are
exceptional halts. A transaction is valid only if every claim holds, so code that reads a claim can
treat it as verified; it still has to check the verifier, since a claim is only as sound as that.

**Source**: `frame_tx.rs` (`OpProofParamHandler`).

## Gas Accounting

### Total gas limit

`FrameTransaction::standard_gas_limit()` computes:

```
mandatory_gas =
      FRAME_TX_INTRINSIC_COST                       # 12000
    + len(frames) * FRAME_TX_PER_FRAME_COST         # 475 each
    + value_transfer_cost                           # EIP-2780 TX_VALUE_COST per value frame
    + keyed_nonce_access_cost                       # EIP-8250: 12100 per non-zero nonce key

standard_gas_limit = mandatory_gas + data_cost + Σ(frame.gas_limit)
```

The data cost charges 4 gas per zero byte and 16 per non-zero byte (EIP-7623) over each frame's
`data` and EIP-8250's `rlp(nonce_keys) || rlp(nonce_seq)`. The proof of a proof frame is charged 16
gas per byte whatever its value, since the signature hash commits only to its length; the calldata
floor counts it like any other byte. Verification itself is not an intrinsic cost: it is charged
through the proof frame's `limits.execution`, in full.
The rest of the RLP framing and the other scalar fields are not billed. `FRAME_TX_PER_FRAME_COST = 475` covers a fixed CALL context overhead (100)
plus `G_log` (375) for each frame's receipt sub-entry.

The same data is subject to the EIP-7623 calldata floor, raised to 64 gas per byte by EIP-7976
(frame transactions exist only from Hegota, which is after Amsterdam, so the raised floor always
applies). The mandatory costs are always charged in full and so appear on both sides of the
comparison:

```
calldata_floor_gas = mandatory_gas + TOTAL_COST_FLOOR_PER_TOKEN * calldata_tokens
max_gas            = max(standard_gas_limit, calldata_floor_gas)
```

`FrameTransaction::max_gas()` returns it: the gas reserved from the block pool before execution
and the quantity the fee budget must cover at the base fee. A transaction whose data floor exceeds what it declared for
execution reserves the floor; it is **not** rejected.

At the end of the transaction the EIP-3529 storage refund is applied *before* the floor:

```
gas_used_before_refund = standard_gas_limit - tx_unused_gas
applied_refund         = min(refund_counter, gas_used_before_refund / 5)
gas_used               = max(gas_used_before_refund - applied_refund, calldata_floor_gas)
```

**Source**: `FrameTransaction::standard_gas_limit()`, `calldata_floor_total()` and `max_gas()` in
`transaction.rs`; the finalization in `execute_frame_tx`
(`vm.rs`).

### Fee budget

`max_fee` is one budget for the execution, state and blob gas together. With `base_fee_per_gas`
and `blob_base_fee` the including block's base fees and `blob_gas = 131072 ×
len(blob_versioned_hashes)`:

```
required_max_fee = max_gas × base_fee_per_gas + blob_gas × blob_base_fee
max_priority_fee = min(max_priority_fee_per_gas × max_gas, max_fee − required_max_fee)
max_cost         = required_max_fee + max_priority_fee
```

The transaction is invalid if `max_fee < required_max_fee`, checked before any frame executes and
reported as `INSUFFICIENT_MAX_FEE_PER_GAS`. There is no separate fee cap per gas or per blob gas,
and no rule relating `max_priority_fee_per_gas` to `max_fee`. `max_cost <= max_fee` always.

`GASPRICE` returns `base_fee_per_gas + max_priority_fee // max_gas`. It depends only on the
transaction and the block's base fees, so every frame observes the same value. It is a lower
bound on what the payer pays per unit of gas used, blob gas aside, and exact when `max_fee`
covers the whole tip. The receipt's `effectiveGasPrice` reports the same value.

### Fee charged to the payer

When APPROVE grants payment (scope 0x1 or 0x3), the payer is charged the transaction's
`max_cost`. Because the debit happens at APPROVE time, a frame that runs after payment approval
observes the payer's balance reduced by `max_cost` via `BALANCE`/`SELFBALANCE`. The payer must be
able to front it: a lower balance makes the APPROVE frame revert.

At the end of the transaction the escrow is settled over the gas used, both dimensions:

```
base_fee_paid     = gas_used × base_fee_per_gas + blob_gas × blob_base_fee
priority_fee_paid = min(max_priority_fee_per_gas × gas_used, max_cost − base_fee_paid)
payer_refund      = max_cost − base_fee_paid − priority_fee_paid
```

`base_fee_paid` is burned, `priority_fee_paid` goes to the coinbase and `payer_refund` back to the
payer. Since `gas_used <= max_gas`, the refund is never negative and the payer never pays more than
`max_fee`. Intrinsic gas is inside `gas_used` and stays non-refundable.

**Source**: `FrameTransaction::fee_budget` and `FrameFeeBudget::settle` in `transaction.rs`;
`approve_payment` in `frame_tx.rs`; the settlement in `execute_frame_tx` (`vm.rs`).

### During execution

Each frame runs with its own gas_limit. Gas consumed is tracked per-frame. A frame
that reverts via the `REVERT` opcode is charged its actual `gas_used` (standard EVM
semantics); a frame that fails with an exceptional halt (e.g. out-of-gas, invalid
opcode) is charged its full gas_limit. Frames skipped by a failed atomic batch are
not executed and their gas is refunded. Unrolling a batch does not re-price it: the
frames that ran before the failure keep their status and their gas, and only their
logs are dropped, along with the state changes the unroll discards.

The intrinsic gas (everything in `standard_gas_limit` other than `Σ(frame.gas_limit)`)
is always consumed — it is not part of any frame's gas budget and is
non-refundable.

### Refund

EIP-3529 storage refunds accumulate into a single transaction-scoped counter across frames rather
than settling per frame. A reverted frame's contribution — and that of every frame unrolled by a
failed atomic batch — is dropped along with its state changes, because the counter lives in the
substate that those paths revert. The counter is applied once at the end of the transaction, capped
at a fifth of the gas used before refunds:

```
applied_refund    = min(refund_counter, gas_used_before_refund / 5)
```

It lowers the `gas_used` the escrow is settled over (see
[Fee charged to the payer](#fee-charged-to-the-payer)), and so what the payer pays.

**Source**: `vm.rs` post-execution settlement block.

## Execution Flow

### 1. Validation

- Frame count: 1 ≤ len(frames) ≤ `FRAME_TX_MAX_FRAMES` (64)
- Static constraints: reserved modes/flags, per-frame value rule, proof frame
  shape and position, expiry-verifier frame shape
- Nonce: the account nonce, or every selected key, must be at `nonce_seq`; a keyed set at `2**64 - 1` needs unused keys instead, and the empty set cannot use that sequence (EIP-8250)
- Fees: `max_fee` covers `required_max_fee` at the block's base fees (see [Fee budget](#fee-budget))
- Proof frames lead the frame list, so every claim is verified before any other frame executes

Notable omission vs standard transactions: **no balance check, no EOA check, no nonce increment**. These are handled by APPROVE during execution instead of during validation.

### 2. Context initialization

Creates `FrameTxContext` with:
- `sender_approved: false`, `payer_address: None`
- Computes `sig_hash` (each proof replaced by its length, and its digest if committed; all other frame data committed)
- Fixes the fee budget (`max_cost` and the `GASPRICE` value) at the block's base fees
- Calculates intrinsic gas, starts `total_gas_used` at intrinsic cost

### 3. Frame loop

For each frame in order:

1. **Set context**: Update `current_frame_index`, reset `approve_called_in_current_frame`.
2. **Resolve target**: `frame.target.unwrap_or(tx.sender)`.
3. **Set caller and static mode** per frame mode (see [Frame Modes](#frame-modes)).
4. **Create CallFrame**: Fresh stack, memory, and the frame's gas_limit.
5. **Push substate backup**: State isolation per frame (and a batch-level backup at atomic-batch entry).
6. **Execute**: `run_execution()`, or run the built-in default code when the resolved target has no code.
7. **Handle result**:
   - Success → commit substate, collect logs
   - Failure → revert substate, roll the journaled context back to the frame's entry (see below), charge full gas_limit; if inside an atomic batch, unroll the batch (roll back to its entry snapshot and mark remaining batch frames SKIPPED with status 0x2)
8. **Store result**: `(status, gas_used, logs)` in `frame_results`.
9. **VERIFY enforcement**: A reverted VERIFY frame sets `tx_invalid = true` and breaks. A VERIFY frame that succeeds without APPROVE is valid.
10. **Clear transient storage** between frames.

**Journaled context.** Three things EIP-8141 journals with state live in `FrameTxContext`, outside
the substate and the cache: the approval context (`sender_approved`, `payer`), the state-gas
ownership records (`outstanding_charge_owners`), and the refills that lowered an earlier frame's
receipt `gas_used.state`. Every change to them is appended to `FrameTxContext::journal`. A nested
call records the journal's length when it starts, and so do a frame and an atomic batch; when one
of them fails, `VM::rollback_frame_context` undoes the changes made since, newest first. A call
that reverts above an `APPROVE` therefore takes the approval with it even when the frame
succeeds, as the nonce increment and the `max_cost` collection the approval made to state are
reverted with the call.

### 4. Post-execution

- Check `payer_address.is_some()` (otherwise TX invalid)
- Settle the escrow: burn the base fee, pay the coinbase the capped priority fee, refund the payer the rest
- Pay coinbase (`priority_fee_paid`)
- Derive top-level `succeeded` from all frame statuses (true iff every frame status is `0x1`; see §9)
- Build `ExecutionReport` with frame_results and payer_address

### 5. Invalid transactions

If any of these fail, the transaction is rejected entirely (no state changes):
- A VERIFY frame reverts (batched or not)
- No payer set after all frames execute
- A SENDER frame executes before sender approval

Invalid frame transactions that reach the payload builder are **removed from the mempool** since their failure is deterministic.

## Receipt Format

Frame receipts use distinct encodings for consensus and for internal storage.

**Consensus payload** (receipts-trie root, and served over eth/68) —
`encode_inner_with_bloom`:

```
0x06 || rlp([cumulative_gas_used, payer, [frame_receipt, ...]])
frame_receipt = [status, gas_used, logs]
```

There is no top-level `succeeded`, no bloom, and no aggregated `logs`. On decode,
`succeeded` is **derived**: true iff every frame's status is `0x1` (success).
`status` codes: `0x0` failure, `0x1` success, `0x2` skipped (frame skipped by a
failed atomic batch). `gas_used` is the frame's gas, not accounting for refunds.
The `payer` is the address recorded by APPROVE payment (zero address ⇒ `None`).

**eth/69 and later** serve receipts through the `RLPEncode for Receipt` impl
(`encode_inner`), not `encode_inner_with_bloom`. This carries the same fields but
puts the type as the first element *inside* the RLP list rather than as a raw
EIP-2718 prefix byte: `rlp([0x06, cumulative_gas_used, payer, [frame_receipt, ...]])`,
consistent with how eth/69 encodes every typed receipt. That is exactly the form
EIP-8141 §Networking specifies for the `Receipts` message of the protocol version
carrying the fork; Hegota rides eth/70 and eth/71, both of which serve
`Receipts70` through this impl. `receipts70_frame_receipt_matches_the_eip8141_wire_form`
pins the bytes.

The two wire layouts are therefore NOT byte-identical for frame receipts; only
eth/68 matches the receipts-trie bytes. That difference is unreachable in
practice, since eth/68 predates Hegota and so predates any block that can contain
a frame transaction, but an eth/68 peer requesting a Hegota block's receipts would
receive the prefix form.

**Internal storage encoding** — `encode_storage` — additionally persists the
top-level `succeeded` flag and the aggregated `logs`, which the consensus layout
omits but which `eth_getLogs` / `eth_getTransactionReceipt` need:

```
0x06 || rlp([succeeded, cumulative_gas_used, logs, payer, [frame_receipt, ...]])
```

**RPC response** (`eth_getTransactionReceipt`) includes `payer` and
`frameReceipts` as additional JSON fields when the transaction is type 0x06.
The JSON follows the frame transaction definitions proposed in
[execution-apis#907](https://github.com/ethereum/execution-apis/pull/907):

- Each frame receipt carries `status`, `executionGasUsed`, `stateGasUsed`, `gasUsed`
  (their sum) and `logs`, as full log objects whose `logIndex` continues the
  block-wide sequence across frames.
- A blob-carrying frame transaction's receipt also carries `blobGasUsed` and
  `blobGasPrice`.
- In the transaction object, each frame is `{mode, flags, target, executionGas,
  stateGas, value, data}`, and the sender is `from`.

**Source**: `crates/common/types/receipt.rs` (`FrameReceipt`,
`encode_inner_with_bloom`, `encode_storage`, `encode_inner`),
`crates/networking/rpc/types/receipt.rs`.

## Contract Deployment

The fork installs nothing. The contracts frame transactions rely on are ordinary contracts, each
created by a keyless deployment transaction that its EIP publishes. Nobody holds the key of the
sender, so that transaction is the only one able to create code at its address, and the address
alone identifies the canonical code:

| Contract | Address | Runtime code |
|---|---|---|
| EIP-8141 expiry verifier | `0x81413f0cF12e9b6a49B1D0439E081c577D57FfFf` | 26 bytes |
| [EIP-8250](./eip-8250.md) `NONCE_MANAGER` | `0x8250968C12e01A19d6F667b9B2F3b3A4d0e51cB7` | 5 bytes |
| [EIP-8272](./eip-8272.md) `RECENT_ROOT_ADDRESS` | `0x8272D9679689Ea2f307140CdF9002D27dC00Ffff` | 320 bytes |

A chain gets them by including the deployment transactions before the fork or by allocating the
accounts in genesis with nonce 1 and the runtime code, as `fixtures/genesis/l1-hegota.json` does.
EIP-8250 requires `NONCE_MANAGER` to be in state when the fork activates. The other two may arrive
later: until the expiry verifier or the recent root contract is deployed, a frame targeting it runs
the protocol default code, which reverts in a `VERIFY` frame with flags 0, so the transaction is
invalid.

Because activation changes no state, the fork block is executed like any other block: nothing at
the boundary reaches the block access list, and the parallel block-access-list path applies.

**Source**: `frame_tx_expiry_verifier`, `frame_tx_nonce_manager` and `frame_tx_recent_root` in
`crates/common/types/transaction.rs`; the runtime code in `crates/vm/system_contracts.rs`.
`test/tests/levm/frame_contract_deployment_tests.rs` executes each published deployment
transaction and checks its hash, its sender, the address it creates and the code it leaves.

## Mempool Handling

Frame transactions receive special treatment in mempool validation (`blockchain.rs`):

1. **Balance check skipped**: The payer is unknown until execution (it's determined by which address calls APPROVE with a payment scope). We can't verify balance at mempool time.
2. **EOA check skipped**: For the same reason — a non-existent sender is valid if a payer will fund the execution. Nonce sanity is still applied to such senders against their implied nonce of 0 (see point 7), rather than skipped.
3. **Static validation and stateless claims up front**: `validate_static_constraints` runs at admission, and the claims of the proof frames a precompile verifies are checked before any state is read (`validate_precompile_claims`). Those claims depend on no state, so this is the only time they are verified: the prefix simulation and the revalidation after each block skip them. A claim a contract verifies runs in the prefix simulation.
4. **`MAX_VERIFY_GAS` proof cap**: the proof frames count toward the budget through their execution limits (spec rule #6, `MAX_VERIFY_GAS = 100_000`), checked before any proof is verified; a tx whose proof frames alone exceed the budget is rejected. This is a sound subset of the full validation-prefix budget check (see Known Limitations).
5. **Hegota fork gating**: frame txs are rejected before the Hegota fork activates.
6. **Expiry drop**: a frame tx whose expiry-verifier deadline has passed is dropped.
7. **Blob-carrying frame txs need their sidecar**: a frame tx carrying `blob_versioned_hashes` is admitted only together with its blobs bundle, validated exactly as an EIP-4844 tx's (see [Blob-carrying frame transactions](#blob-carrying-frame-transactions)); the bundle-less entry point rejects it with `BlobTxNoBlobsBundle`.
8. **Standard checks still apply**: Nonce ordering for account-nonce transactions (including for not-yet-existent senders, whose implied nonce is 0; keyed EIP-8250 transactions are checked against `NONCE_MANAGER` by the simulation instead), fee validation, gas limit vs block limit, intrinsic gas coverage, chain ID.

### Structural rules beyond the prefix

Two structural rules constrain frames the recognized prefix shapes do not cover, both enforced by `validate_prefix_structure`:

- **No VERIFY frame after the prefix** (rule 8). A reverting VERIFY frame invalidates the whole transaction wherever it sits, so one placed after the prefix would tie validity to state that prefix simulation never inspects — the unbounded-invalidation case the public mempool rules exist to prevent.
- **An expiry verifier frame may only be the first frame** (§Expiry Verifier Frame). Expiry frames are transparent to shape matching, so a misplaced one would otherwise pin the transaction to a deadline outside the recognized shape.
- **The prefix's state budget is capped** (rule 6). The `limits.state` values across the validation prefix may sum to at most `MAX_VERIFY_STATE_GAS` (500,000). The cap bounds the state growth the public mempool admits; it does not bound simulation work, which `MAX_VERIFY_GAS` does.
- **An EIP-8272 recent root verifier frame may only lead the transaction**, first or behind an expiry verifier frame, and is skipped by shape matching like the expiry frame. See [EIP-8272](./eip-8272.md#mempool).

### Replacement and eviction

- **Replacement** (§Replacement and Eviction): a frame-tx replacement must raise **both** `max_fee` and `max_priority_fee_per_gas` by at least the node's minimum increment (`DEFAULT_PRICE_BUMP_PERCENT`, 10%, the conventional default; `DEFAULT_BLOB_PRICE_BUMP_PERCENT` for a blob-carrying one, whose `max_fee` pays for its blob gas too). The pool applies this to every transaction type, so frame txs never take a looser "either dimension rises" path: each replacement re-runs the validation-prefix simulation, so one-wei bumps would buy unbounded EVM work.
- **Eviction**: when arrival order picks a frame tx as the victim, the spec order decides which frame tx actually goes — nearest expiry deadline first, then lowest priority fee (`Mempool::worst_frame_tx`). Arrival order still decides *whether* a frame tx is sacrificed at all, so frame txs are neither starved by nor privileged over the rest of the pool. The order's first tier — transactions already invalid against the head — is served by post-block revalidation, which has the state view the eviction path lacks.

### P2P propagation

Frame transactions **are** propagated over P2P, but **announce-only**: like
EIP-4844 blob txs, they are advertised by hash via `NewPooledTransactionHashes`
(never full-body broadcast in a `Transactions` message), and the full body is
served on request through `GetPooledTransactions` →
`PooledTransactions` as `P2PTransaction::FrameTransaction`, or as
`P2PTransaction::FrameTransactionWithBlobs` when it carries blobs (see below).

**Source**: `crates/networking/p2p/tx_broadcaster.rs`,
`crates/networking/p2p/rlpx/eth/transactions.rs`.

### Blob-carrying frame transactions

A frame tx with `blob_versioned_hashes` follows EIP-4844 from submission to inclusion
(§Blob handling, §Networking):

- **Network wrapper**: `eth_sendRawTransaction` and `PooledTransactions` carry it as
  `0x06 || rlp([tx_payload_body, wrapper_version, blobs, commitments, cell_proofs])`
  (`WrappedFrameTransaction`). A type-0x06 payload whose first item is a list is the
  wrapper; otherwise it is the plain transaction. The tx hash covers the plain payload,
  and `BlockBodies` carry the plain payload.
- **Admission**: the sidecar is validated as an EIP-4844 tx's — commitments match the
  versioned hashes, KZG proofs verify, at most `MAX_BLOB_COUNT` (6) blobs (EIP-7594),
  cell-proof sidecar (version 1) from Osaka — and the transaction gets the blob pool's
  wire-size cap and replacement rules. The pool indexes the sidecar by versioned hash,
  so `engine_getBlobsV2` and `engine_getBlobsV3` serve its blobs.
- **Building**: `apply_transaction` routes it through `apply_blob_transaction`, so its
  blobs count toward `blob_gas_used` and the block's blob cap and its sidecar joins the
  payload's blobs bundle, the same accounting `verify_blob_gas_usage` applies on import.
- **eth/72**: EIP-8070 defines blob elision and `cell_mask` for type-3 txs only. A
  frame tx is announced at its full wrapped size, adds nothing to `cell_mask`, and is
  served with its blobs; the pool rejects a frame sidecar whose blobs are elided.

**Source**: `crates/common/types/transaction.rs` (`WrappedFrameTransaction`),
`crates/blockchain/blockchain.rs` (`add_blob_transaction_to_pool_inner`),
`crates/blockchain/payload.rs` (`apply_transaction`),
`crates/networking/p2p/rlpx/eth/eth72/transactions.rs`.

## LStar: stripped proofs and the aggregate proof

The EIP's Aggregation rationale says that a proof "can move out of the transaction without
changing what was signed or how the transaction executes, as long as its claim is still proved and
its length and any committed digest are retained", and that "a later EIP can let the protocol strip
a proof if `PROOF_READ_FLAG` is clear, the block's aggregate proof covers the claim, and the
frame's limit covers its verifier's cost". This section describes that rule as the node implements
it for leanSPHINCS signatures, from `Fork::LStar` (`lstarTime`). The EIP leaves the rule to that
later EIP, so its encoding and its block are choices of this implementation; they are listed under
[Choices the text leaves open](#choices-the-text-leaves-open).

Nothing changes for a pending transaction. It is signed, submitted, pooled and gossiped with its
signatures inside it, as before LStar. Only the block changes.

### Stripped frames

In a block from LStar, the `data` of a proof frame is either the byte string
`key || msg || proof`, as before, or the RLP list

```
data = [claim, proof_length]
```

where `claim` is the 64 bytes `key || msg` as the frame encodes them (a zero `msg` stays zero) and
`proof_length` is the byte length of the proof that left. This is the frame's elided form in the
signature hash. A frame whose `data` is that list is a **stripped** proof frame.

A proof may be stripped only if all of the following hold:

- the frame's verifier, its resolved target, is `LEANSPHINCS_VERIFIER`, whose claims the aggregate
  proof covers;
- `PROOF_READ_FLAG` is clear: an aggregate does not supply the bytes `VERIFY` code may read;
- `PROOF_COMMIT_FLAG` is clear: the aggregate proves `(key, msg)` claims and does not show that a
  signature hashes to a committed digest;
- `proof_length` is 7740, one leanSPHINCS signature;
- the frame's `limits.execution` covers its verifier's cost (13,200 plus the 100 of a warm
  access), as it had to for the proof to verify inside the transaction.

A stripped frame that breaks one of the first four rules makes the block invalid before it
executes. One that breaks the last makes its transaction invalid when it executes, exactly as the
frame with its proof would have.

A stripped transaction is valid only inside a block from LStar. The pool rejects one, whether it
comes from a peer or from `eth_sendRawTransaction` (`MempoolError::FrameTxStrippedProof`), at every
fork. A block before LStar that has one is invalid, and the payload builder refuses to include one.

**Source**: `FrameTransaction::stripped_proofs`, `strip_proofs`, `validate_stripped_proofs` and the
`EncodedFrame`/`DecodedFrame` encoding in `crates/common/types/transaction.rs`.

### What changes for a transaction, and what does not

| | With the proof stripped |
|---|---|
| Signature hash | The same. `compute_sig_hash` already encodes every proof frame as `[claim, len(proof)]`, which is what a stripped frame carries. |
| Gas | The same. The payer's charge is a function of what the signature hash covers: the proof is priced by its length (`elided_proof_len`), and the frame is charged its whole `limits.execution`. A leanSPHINCS-authorized transfer pays 513,009 gas in a Hegota block and in an LStar block, stripped or not. |
| `PROOFPARAM`, `TXPARAM(0x0B)` | The same: the claim and the count of proof frames. |
| `FRAMEPARAM(0x04)` | The same: `64 + proof_length`, the length the data had with the proof. |
| Receipt, block access list | The same. The frame yields the same receipt, and its verifier is recorded as touched as when it is called, so a block's access list does not depend on which of its proofs were stripped. |
| Verification | The verifier is not called (`VM::proof_frame_claim_holds`). The claim holds because the block's aggregate proof covers it, which is checked before the block executes. |
| Encoding | 7,739 bytes shorter for each stripped signature. |
| Transaction hash | **Different.** The hash covers the encoding, and the encoding no longer holds the proof. |

The transaction hash is the one rule the Aggregation rationale does not address: it names the
signature hash and the charge as unchanged, and the transaction hash covers the proof. The node
keeps the rule it has for every transaction, that a transaction's hash is the hash of the encoding
the block carries. A stripped transaction therefore has another hash in the block than it had in
the pool, and receipts, `eth_getTransactionByHash` and the transaction index know it by the hash in
the block. Nothing maps the pool hash to it: a sender who wants to follow its transaction computes
the stripped hash, or looks for its sender and nonce. In JSON a stripped frame shows its claim as
`data` and adds `proofLength`.

### The block

- **Body.** `aggregate_proof`, a byte string, is the last item of the block body
  (`BlockBody::aggregate_proof`), after the withdrawals. It is present from LStar, empty when the
  block has no stripped frame, and absent before. No root of the body covers it.
- **Header.** `aggregate_proof_hash = keccak256(aggregate_proof)` follows `burned_fees`
  (EIP-8079), the other field LStar adds, so the trailing optional fields still decode by
  position. It is required from LStar and forbidden before
  (`validate_prague_header_fields`).
- **Genesis.** A chain that starts in LStar has neither in its genesis block, which has no
  `burned_fees` either. Its first block is the first one with them.
- **Size.** The proof has at most `MAX_AGGREGATE_PROOF_BYTES` (1,048,576) bytes, the bound
  EIP-8288 gives its dependency proof. It is left out of EIP-7934's block size check and of the
  `size` an RPC block reports (`Block::length_without_aggregate_proof`).
- **Engine API.** The payload carries `aggregateProof` (hex bytes) in `engine_getPayloadV6` and
  `engine_newPayloadV5`, the versions a Hegota block uses, and in the payload bodies. The header's
  commitment is not a payload field: the receiver derives it, and the block hash covers it. The
  field is required from LStar (`0x` for the empty proof) and must be absent before; either
  mismatch makes the payload `INVALID`.

### Validity

`validate_aggregate_proof` (`crates/blockchain/aggregate_proof.rs`) runs before the block
executes, on every import path (`add_block`, the pipeline, and so `engine_newPayload` and sync).
From LStar:

1. the block carries an aggregate proof of at most `MAX_AGGREGATE_PROOF_BYTES` bytes;
2. the header's `aggregate_proof_hash` is the hash of the proof;
3. every stripped proof frame is one the protocol may strip;
4. the proof is empty when the block has no stripped frame, and otherwise
   `leansphincs_aggregate_verify(claims, proof)` holds, where the claims are the `(key, msg)` of
   the block's stripped frames, a zero `msg` replaced by the transaction's signature hash. The
   verifier sorts and deduplicates the claims and accepts the proof for exactly that set: a claim
   fewer, a claim more or another claim fails.

Before LStar a block with an aggregate proof, or with a stripped frame, is invalid.

A block may mix stripped and unstripped proof frames. An unstripped one is verified by its frame,
as before, and takes no part in the aggregate proof: a block whose transactions all keep their
proofs is a valid LStar block with an empty proof. The proof system is leanVM's recursive
aggregation (`ethrex_crypto::leansphincs_aggregation`).

### The builder

A payload is built as before, from the pool's transactions with their proofs, each verified by
its frame as the transaction executes. When the payload is handed out,
`PayloadBuildResult::with_aggregate_proof` strips every proof the protocol may strip from the
included transactions (`strip_and_aggregate`), aggregates the stripped signatures, and sets the
block's transactions, `transactions_root`, `aggregate_proof` and `aggregate_proof_hash`.

- **After execution, not before.** Stripping changes what the block carries of a transaction (its
  encoding, its hash, the transactions root, the block's size), and nothing the transaction does.
  The state root, the receipts, the gas used and the block access list are those of the execution
  with the proofs in place, and a node that imports the block reproduces them from the stripped
  transactions.
- **Once per payload.** Proving takes from a tenth of a second to several seconds, so
  `build_payload_loop` does it for the payload it ends with, on a blocking thread, and not for each
  rebuild. Until then the payload is a valid block whose transactions carry their proofs. The
  one-shot `build_payload` and `build_payload_with_transactions` do it before they return.
  `initiate_payload_build` prepares the prover when the build starts.
- **A proof that cannot be made fails the build.**
- **The pool.** The transactions stay in the pool, with their proofs, until the block becomes the
  head. `remove_block_transactions_from_pool` then removes a stripped transaction by its pool hash:
  it finds the sender's pending transaction with the same signature hash
  (`Mempool::remove_frame_transaction_by_sig_hash`).

One aggregate proof is about 200 KB for a handful of signatures, so a block with few of them is
larger with the proof than with the signatures: a block of one leanSPHINCS-authorized transfer is
8,605 bytes in Hegota and 905 bytes plus a 202,232-byte proof in LStar.

### Storage and devp2p

The proof is stored with the block body and travels in `BlockBodies` as the body's last item, so
no message changes. `validate_block_body` checks the proof against the header's commitment, so a
peer that serves a body with another proof, or with the transactions unstripped, fails at
download.

### The stateless guest

A zkVM guest does not link the aggregation verifier, as it does not link the leanSPHINCS verifier.
It rejects a block that has a stripped proof frame or a non-empty aggregate proof
(`reject_unverified_aggregate_proof`), and executes a block whose proof frames keep their proofs
as before. The SSZ `NewPayloadRequest` it starts from has no field for the proof, so
`verify_stateless_block` gives an LStar block the empty proof and the header's commitment to it; a
block that carried another proof then fails the block hash check.

### Choices the text leaves open

1. **The encoding of a stripped frame.** The EIP says the stripped frame "keeps its elided form".
   The node encodes the frame's `data` as that form, the list `[claim, proof_length]`, in place of
   the byte string.
2. **Committed proofs are never stripped.** The EIP lets a committed proof leave "provided that
   whatever replaces it shows that it hashes to the digest". The aggregation proves
   `(public key, message)` claims and cannot show that, and the two-item list has no place for the
   digest.
3. **Only `LEANSPHINCS_VERIFIER` proofs are stripped**, and only at 7,740 bytes. The EIP's rule is
   about any verifier an aggregate can prove; this aggregate proves one scheme.
4. **The transaction hash changes** when a proof is stripped (see above).
5. **The verifier still counts as touched** in the block access list for a stripped frame, though
   it is not called.
6. **The block.** The proof's place in the body, the header field and its position, the Engine API
   field, the 1 MiB bound and the exclusion from EIP-7934 follow EIP-8288's dependency proof where
   it applies; the EIP defines none of them.
7. **Activation.** LStar also activates EIP-8079 in this node; no switch separates the two.

(`validate_aggregate_proof_commitment`), `crates/vm/levm/src/vm.rs`

## Spec Gaps and Design Decisions

The EIP-8141 specification leaves several behaviors underspecified. This section documents how ethrex fills those gaps.

### 1. ORIGIN opcode behavior

**Spec gap**: The spec doesn't define what the `ORIGIN` opcode (0x32) should return during frame execution. In standard transactions, ORIGIN always returns the EOA that signed the transaction.

**ethrex decision**: `env.origin` is set to the frame's **caller** — `ENTRY_POINT (0xaa)` for DEFAULT/VERIFY frames, `tx.sender` for SENDER frames (`vm.rs`).

**Rationale**: Frame transactions don't have a single signing EOA. Setting ORIGIN to the frame's caller is consistent with the frame execution model. Setting it to tx.sender for all frames would leak sender identity to DEFAULT/VERIFY frame targets, which may not be desirable.

**Risk**: Contracts that use `tx.origin == msg.sender` as an EOA check will behave differently in frame transactions. This is unlikely to cause issues in practice since `tx.origin` for authorization is already a known anti-pattern.

### 2. APPROVE gas cost

**Spec gap**: The spec says APPROVE "exits context" but doesn't specify its gas cost.

**ethrex decision**: APPROVE uses the same gas model as RETURN — memory expansion cost only, no base opcode cost (`frame_tx.rs`, `gas_cost::exit_opcode`). The EIP has since fixed this as the instruction's gas, so it is charged before the checks that can refuse the approval: a refused APPROVE reverts its call frame having paid the expansion.

**Rationale**: APPROVE is functionally equivalent to RETURN (copies memory to output, halts execution) with the additional side effect of updating approval state. The approval state update is a transaction-level bookkeeping operation, not an EVM storage operation, so no additional gas is charged.

### 3. Transient storage between frames

**Spec gap**: The spec doesn't state whether transient storage (EIP-1153 TSTORE/TLOAD) persists across frames.

**ethrex decision**: Transient storage is **cleared between frames** (`vm.rs`).

**Rationale**: Frames are independent execution contexts. Allowing transient storage to leak between frames would create an implicit communication channel that could interact with frame ordering in surprising ways. Clearing it is the conservative choice.

### 4. APPROVE output data accessibility

**Spec gap**: APPROVE copies `memory[offset..length]` to output, but the spec doesn't define how subsequent frames can access this data.

**ethrex decision**: The output data is stored in the CallFrame's output buffer during execution, but `frame_results` only records `(status, gas_used, logs)` — the output bytes are **discarded** (`vm.rs`).

**Impact**: `FRAMEPARAM` param 0x05 returns a past frame's status, but there's no way to read a VERIFY frame's output data from a later frame. If a use case requires passing structured data from a VERIFY frame to a SENDER frame, it would need to use events (logs) or a separate storage-based communication pattern.

**Possible future work**: Add output bytes to `frame_results` and expose via a new `FRAMEPARAM` param.

### 5. Frame-entry warmth and the target access charge (resolved)

**Spec rule** (Rationale): "Cold/warm access costs for the frame's target account are charged within the frame's own `gas_limit` through the normal EVM warm/cold accounting, not through the per-frame cost." The Execution section adds that the warm/cold journal is shared across frames.

**ethrex behavior**: entering a frame charges `WARM_ACCESS` (100) or the fork's cold account access (3000 from Amsterdam, EIP-8038) for the resolved target. The charge comes out of the frame's own budget; a frame that cannot afford it forfeits its gas limit without executing. A delegated target's delegate is followed at dispatch, which the EIP places after the balance check, so its access is added to the entry charge only for a frame whose sender can fund `value`: one that cannot reverts having paid the target's access, and never reads the delegate or files it in the block access list. The target is warmed inside the frame's substate backup, so a failed frame leaves nothing warm for later frames — matching the reference implementation, which merges a frame's accessed set into the shared journal only on success.

`tx.sender` and the coinbase are warm from the start of the transaction: `Substate::initialize` seeds them for every transaction type, frame transactions included. (An earlier revision of this document claimed the sender was cold; it was not.)

Two cases do **not** pay:

- A `VERIFY` frame whose resolved target has no code runs the protocol default code instead of an EVM. It builds no gas meter, so it neither pays the entry charge nor warms its target. A `SENDER` or `DEFAULT` frame to a codeless account is not special — it runs an EVM over empty code and pays.
- A frame whose sender cannot fund its `value` never starts, and spends nothing.

Pinned by the `warmth/` fixtures in the spec-test suite.

### 6. Substate gas refunds (SSTORE refunds) within frames

**Spec gap**: The spec defines gas refunds for unused frame gas but doesn't address EVM-level gas refunds (e.g., SSTORE clearing refund from EIP-3529).

**ethrex decision**: The `substate.refunded_gas` accumulates normally within each frame, but the final refund calculation (`vm.rs`) only considers unused frame gas limits — it does **not** add SSTORE refunds on top.

**Impact**: SSTORE clearing refunds that would normally reduce gas_used in standard transactions are effectively lost in frame transactions. Gas accounting is simpler but slightly less favorable to users who clear storage.

### 7. Receipt encoding in receipt trie (resolved)

**Spec gap**: The spec defines a receipt format `[cumulative_gas_used, payer, [frame_receipt, ...]]` but the earlier ethrex implementation did not commit the frame-specific fields into the receipts-trie encoding.

**ethrex decision (current)**: For type 0x06, `encode_inner_with_bloom` now emits the EIP-8141 consensus payload `0x06 || rlp([cumulative_gas_used, payer, [frame_receipt, ...]])` — there is no top-level `succeeded`, no bloom, and no aggregated `logs`; `succeeded` is derived from the frame statuses on decode. eth/68 serves these exact bytes; eth/69 serves the same fields via `encode_inner` (type as the first list element, not a prefix byte), so the two wire layouts are not byte-identical for frame receipts (see [Receipt Format](#receipt-format)). The receipts-trie root commits to the payer and every per-frame receipt. The internal storage encoding (`encode_storage`) keeps `succeeded` and aggregated `logs` for RPC/`eth_getLogs`. See [Receipt Format](#receipt-format).

### 8. ENTRY_POINT address collision

**Spec gap**: The spec defines `ENTRY_POINT = 0x00..00aa` as the caller for DEFAULT and VERIFY frames. It does not reserve this address or prevent deployment at it.

**ethrex decision**: Uses `Address::from_low_u64_be(0xaa)` as-is (`vm.rs`).

**Impact**: If a contract exists at address `0xaa` on the chain, DEFAULT/VERIFY frames would appear to originate from that contract. On the demo chain this is not an issue. On mainnet, this address should be either reserved or protected from deployment.

### 9. Failed frame behavior and top-level `succeeded`

**Spec gap**: The spec says "if frame reverts, discard state changes and continue." Two things are underspecified: (a) whether execution continues to subsequent frames, and (b) what the top-level receipt `status` should be.

**ethrex decision**: A reverted non-VERIFY frame discards its state changes but execution continues to the next frame; the frame is recorded as failed (`0x0`) in `frame_results`. A reverted VERIFY frame instead invalidates the whole transaction (it is authentication, so the tx is excluded). The transaction is still included and gas is paid when a SENDER/DEFAULT frame reverts, matching the standard Ethereum model where `status: 0` means execution reverted.

The top-level `succeeded` is **derived identically on encode and decode**: `true` iff *every* frame's status is `0x1` (success), i.e. `false` if any frame (of any mode) reverted or was skipped (`vm.rs` sets the VM result this way; `receipt.rs` re-derives the same on decode). This unification is mandatory, not a stylistic choice: the consensus `frame_receipt` (`[status, gas_used, logs]`) carries **no frame mode**, so a node decoding receipts from the wire or the receipts trie cannot tell SENDER frames apart from DEFAULT/VERIFY ones. An all-frames rule is therefore the only definition the executing node and a wire/trie-decoding node can compute identically; a SENDER-only rule would make a freshly-executed receipt's `status` disagree with the same receipt decoded from consensus bytes (note: `succeeded` is itself not in the consensus encoding, only the per-frame statuses are, so this only affects the derived JSON-RPC `status`, never the receipts root).

**Rationale**: In standard Ethereum transactions, `status: 0` means execution failed — it does not mean the transaction wasn't included. The same applies to frame transactions. Per-frame receipts in `frame_receipts` provide granular detail for batch operations where some frames may succeed and others fail; the aggregate `succeeded` simply reports whether the whole transaction executed cleanly.

### 10. Double-call protection for APPROVE

**Spec gap**: The spec implicitly assumes APPROVE is called once per approval type, but doesn't explicitly state what happens if a later frame re-approves a scope that is already set.

**ethrex decision**: Re-approving an already-set scope is an exceptional halt — `APPROVE_PAYMENT` (0x1) fails if `payer` is already set, `APPROVE_EXECUTION` (0x2) fails if `sender_approved` is already true, and `APPROVE_EXECUTION_AND_PAYMENT` (0x3) fails if either is already set (`frame_tx.rs`, `apply_approve`).

**Rationale**: Re-approving is likely a bug in the frame transaction construction. Failing loudly prevents subtle issues like a second payer accidentally overriding the first.

### 11. Atomic-batch revert: gas and status of rolled-back frames (resolved)

**Formerly a spec gap**, now settled by the spec:

> Logs emitted by frames that executed before the failure are discarded together with their state changes when the batch is unrolled. Those frame receipts retain their execution status and gas used, with empty logs.

So an unrolled batch is *not* re-priced or re-labelled. A frame that succeeded before the failure keeps status `0x1` and the gas it used; the failing frame keeps whatever the single-frame rule already gave it (actual `gas_used` for a `REVERT`, the full `gas_limit` for an exceptional halt); the remaining members are `0x2` SKIPPED with their gas refunded. Only the logs are dropped, along with the state changes.

This matters beyond the receipts trie: the per-frame gas feeds `total_gas_used` → the block header `gasUsed` and the payer's refund, so charging every batch frame its full `gas_limit` (which ethrex did before this rule landed) over-bills the payer and mislabels frames that ran. Pinned by `atomic_batch_unroll_keeps_frame_status_and_gas_but_drops_logs`.

The earlier revision of this section asked for cross-client confirmation before pinning the choice, since it is consensus-visible. The reference implementation now supplies it: the `tests-frames-devnet@v0.0.0` release carries three fixtures over this shape --
`eip8141_frame_transactions/frame_transactions/atomic_batch_rollback`,
`eip8141_frame_transactions/block_access_lists/bal_atomic_batch_write` and
`eip8141_frame_transactions/block_access_lists/bal_atomic_batch_skipped_frame_absent`
-- and each one fails against the full-`gas_limit` behaviour on the block header `gasUsed`, not on a receipt field. So the header quantity the old note was worried about is exactly what the fixtures measure, and they agree with the rule above.

### 12. Frame `gas_limit` bound is `2**63-1`, not `2**64-1` (intentional stricter validity rule)

**Spec rule**: EIP-8141 static validation allows `frame.gas_limit <= 2**64-1` and cumulative frame gas `<= 2**64-1`.

**ethrex behavior**: `validate_static_constraints` (`transaction.rs`) rejects any `frame.gas_limit > i64::MAX` (`2**63-1`) and any cumulative `> i64::MAX`. This is **stricter than the spec** — a frame tx the spec considers statically valid (a `gas_limit` in `[2**63, 2**64-1]`) is rejected. The cap exists because the EIP-8037 state-gas dimension is tracked as `i64`; keeping the static bound at `i64::MAX` guarantees the downstream gas accounting can never overflow.

**Status — documented divergence, effectively unreachable.** Any `gas_limit >= 2**63` exceeds every real block gas limit by orders of magnitude and is rejected by the gas-limit-vs-block-limit check regardless, so no spec-conformant builder could produce a block that exercises the difference. Kept as a deliberate stricter rule rather than relaxing to `2**64-1` (which would require making the entire gas path `u64`-clean) until there is a concrete need.

### 13. EIP-8037 merge-time repayment of spilled state gas (resolved)

**Spec rule**: when a successful child call frame merges into its parent, the state-gas
reservoir repays any spill still outstanding in the merged frame back into execution gas
(execution-specs#3478). A cross-frame refund can credit the reservoir while the execution
gas that funded the charge stays reduced; the merge is the first point where the claim and
the credit share one meter. A failed child repays nothing. Frame transactions carry no
reservoir, so the rule never applies to them.

**ethrex behavior**: `repay_state_gas_spill` runs at every `CALL`-family and `CREATE`-family
merge from Amsterdam on, moving `min(reservoir, frame spill)` from the reservoir into the
parent frame's `gas_remaining`. Billing-neutral: the user total and the EIP-7778 dimensions
are unchanged, but the execution gas a parent holds after a child returns is.

**Status — resolved.** Both fixture bundles carry the rule: `tests-frames-devnet@v0.3.0`
(built from `devnets/frames/0` rebased onto the current `forks/amsterdam`) and
`tests-glamsterdam-devnet@v8.1.4`, which is where the pins sit.

Pinned by the `test_state_gas_cross_frame_refund` cases in both bundles.

## Known Limitations


### In-memory frame transaction context

The `FrameTxContext` is stored on the VM struct and accessed via `Option<FrameTxContext>`. This means:

- Frame transaction opcodes (APPROVE, TXPARAM, FRAMEDATALOAD, FRAMEDATACOPY, FRAMEPARAM, PROOFPARAM) halt exceptionally when executed outside a frame transaction — they check for `frame_tx_context.is_some()`.
- The context is created fresh for each frame transaction and dropped after execution.
- No frame transaction state persists across transactions.

### Mempool validation-prefix simulation (implemented)

The full ERC-7562-style validation-prefix simulation is implemented as a local peer policy. Admission runs the following checks in order, all in addition to the static and signature checks above:

1. **Prefix recognition and structural validation**: the frame list is walked to identify the recognized shapes (`self_verify`, `deploy+self_verify`, `only_verify+pay`, `deploy+only_verify+pay`), and structural rules (frame modes, scope restrictions, gas budget) are validated. Unrecognized or invalid prefixes are rejected at admission.
2. **Validation-trace simulation**: a dedicated `ValidationObserver` on the VM enforces ERC-7562-style banned-opcode and storage-dependency rules during a throwaway prefix-only execution against the canonical head state. Banned opcodes (TIMESTAMP outside the expiry verifier, BALANCE, SELFBALANCE, BLOCKHASH, ORIGIN, COINBASE, GASPRICE, NUMBER, PREVRANDAO, GASLIMIT, BASEFEE, BLOBHASH, BLOBBASEFEE, SLOTNUM, SELFDESTRUCT, INVALID, TLOAD, TSTORE; SSTORE/CREATE/CREATE2 only inside a deploy frame; GAS only immediately before a call instruction) cause the tx to be rejected with `FrameTxValidationFailed`.
3. **Paymaster availability accounting**: the simulation identifies the payer (paymaster) and reserves the tx's `max_fee` against the paymaster's on-chain balance. `max_fee` bounds the `max_cost` APPROVE collects at any base fees, while the inclusion block's base fees are not known at admission. Concurrent pending reservations are summed so multiple sponsored txs cannot collectively overdraw the paymaster.
4. **Post-block revalidation**: after each new canonical block, pending frame txs are re-simulated against the updated head state and evicted if they no longer pass. Expiry-based eviction (deadline now behind the new block's timestamp) runs first without a full re-simulation.

**The simulation runs each prefix frame on block execution's terms.** It charges the resolved target's warm or cold access, and any delegation access, at frame entry within `limits.execution`. It seeds each frame's state pool from its own `limits.state` and isolates it, so a payment `APPROVE` that creates the sender or an EIP-8250 keyed-nonce slot draws on that budget and nothing else. It records each completed frame's status and gas, so a later prefix frame can read an earlier one through `FRAMEPARAM`. A prefix that would halt in a block for want of either budget is therefore rejected at admission, and one that fits is admitted.

**This is a local peer policy**: it never affects consensus or block building. It may over-reject (conservative) and must never under-reject.

**Known interim limitations (OQ resolutions)**:

- **OQ1 (canonical paymaster bytecode)**: no canonical paymaster bytecode hash is pinned in the EIP draft or any reference implementation. All paymasters are therefore treated as non-canonical, making the effective limit `MAX_PENDING_TXS_USING_NON_CANONICAL_PAYMASTER = 1` pending sponsored tx per paymaster. A clearly-marked hook (`FRAME_CANONICAL_PAYMASTER_CODE_HASH` const + `is_canonical_paymaster` fn in `mempool.rs`) is in place to flip this once the canonical bytecode is resolved upstream.
- **OQ3 (pending withdrawal amount)**: ethrex has no paymaster withdrawal queue. The pending withdrawal amount is treated as 0 in the availability formula: `available = balance - reserved_cost`. This is conservative (the formula under-computes available funds only if the paymaster has a real pending withdrawal, which cannot occur here).
- **Reorg re-add of reservations**: when a block is re-orged out, frame txs from the re-orged block are not automatically re-admitted with their reservations restored. A subsequent re-submission re-runs full admission and re-reserves. This is out of scope (ties to existing TODO #797).

**Policy scope**: this is a local peer policy. It runs only during mempool admission and post-block revalidation. It never influences block building, execution, or consensus. A frame tx admitted by this policy and included in a block by a different builder is still executed correctly.

### No access list support

Frame transactions don't have an access list field. Standard EIP-2930 access lists allow pre-declaring storage slots to reduce gas costs. Adding access list support to frame transactions would require extending the RLP format.

### Calldata gas is computed from RLP-encoded frames

The calldata gas component of intrinsic gas (`data_cost()` in `transaction.rs`) re-encodes the frames to RLP to count bytes. This is functionally correct but allocates a temporary buffer on every call. For gas limit validation in hot paths, this could be cached.
