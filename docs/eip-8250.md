# EIP-8250: Keyed Nonces for Frame Transactions

> **Spec target:** ethereum/EIPs `EIPS/eip-8250.md` @ commit `81b976ac0` (2026-08-03, "pin NONCE_MANAGER to 0x...8250"; Draft, Standards Track: Core; requires EIP-8141).

Implementation notes for EIP-8250 in ethrex. Builds on the EIP-8141 frame-transaction (type `0x06`) machinery and activates under the same `Fork::Hegota`.

## Overview

EIP-8250 replaces the single linear sender nonce of a frame transaction with a **keyed nonce** model: the envelope carries `nonce_keys` (1..=16 strictly-increasing `uint256` keys) plus a single `nonce_seq`. For every selected key, the protocol checks `current_nonce_seq(sender, key) == nonce_seq` and, on payment approval, advances each key's sequence by one. Key `0` is the legacy linear nonce domain (the account's `nonce`); non-zero keys live in the `NONCE_MANAGER` predeploy. This lets a shared sender run replay-independent transactions on disjoint key sets.

## Architecture

```
FrameTransaction envelope (crates/common/types/transaction.rs)
  nonce: u64                    ──►   nonce_keys: Vec<U256>  +  nonce_seq: u64
  (RLP, rkyv, sig_hash, serde, GenericTransaction, Transaction::nonce()->nonce_seq)

VM entry (crates/vm/levm/src/vm.rs)
  execute_frame_tx / run_frame_validation_prefix
    └─ for key in nonce_keys: current_nonce_seq(sender,key) == nonce_seq   (NonceMismatch otherwise)

APPROVE_PAYMENT / APPROVE_EXECUTION_AND_PAYMENT (opcode_handlers/frame_tx.rs)
    └─ consume_keyed_nonces(sender):
         key 0     → increment_account_nonce(sender)
         non-zero  → NONCE_MANAGER[slot(sender,key)] = nonce_seq+1  (+ KEYED_NONCE_FIRST_USE_GAS on 0→nonzero)

NONCE_MANAGER predeploy (crates/vm/system_contracts.rs, install in backends/levm/mod.rs)
    address 0x…8250, code 0x60006000fd (revert), nonce 1, installed at the Hegota boundary.
    slot(sender, key) = keccak256(left_pad_32(sender) || uint256_to_bytes32(key))
```

| Index | Value | Notes |

| `0x0D` | `len(nonce_keys)` | |
| `0x0E` | `nonce_keys_hash` | `keccak256(be32(len) ‖ be32(k0) ‖ …)` |

## Divergences from the draft spec (devnet)

1. **TXPARAM `nonce_keys[0]` at `0x10`** — spec-conformant, no longer a divergence. The draft originally assigned `0x0B`, which EIP-8141 already defines (and ethrex ships) as `len(signatures)`. The spec now pins `TXPARAM_NONCE_KEY_0 = 0x10` and states that EIP-8141 assigns indices through `0x0B` including `0x0B = len(signatures)`, so its four added indices are non-conflicting. `0x10` is the index ethrex has shipped since the implementation landed.

2. **`NONCEKEYLOAD` (opcode `0xB9`) for indexed `nonce_keys[i]` — ethrex-only extension.** EIP-8250 exposes only `len(nonce_keys)` (`TXPARAM 0x0D`), the whole-set digest `nonce_keys_hash` (`TXPARAM 0x0E`), and `nonce_keys[0]` (`TXPARAM 0x10`); it deliberately provides **no per-index accessor**, using the digest as the primitive for committing to the full key set. To let frame code read individual keys (author request), ethrex adds a dedicated opcode `NONCEKEYLOAD = 0xB9` — stack `[index]` → `nonce_keys[index]`; gas `3`; exceptional-halt (all gas consumed) on an out-of-range or oversized index; fork-gated at Hegota; reads only the signed envelope, allowed in any frame mode incl. VERIFY. This is a **spec extension, not required for conformance** (the digest already lets frame code commit to/verify the whole key set), so it is a documented divergence flagged for the 8141-family opcode registry upstream — the byte, gas, and out-of-range semantics are consensus-visible and must match across clients. Under the key-0-only mempool policy, `index > 0` resolves only for builder-included multi-key txs; for mempool-admitted txs (`nonce_keys == [0]`) only `index 0` succeeds. Handler + accessor unit test in `opcode_handlers/frame_tx.rs` (`OpNonceKeyLoadHandler` / `load_nonce_key`, covering indexed reads and the out-of-range exceptional halt); fork-gating test (invalid pre-Hegota, valid at Hegota) in `opcodes.rs`.
3. **`NONCE_MANAGER` address `0x…8250` — spec-conformant, no longer a divergence.** The spec pins `NONCE_MANAGER = 0x0000000000000000000000000000000000008250`, the `0x…<EIP>` convention `EXPIRY_VERIFIER = 0x…8141` already uses, which is the value ethrex has shipped since the implementation landed. `NONCE_MANAGER_CODE = 0x60006000fd` matches too. `FORK_TIMESTAMP` remains `TBD` upstream, as it is decided by fork scheduling.
4. **Payment approval is forbidden inside an atomic batch.** EIP-8250 mandates that keyed-nonce consumption "MUST NOT be reverted by a later frame revert, by skipping frames, or by restoring an atomic-batch snapshot", and groups the five effects of a successful payment-scoped APPROVE (nonce consumption, payer recording, the balance debit, first-use gas, approval flags) as durable together. The "restore an atomic-batch snapshot" clause only bites when the payment APPROVE runs *inside* a batch (after the snapshot). Making all five effects survive that revert requires re-asserting the balance debit as an idempotent delta across arbitrarily nested reverts, coherent with the end-of-tx refund and EIP-7928 BAL — a mechanism the draft does not pin and that needs cross-client validation. Shipping only *part* of it (consumption + flags durable, debit reverted) would strand an authorization over an un-charged payer and mint the refund. So ethrex instead **rejects a payment-scoped APPROVE whose frame is in an atomic batch** (`apply_approve`, via `FrameTransaction::frame_is_in_atomic_batch`): the APPROVE reverts, `payer` stays unset, and the transaction is invalid. This matches the mempool, which already bans the batch flag in the validation prefix (where payment is granted); the consensus guard covers the crafted-block path the prefix rules do not reach. **The legitimate case is unaffected:** payment granted in a non-batch frame with a *later* SENDER atomic batch reverting keeps its consumption, because an independent frame's committed state is absorbed into the tx-level backup and is outside the batch's revert scope (covered by `eip8250_tests`). Full in-batch-payment durability is deferred to **Hegotá devnet + cross-client interop validation**.

## Validation rules

- **Nonce-key validity.** A `nonce_keys` list that contains key `0` is rejected unless it is exactly `[0]` — key 0 maps to the account's linear nonce, so it may only appear as the sole key. This closes a double-consumption hole where one transaction could consume the account nonce via both key 0 and a keyed slot. Enforced in `validate_static_constraints` (with a unit test); composes with the existing 1..=16, strictly-increasing, `nonce_seq != u64::MAX` checks.
- **NONCE_MANAGER activation.** At the Hegota boundary the predeploy at `0x…8250` is installed following the spec's 3-case rule: nonce = `max(existing_nonce, PREDEPLOY_NONCE)`, balance preserved, idempotent on re-run (early-returns once the expected runtime bytecode is present, so exactly one account update is produced at the first Hegota block). Case 3 (an address that already carries code/storage) is spec-undefined and is not special-cased.

## Mempool policy

The public mempool admits **both key-0 and non-zero-keyed** frame transactions.

- **Key-0 / linear** frame txs use the account's linear nonce domain: they are tracked per sender (`pending_frame_tx_by_sender`) against the shared `(sender, nonce_seq)` slot (`txs_by_sender_nonce`), so at most one is pending per sender and a same-nonce resubmission is a fee-bump.
- **Non-zero-keyed** frame txs claim each of their individual keys in a per-`(sender, nonce_key)` holder map (`pending_frame_key_holder`), never in the linear slot (see the deliberate divergence below). First-seen holds a key, so one sender may have several pending keyed txs as long as their key sets are **fully disjoint**. A later tx that shares ANY key with a pending one is rejected (`FrameTxSenderAlreadyPending`) unless it is an exact-key-set fee-bump of that same tx (same `nonce_seq` → replacement; different `nonce_seq` → rejected). Tracking per individual key rather than by a whole-key-set digest is deliberate: under a set digest a sender's `{a,b}` and `{b,c}` hashed differently and both admitted, then whichever mined first consumed the shared key `b` and silently invalidated the other. Their per-key nonce validity is checked by the validation-prefix simulation (`run_frame_validation_prefix` → `current_nonce_seq`) against `NONCE_MANAGER`, not the linear account nonce; the linear-nonce admission guards (`nonce < account_nonce`, `nonce == u64::MAX`) are skipped for them. `get_nonce` (the pending-nonce RPC) stays linear/key-0-scoped and ignores keyed txs.

Mempool admission is a local over-rejection policy; block execution validates every key in full regardless. One holder per `(sender, nonce_key)`, the linear slot never being touched by keyed txs, and per-paymaster reservation limits remain enforced.

**Deliberate divergence: concurrent keyed transactions per sender.** EIP-8250 §Mempool re-expresses
the pending identity as `(sender, nonce_keys, nonce_seq)` but keeps EIP-8141's rule verbatim: "All
other EIP-8141 public mempool rules, including the limit of one pending frame transaction per
sender, remain unchanged." Its Motivation frames keyed-aware concurrency as future work, removing
"the protocol-level nonce obstacle to future keyed-aware mempools". ethrex implements that future
mempool, but only for transactions that provably cannot invalidate each other. ethereum/EIPs#12039
(*Define keyed mempool concurrency*, open) proposes essentially this policy upstream, as an optional
exception keyed per `(sender, nonce_key)` with `nonce_keys == [0]` left under the sender limit. This is admission
policy, never consensus, and it admits a superset of what the spec's rule admits, so a block built
by either node is valid to both.

**Concurrency eligibility gate.** `keyed_concurrency_verdict` (called from `validate_transaction`,
carried into the locked insert as `KeyedConcurrency`) grants concurrency only when all four hold:

1. the sender runs real contract code, neither an EOA nor an EIP-7702 delegation (an EOA's
   default-code prefix authenticates against the sender's own nonce, and a delegation can be
   retargeted at any time),
2. the validation prefix has no deploy frame, which would install the sender's code mid-flight,
3. the prefix read no sender storage (`FrameValidationOutcome::touched_sender_slots` is empty), so
   no sibling transaction's `SSTORE` can invalidate it,
4. the prefix did not read `TXPARAM(0x0C)`, the legacy account nonce that a key-0 transaction bumps
   on inclusion (`ValidationObserver::read_legacy_nonce`).

**Safe fallback.** Anything else is held to EIP-8141's one pending frame transaction per sender.
Concurrency also requires *both* sides to be independent: an eligible transaction is refused when the
sender already has an ineligible one pending, and vice versa.

**Key-domain separation.** A `[0]` transaction and a keyed transaction from the same sender are never
pending together (`FrameTxKeyDomainMixed`), in either arrival order. A `[0]` transaction consumes the
legacy account nonce on inclusion, so allowing the mix would let it invalidate a keyed transaction
that depends on that nonce. `pending_keyed_by_sender` records each pending keyed transaction with the
verdict it was admitted under, which is what makes this check and the fallback cheap.

**Atomic replacement check.** The insert re-validates the fee bump against the predecessor that is
pooled *now*, under the write lock. The price check in `find_tx_to_replace` /
`find_keyed_frame_tx_to_replace` runs unlocked, so without the recheck two concurrent
same-`(sender, keyset, nonce_seq)` resubmissions could let a lower-fee one evict a higher-fee one.

### Known mempool-local limitations (benign, adversarial-review-tracked)

These are self-healing, mempool-local behaviors — they never corrupt the pool, leak a reservation, or produce an invalid block; block execution is authoritative:

- **Builder defers a sender's independent txs by one block.** Because keyed frame txs (a different nonce domain) can now legitimately coexist with a sender's linear txs, the payload builder groups them under one sender and its whole-sender-queue drop (`TransactionQueue::pop`) can skip that sender's *independent* linear txs for the current build if a coexisting keyed tx is stuck at the queue head (fails execution or does not fit remaining gas). The skipped txs stay pooled and are included in the next build, so it self-heals within one block. Giving keyed txs a distinct builder grouping is a possible follow-up; builder ordering is out of scope for this admission change.
