# EIP-8250: Keyed Nonces for Frame Transactions

> **Spec target:** ethereum/EIPs `EIPS/eip-8250.md` @ commit `1a086d5c`, the bogota-devnet-2
> revision: the empty key set selects the account nonce, key `0` is an ordinary key, and
> `nonce_seq == MAX_NONCE_SEQ` marks single-use keys.
>
> **Reference implementation:** execution-specs `devnets/bogota/2`, released as
> `tests-bogota-devnet@v2.0.0`.

Implementation notes for EIP-8250 in ethrex. It builds on the [EIP-8141](./eip-8141.md) frame
transaction (type `0x06`) and activates with it at `Fork::Hegota`, the fork execution-specs calls
`Bogota`.

## Overview

EIP-8250 replaces a frame transaction's single `nonce` with a set of **nonce keys** and one shared
**sequence**:

- `nonce_keys` holds up to 16 strictly increasing `uint256` keys.
- `nonce_seq` is the `uint64` sequence every selected key must currently be at.

The empty key set selects the sender's account nonce and keeps EIP-8141's replay behavior. Every
key, `0` included, is a slot in the `NONCE_MANAGER` system contract. A keyed transaction never
touches the account nonce, so one sender can use independent replay domains: a privacy pool's
nullifiers, a session key's own sequence, or single-use authorizations.

`nonce_seq == MAX_NONCE_SEQ` (`2**64 - 1`) is the single-use form of a keyed transaction: it is
valid only while every selected key is unused, and it exhausts each of them by writing
`MAX_NONCE_SEQ`, so no sequence can select them again. The empty key set cannot use that sequence.

## How to use it

A frame transaction on keyed nonces differs from an EIP-8141 one only in the two nonce fields and in
the state budget of its payment-approving frame:

1. Pick the keys. Use `[]` for the account nonce, or up to 16 distinct keys in increasing order.
2. Set `nonce_seq` to the current sequence of every selected key, or to `MAX_NONCE_SEQ` to use
   unused keys once. A key nobody has used reads as `0`. The current sequence is
   `NONCE_MANAGER.storage[keccak256(left_pad_32(sender) || be32(key))]`, readable with
   `eth_getStorageAt` on `0x8250968C12e01A19d6F667b9B2F3b3A4d0e51cB7`.
3. Give the frame that calls `APPROVE` with a payment scope enough `limits.state` for every key's
   first use: 97,920 per key whose slot is still zero. An account-nonce transaction from a sender
   that does not exist yet pays account creation instead. Separately, every key adds
   `KEYED_NONCE_ACCESS_COST`, 12,100 gas, to the transaction's intrinsic gas and to its calldata
   floor; it comes out of the fee, not out of any frame's limits.
4. Sign as usual. The signature hash covers `nonce_keys` and `nonce_seq` where it covered `nonce`.

Example: transactions on key `0xbeef`.

```text
nonce_keys = [0xbeef]      nonce_seq = 1           ->  invalid: the key is at 0
nonce_keys = [0xbeef]      nonce_seq = 0           ->  valid; afterwards the key is at 1
nonce_keys = [0xbeef]      nonce_seq = 1           ->  valid on the next transaction
nonce_keys = [0xbeef]      nonce_seq = 2**64 - 1   ->  invalid: single use needs an unused key
nonce_keys = [0xcafe]      nonce_seq = 2**64 - 1   ->  valid once; afterwards the key is exhausted
nonce_keys = []            nonce_seq = 2**64 - 1   ->  statically invalid (NONCE_IS_MAX)
```

The JSON-RPC form carries the sequence in `nonce`, as before, and the keys in `nonceKeys`:

```json
{ "type": "0x6", "nonce": "0x0", "nonceKeys": ["0xbeef"], "sender": "0x...", "frames": [...] }
```

## Architecture

```text
FrameTransaction (crates/common/types/transaction.rs)
  [chain_id, nonce_keys, nonce_seq, sender, frames, signatures, fees, blob_versioned_hashes]
  static validity: 0..=16 keys, strictly increasing; [] not at 2**64 - 1
  data cost and calldata tokens include rlp(nonce_keys) || rlp(nonce_seq), without
    rlp(nonce_seq) for a single-use keyed set
  mandatory_gas, shared by intrinsic gas and the calldata floor, includes
    KEYED_NONCE_ACCESS_COST (12,100) per key

VM, before any frame runs (crates/vm/levm/src/vm.rs)
  [] at 2**64 - 1, checked first                          (NonceIsMax)
  []: the account nonce == nonce_seq                      (NonceMismatch otherwise)
  keyed at 2**64 - 1: every key's slot reads 0            (NonceMismatch otherwise)
  keyed otherwise: every key's slot reads nonce_seq       (NonceMismatch otherwise)
  legacy_sender_nonce captured for TXPARAM(0x0D)

APPROVE with scope 0x1 or 0x3 (crates/vm/levm/src/opcode_handlers/frame_tx.rs, approve_payment)
  1. payer balance >= max_cost, else the frame reverts
  2. [] and the account nonce is already 2**64 - 1: exceptional halt
  3. nonce_state_gas from the frame's limits.state, else exceptional halt:
       []    -> new-account state gas when tx.sender does not exist
       keyed -> 97,920 per selected slot that still reads 0
  4. consume_nonce_set:
       []    -> increment the account nonce
       keyed -> NONCE_MANAGER[slot(sender, key)] = nonce_seq + 1, or 2**64 - 1 for single use
  5. collect max_cost and record the payer

NONCE_MANAGER (crates/common/types/transaction.rs, crates/vm/system_contracts.rs)
  address 0x8250968C12e01A19d6F667b9B2F3b3A4d0e51cB7, code 0x60006000fd,
  an ordinary contract created by its keyless deployment transaction
```

Steps 3 to 5 apply together or not at all. They sit inside the approving frame's revert scope, so a
frame that fails after approving discards them with its other effects. Once that frame succeeds,
nothing later in a valid transaction reverts them: not a later frame failure, not an atomic batch
unroll, and not a restore that discards the execution body.

Keyed-nonce reads and writes are protocol bookkeeping. They warm neither `NONCE_MANAGER` nor its
slots and are not priced as `SSTORE`; `KEYED_NONCE_ACCESS_COST` in the intrinsic gas pays for
them instead. They are ordinary storage for the block access list: every slot `consume_nonce_set`
writes is a storage change of `NONCE_MANAGER` at the transaction's index, carrying the written
value. The reads are not recorded, and since a valid transaction writes every slot it reads, with a
different value, those slots never appear among the storage reads. An account-nonce transaction
leaves `NONCE_MANAGER` out of the list.

## Transaction introspection

| `TXPARAM` | Value |
|---|---|
| `0x01` | `nonce_seq` |
| `0x0D` | the sender's account nonce before any frame ran. Payment approval does not update it. |
| `0x0E` | `len(nonce_keys)` |
| `0x0F` | `keccak256(be32(len) \|\| be32(key_0) \|\| ...)` |
| `0x10` | `nonce_keys[0]`, or `0` for the empty key set |

Verifier code that treated `TXPARAM(0x01)` as the account nonce must either require
`TXPARAM(0x0E) == 0` or handle keyed sequences.

## Deployment

`NONCE_MANAGER` is an ordinary contract. Its keyless deployment transaction creates it at
`0x8250968C12e01A19d6F667b9B2F3b3A4d0e51cB7` with code `0x60006000fd`, and a chain must have it in
state when the fork activates, either deployed before the fork or allocated in genesis with nonce
1. Activation changes no state and adds nothing to the block access list.
[EIP-8141 § Contract Deployment](./eip-8141.md#contract-deployment) lists all three frame
contracts.

## Mempool

- **Identity.** A pending frame transaction is identified by `(sender, nonce_keys, nonce_seq)`. A
  submission with the same identity is a fee-bump replacement. Anything else from a sender with a
  pending frame transaction is refused with `FrameTxSenderAlreadyPending`, since EIP-8250 keeps
  EIP-8141's limit of one pending frame transaction per sender.
- **Account nonce slot.** A keyed transaction's `nonce_seq` is not an account nonce, so it is never
  indexed under `(sender, nonce)`. It neither replaces nor shadows an ordinary transaction that the
  same sender has pending at that nonce.
- **Nonce checks.** Admission skips the account-nonce ordering checks for keyed transactions. The
  validation-prefix simulation checks every key against `NONCE_MANAGER` at the head instead.
- **Revalidation.** After every fork-choice update each pending frame transaction is simulated
  again at the new head, so a key consumed by an included transaction evicts the transactions that relied on it. That
  covers the `TXPARAM(0x0D)` dependency as well, at the cost of a full rescan.
- **State budget.** EIP-8141 rule 6 lets a `VERIFY` frame declare state gas for this EIP's first-use
  charge. The prefix's state budgets together may not exceed `MAX_VERIFY_STATE_GAS` (500,000), and
  the simulation draws the charge from the frame's own `limits.state`, as block execution does.

## Design decisions

- **One pending frame transaction per sender.** EIP-8250 removes the protocol obstacle to
  concurrent keyed transactions, but keeps the mempool limit. ethereum/EIPs#12039 proposes the
  concurrency policy and is still open, so ethrex follows the current text.
- **The account nonce's `nonce_seq` bound is a static rule.** An empty key set at `2**64 - 1`
  reads no state to be invalid, so `validate_static_constraints` enforces it and the mempool
  rejects such a transaction before reading any. Block execution checks it ahead of every other
  static rule and reports `NONCE_IS_MAX`, as execution-specs does, rather than a generic
  frame-format error.
- **The single-use sequence is not priced as data.** For a keyed set at `MAX_NONCE_SEQ`,
  `nonce_calldata` leaves `rlp(nonce_seq)` out, so the single-use form costs no more than first use
  at sequence `0`. The field is still encoded and signed.

## Testing

```sh
# VM and mempool unit tests
cargo test -p ethrex-test --test ethrex_tests -- eip8250 keyed_nonces

# Envelope, signature hash and the reference keyed transaction from execution-specs
cargo test -p ethrex-test --test ethrex_tests -- frame_tx_validation_tests

# The pinned tests-bogota-devnet release, EIP-8250 suite included
make -C tooling/ef_tests/blockchain test-levm
make -C tooling/ef_tests/engine test
make -C tooling/ef_tests/engine test-strict
```

The fixture targets overlay the release's `Bogota` and Amsterdam-to-Bogota fixtures on the base
suite. `tests/bogota/eip8250_keyed_nonces` covers the envelope, stateful validity, nonce
consumption and its state gas, `TXPARAM` `0x0D` to `0x10`, the block access list, and the
deployment of `NONCE_MANAGER` before and after the fork, and the keyed-nonce access cost in the
intrinsic gas, the calldata floor and `TXPARAM`'s maximum cost.
