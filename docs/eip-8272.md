# EIP-8272: Recent Roots for Frame Transactions

> **Spec target:** ethereum/EIPs `EIPS/eip-8272.md` @ commit `d8636a330` (2026-08-03, "pin RECENT_ROOT_ADDRESS to 0x...8272"; Draft, Standards Track: Core; requires EIP-7623, EIP-7843, EIP-8141).

Implementation notes for EIP-8272 in ethrex. Builds on EIP-8141 frame transactions and EIP-7843 `SLOTNUM` (both already present); activates under `Fork::Hegota`.

## Overview

EIP-8272 lets a frame transaction declare verified **recent roots** — `(source_id, slot, root)` tuples — in its signed envelope, so validation code (e.g. privacy proofs) can reference a recent commitment without reading another account's mutable storage. References are checked for validity at block execution against the `RECENT_ROOT_ADDRESS` predeploy.

## Implemented (this branch)

| Piece | Detail |
|-------|--------|
| Opcode `RECENTROOTREFLOAD` | `0xB6`, spec-conformant. Stack `[field, index]` (field on top); `field` 0→source_id, 1→slot, 2→root; gas 3; halts if `index ≥ len` or `field > 2`; reads only the envelope. |
| Envelope field | `recent_root_references: Vec<RecentRootReference>` — last RLP field (the **10th** ethrex field, after `blob_versioned_hashes`; the spec calls it the 9th because it omits ethrex's `signatures`). `RecentRootReference { source_id: H256, slot: u64, root: H256 }`, RLP `[source_id, slot, root]`, rkyv-derived. Covered by `compute_sig_hash` (not elided in VERIFY frames). |
| Static validation | `len ≤ FRAME_TX_MAX_RECENT_ROOT_REFERENCES (16)`; 3-tuple shape + 32-byte `source_id`/`root` + `slot < 2**64` enforced by the type/RLP. |
| TXPARAM `0x11` | `len(recent_root_references)`, spec-conformant. |
| `RECENT_ROOT_ADDRESS` | predeploy at `0x…8272` (`crates/vm/system_contracts.rs`). |
| Gas | `RECENTROOTREFLOAD = 3`; `RECENT_ROOT_REFERENCE_ADDRESS_GAS = ACCESS_LIST_ADDRESS_COST = 3000`; `RECENT_ROOT_REFERENCE_GAS = ACCESS_LIST_STORAGE_KEY_COST + 2*30 + 7*6 = 3102`. Both access-list parameters are 3000 from Amsterdam onward (EIP-8038) and frame txs exist only from Hegota, so the raised values always apply and neither constant needs a fork parameter. The live values sit in ethrex-common (which cannot depend on levm's `gas_cost`); `gas_cost` derives its own from `ACCESS_LIST_*_AMSTERDAM` and asserts equality at compile time so the two cannot drift. The EIP-8272 delta splits in two, per §Gas accounting: `recent_root_calldata = rlp(recent_root_references)` is ordinary transaction data, so its cost enters `data_cost` (hence `standard_gas_limit`) and its tokens enter `calldata_tokens` (hence the EIP-7623 floor); `FrameTransaction::recent_root_reference_intrinsic_gas()` = `ADDRESS_GAS + n * REFERENCE_GAS` is a **mandatory** cost, added to both `standard_gas_limit` and `calldata_floor_gas` so the floor can never absorb the warming it prepays. Both are zero when no reference is declared, so a reference-free frame tx costs exactly the EIP-8141 figure. Pinned by `reference_gas_is_charged_even_when_the_calldata_floor_binds`. |

## `RECENT_ROOT_CODE`

ethrex installs the 144-byte runtime specified in [ethereum/EIPs#12131](https://github.com/ethereum/EIPs/pull/12131), assembled verbatim from §Bytecode rather than compiled, so the mapping to the prose is line by line. ethrex's bytes are identical to the PR's, all 144 of them. The PR is unmerged, so upstream's Constants table still reads `TBD` on master.

| | |
|---|---|
| Length | 144 bytes |
| `keccak256(RECENT_ROOT_CODE)` | `0x432c8b183d17d5e9939623833203b9a5b62325246cfcd9307982bfde8f18c6fb` |
| `PUSH32` at `0x22` (immediate `0x23..0x43`) | `keccak256("RECENT_ROOT_ENTRY")` |
| `PUSH32` at `0x5a` (immediate `0x5b..0x7b`) | `keccak256("RECENT_ROOT_STORAGE")` |

Both immediates are the domains the read side already derives in `RecentRootReference::{entry_hash, storage_key}`, so the swap moved gas and call semantics and left the hash layout alone: a root written through the predeploy validates its own reference. `recent_root_bytecode_matches_spec` pins all four rows.

**Measured write gas.** A plain EOA transaction to `0x…8272` with 64 non-zero calldata bytes costs **127 256 gas** (`plain_eoa_call_writes_the_entry`). Execution is far above the EIP-7623 calldata floor, so the floor never binds and each zero byte in `salt ‖ root` takes 12 gas off — a zero byte is one token against a non-zero byte's four. That single curve reconciles both figures on record: `#12131` reports 127 244 for a payload with one zero byte, and ethrex `#7120` reports 127 196 for one with five. Neither is a pricing disagreement.

**The two questions `#12131` raised, both now settled the way ethrex ships:**

- **The modulus is compiled as a mask.** `push2 0x1fff` equals `S mod RECENT_ROOT_LENGTH` only while that constant is 8192; a `MOD` would cost 3 more gas and survive any future value. The spec's own assembly listing endorses the mask ("`RECENT_ROOT_LENGTH` is a power of two, so the modulus is a mask"). ethrex pins the assumption with a compile-time assertion on `FRAME_TX_RECENT_ROOT_LENGTH == 8192` next to the bytecode, so changing the length breaks the build rather than the chain.
- **Install at activation, with no deployment transaction.** A departure from EIP-2935 and EIP-4788, which deploy from a synthetic sender. ethrex installs at the fork gate with no transaction, which is what the EIP's Activation section mandates ("clients MUST create it with balance 0, nonce 1, code `RECENT_ROOT_CODE`, and empty storage") and what ethrex already does for `0x…8141` and `0x…8250`.

**Static context halts rather than reverting.** Malformed calldata or non-zero value exits through the code's own `REVERT`, refunding the unused gas; a valid-shaped `STATICCALL` reaches the `SSTORE` and exceptional-halts, consuming everything remaining in the subcontext. The two exits cost differently and both are reachable from a frame, so the distinction is consensus-visible.

**Delegate-style calls succeed; they just write elsewhere.** Per §"Only execution whose storage context is `RECENT_ROOT_ADDRESS` writes recent-root storage", a `DELEGATECALL` or `CALLCODE` to this code — and a call to an EIP-7702 account delegated to `0x…8272` — runs the `SSTORE` and returns success, writing the derived entry into the *calling* account's storage. Recent-root storage is untouched and the entry is not referenceable. `delegatecall_writes_the_callers_storage_and_leaves_the_predeploy_untouched` pins both halves.

## Divergences from the draft spec

1. **`RECENTROOTREFLOAD` at `0xB6`** — spec-conformant. The byte has moved twice, both times to dodge EIP-8141: off `0xB4` when that collided with `SIGPARAM`, and off `0xB5` when EIP-8141 v2 introduced `SIGDATACOPY` there (upstream `0231fb05f5`, 2026-08-31). ethrex is at `0xB6` and matches.
2. **TXPARAM index `0x11`** — spec-conformant. The spec was once internally inconsistent, its Constants table saying `0x0F` and its summary table `0x0D`; both settled on `0x0F`, which ethrex shipped. Upstream `0231fb05f5` (2026-08-31) then moved it again, to `0x11`, because EIP-8250's three indices shifted up onto `0x0F` after EIP-8141 v2 claimed `0x0C`. ethrex follows.
3. **`RECENT_ROOT_ADDRESS = 0x…8272`** — spec-conformant, no longer a divergence. The spec pins `RECENT_ROOT_ADDRESS = 0x0000000000000000000000000000000000008272`, the `0x…<EIP>` convention `EXPIRY_VERIFIER = 0x…8141` already uses, which is the value ethrex has shipped since the implementation landed. `RECENT_ROOT_CODE` is still `TBD` upstream; see [`RECENT_ROOT_CODE`](#recent_root_code) above for what ethrex installs in its place.
4. **`source_id = keccak256(caller ‖ salt)`** — spec-conformant, not a divergence. EIP-8272 §Root sources defines `source_id = keccak256(source_address ‖ salt)`, and its Specification preamble fixes the encodings: "Addresses are 20 bytes", salts are 32. The preimage is therefore 52 bytes, with the address unpadded. The write side derives it from `msg.sender` and the call's salt, so a namespace is caller-authenticated (nobody can write into another caller's) and salt-differentiated; a referencing transaction declares the same `source_id` in its envelope.
5. **Beacon slot source: EL-derived when the CL doesn't forward it (EIP-7843 dependency).** `env.slot_number` (EIP-7843 `SLOTNUM`) — which the reference-validity window and the predeploy's slot key on — is meant to come from the CL via `PayloadAttributesV4.slot_number` on `engine_forkchoiceUpdatedV4`. The Hegotá devnet's CL (Lighthouse v8.0.0-rc.1) drives ethrex over `forkchoiceUpdatedV3`, which has no slot field, so `header.slot_number` is `None` and `env.slot_number` would be `0` — leaving every root write committed to slot 0 and no reference ever able to validate (EIP-8272 non-functional e2e). ethrex adds a `ChainConfig` knob **`derivedSlotTime`** (+ `genesisTimestamp`, `secondsPerSlot`) that, once active *and only when the CL supplies no slot*, derives it from the block timestamp: `slot = (block_timestamp − genesis_timestamp) / seconds_per_slot` — exact for slot-aligned PoS timestamps (a missed slot still advances the counter and produces no block). A CL-supplied slot always wins (`ChainConfig::effective_slot_number` prefers `header.slot_number`), so ethrex is forward-compatible with an EIP-7843-aware CL over V4 **with no further change**; the derivation is a single-EL devnet fallback, not the spec mechanism. Gated on a *future* timestamp (new-fork decoupling) so pre-knob blocks keep slot 0 and re-execute identically — the write/reference state is slot-keyed, so an un-gated change to already-produced blocks would be a state-root mismatch. Deployed on the Hegotá devnet 2026-07-08 and proven e2e (a root write committed to the timestamp-derived slot, not slot 0). **Prover caveat:** the Amsterdam SSZ proving reconstruction (`guest-program/src/l1/program.rs`) reads the payload slot verbatim and does *not* apply this derivation, so the `ProgramInput`/witness must carry the derived slot before proving is enabled on a knob-active chain (fail-safe unprovability today, no prover on the devnet; the general RLP "Direct" proving path already mirrors the derivation via the witness `ChainConfig`).

6. **Calldata charge and floor placement (resolved).** EIP-8272 used to restate the whole EIP-8141 gas formula with `recent_root_calldata = rlp(tx.signatures) ‖ rlp(tx.frames) ‖ rlp(recent_root_references)` charged as one byte string, against a superseded EIP-8141 revision — double-charging the frames and signatures ethrex already prices as data fields. The additive rewrite settles it: `recent_root_calldata` is `rlp(recent_root_references)` alone, its cost joins `standard_gas_limit` and its tokens join `calldata_tokens`, while only `recent_root_reference_intrinsic_gas` is added to `calldata_floor_gas`. ethrex had anticipated the first half (it never charged the frames and signatures twice) and now implements the floor placement too.

## Consensus core (implemented)

The full consensus path is wired; the interim reject-all gate is gone.

- **Reference validity** (`execute_frame_tx`, before the frame loop): each reference must satisfy `1 ≤ current_slot − slot ≤ 8191` (`current_slot` from EIP-7843 `env.slot_number`, checked in U256, never `block.timestamp`) and `RECENT_ROOT_ADDRESS[storage_key] == entry_hash`. An invalid reference invalidates the transaction — and on import the block — before any frame executes. `entry_hash` commits to the **raw** slot, so an entry overwritten by an aliasing newer slot (same `slot mod 8192`) can never satisfy a stale reference; this closes the forged-roots soundness hole, and `RECENTROOTREFLOAD` now serves only verified roots.
- **Hash derivation** (`RecentRootReference::{entry_hash, storage_key}` in ethrex-common): `entry_hash = keccak256(keccak256("RECENT_ROOT_ENTRY") ‖ source_id ‖ uint64_be(slot) ‖ root)`, `storage_key = keccak256(keccak256("RECENT_ROOT_STORAGE") ‖ source_id ‖ uint64_be(slot mod 8192))`. One definition shared by the validity check, the predeploy's write, and the mempool policy — a root written through the predeploy always validates its own reference.
- **Access warming and BAL**: the predeploy address and every reference's storage key are warmed in the validity pass (the per-reference intrinsic gas prepaid this). The pass performs real storage reads rather than merely declaring access-list entries, so per EIP-7928 each key is recorded in the block access list as a **read** (`storage_reads`, never a change) under the transaction's own `block_access_index`. Recording happens only after the whole pass succeeds: a failed reference invalidates the transaction and the block with it, leaving nothing to record.
- **Predeploy install** (`install_recent_root_code`): the spec's three activation cases. Absent → create with balance 0, nonce 1, `RECENT_ROOT_RUNTIME_BYTECODE`, empty storage. Present with empty code and empty storage → set the code, take `nonce = max(existing, 1)`, preserve the balance (an EOA may have sent value here pre-fork, and may have sent transactions from it). Present with code or storage in the **parent** state → the payload is invalid; the storage root is read through the store, since it is the only witness that the account holds no slots. Installed at the Hegota gate from both `prepare_block` and `apply_system_calls`, so the account exists before any tx executes in the first Hegota block, and the code and nonce are recorded through `bal_recorder` so a BAL reconstructor reproduces the post-state. Idempotent on the code, so exactly one account update is produced and no later block carries a spurious predeploy entry.
- **Write**: calling the predeploy with exactly 64 bytes `salt ‖ root` and zero value commits the current slot's entry under `source_id = keccak256(caller ‖ salt)` (20-byte address, 32-byte salt). This is the installed bytecode running, not a VM hook, so warm/cold accounting, journaling, gas and BAL recording are whatever the EVM already does for an `SSTORE`: a frame targeting the predeploy, a CALL-family invocation and a transaction sent straight to `0x…8272` all execute the same code and none of them silently no-ops; the write costs whatever the code costs, so an entry that creates a slot pays the EIP-8037 state gas and an overwrite does not; and a write inside a reverting frame rolls back with it (contrast EIP-8250 keyed-nonce consumption, whose spec explicitly mandates revert-survival). In the block access list it is a storage **change** under the writing transaction's `block_access_index`, against a reference's storage **read** — `a_write_is_a_change_and_a_reference_is_a_read` carries both in one block, and `the_access_list_commitment_survives_a_rebuild` requires the importer to reconstruct the same commitment.
- **Mempool/builder policy** (`validate_transaction`): admission-time rejection of too-new (`slot ≥ head_slot + 1`), expired (window exceeded), and uncommitted-root references, asserted explicitly against head state (the mempool's validation-prefix simulation never reaches `execute_frame_tx`, so the storage assertion is duplicated there by design). The policy runs *after* static validation and signature authentication, since it performs one head-state storage read per reference: ahead of them, a single unauthenticated `MAX_TX_SIZE` transaction could declare thousands of references and force a keccak-random storage lookup for each. The same conditions run again from post-block revalidation (`revalidate_frame_txs_after_block`), so a slot advance that ages a reference out of the usable window, or a reorg that leaves it uncommitted, evicts the transaction instead of leaving it pooled until block building fails it; a storage-read failure there is treated as transient and keeps the transaction. Reference failures are split into transient and permanent (`FrameTxRecentRootNotReferenceable` vs `FrameTxRecentRootInvalid`) because block building evicts a frame tx on any non-nonce-mismatch failure: a root written in slot `S` is unreferenceable until `S + 1`, so a build landing in the slot the tx was admitted against must keep it pooled rather than drop it permanently.

## ⚠ Remaining / flagged for devnet validation

- **Cross-client interop** on the Hegotá devnet: the `source_id` derivation (divergence #4) and the hash byte layouts need a second client / spec ratification before any public network relies on them. Any mismatch is a hard fork on the first reference-carrying transaction.
- **CL-provided slot** (divergence #5): the spec-faithful path is an EIP-7843-aware CL forwarding the beacon slot over engine V4; the devnet's Lighthouse does not, so ethrex derives it EL-side behind the `derivedSlotTime` knob. Also fold the derived slot into the `ProgramInput`/witness before enabling proving on a knob-active chain.
- **`SLOTNUM` is banned in the validation prefix, ahead of the spec.** EIP-8141 §Banned Opcodes bans `NUMBER`, `TIMESTAMP`, `PREVRANDAO`, `BASEFEE` and friends because a validation prefix branching on them can pass at admission and fail at inclusion. EIP-8272 makes the beacon slot load-bearing, which gives `SLOTNUM` (EIP-7843) exactly that property, yet it is absent from the list — which predates EIP-7843. ethrex bans it (`0x4B`, in the banned set at `crates/vm/levm/src/vm.rs`), so a validation prefix branching on the slot is admitted by a spec-literal client and rejected here. Proposed upstream as ethereum/EIPs#12066 (*ban SLOTNUM during validation-prefix execution*), unmerged; the divergence stands until it does.
- **`RECENT_ROOT_CODE` is provisional.** ethereum/EIPs#12131 specifies the bytecode ethrex installs, byte for byte, but is open rather than merged. A change to the installed code changes nothing about the hash layout but does change the code hash and the write's gas, so it is a fork for any chain already running. Track the PR until it merges.
- **The PR's test matrix is not fully covered here.** Calldata lengths 0/63/64/65, zero and non-zero value, ordinary `CALL` against a top-level transaction against `STATICCALL`/`DELEGATECALL`/`CALLCODE`/7702, cold fresh write against cold overwrite against warm overwrite, a write inside an enclosing revert, repeated writes by one `(caller, salt)` in a slot, slots `0`/`1`/`8191`/`8192`/`8195`/`2**64-1`, and reference ages `0`/`1`/`8191`/`8192`. Interop rests on these agreeing.
- Upstream spec gaps to flag: `source_id` derivation. Settled upstream: `RECENT_ROOT_ADDRESS` (divergence 3), the opcode byte (divergence 1), the TXPARAM index (divergence 2), the gas section's EIP-8141 revision skew (divergence 6), the foreign-storage semantics of delegate-style and EIP-7702 calls, and the activation requirement on EIP-7843. The `SLOTNUM` ban and the `RECENT_ROOT_CODE` bytecode are specified in open PRs, not merged.
