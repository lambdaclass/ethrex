# EIP-8272: Recent Roots for Frame Transactions

> **Spec target:** ethereum/EIPs `EIPS/eip-8272.md` (Draft, Standards Track: Core; requires EIP-7843, EIP-8141). Read against `eips.ethereum.org` master on 2026-06-24. Pin the exact spec commit once it is frozen.

Implementation notes for EIP-8272 in ethrex. Builds on EIP-8141 frame transactions and EIP-7843 `SLOTNUM` (both already present); activates under `Fork::Hegota`.

## Overview

EIP-8272 lets a frame transaction declare verified **recent roots** — `(source_id, slot, root)` tuples — in its signed envelope, so validation code (e.g. privacy proofs) can reference a recent commitment without reading another account's mutable storage. References are checked for validity at block execution against the `RECENT_ROOT_ADDRESS` predeploy.

## Implemented (this branch)

| Piece | Detail |
|-------|--------|
| Opcode `RECENTROOTREFLOAD` | `0xB5` (see divergence). Stack `[field, index]` (field on top); `field` 0→source_id, 1→slot, 2→root; gas 3; halts if `index ≥ len` or `field > 2`; reads only the envelope. |
| Envelope field | `recent_root_references: Vec<RecentRootReference>` — last RLP field (the **10th** ethrex field, after `blob_versioned_hashes`; the spec calls it the 9th because it omits ethrex's `signatures`). `RecentRootReference { source_id: H256, slot: u64, root: H256 }`, RLP `[source_id, slot, root]`, rkyv-derived. Covered by `compute_sig_hash` (not elided in VERIFY frames). |
| Static validation | `len ≤ FRAME_TX_MAX_RECENT_ROOT_REFERENCES (16)`; 3-tuple shape + 32-byte `source_id`/`root` + `slot < 2**64` enforced by the type/RLP. |
| TXPARAM `0x0F` | `len(recent_root_references)` (see spec-bug note). |
| `RECENT_ROOT_ADDRESS` | predeploy at `0x…8272` (`crates/vm/system_contracts.rs`). |
| Gas | `RECENTROOTREFLOAD = 3`; `RECENT_ROOT_REFERENCE_ADDRESS_GAS = ACCESS_LIST_ADDRESS_COST = 3000`; `RECENT_ROOT_REFERENCE_GAS = ACCESS_LIST_STORAGE_KEY_COST + 2*30 + 7*6 = 3102`. Both access-list parameters are 3000 from Amsterdam onward (EIP-8038) and frame txs exist only from Hegota, so the raised values always apply and neither constant needs a fork parameter. The live values sit in ethrex-common (which cannot depend on levm's `gas_cost`); `gas_cost` derives its own from `ACCESS_LIST_*_AMSTERDAM` and asserts equality at compile time so the two cannot drift. `FrameTransaction::recent_root_reference_gas()` is the whole EIP-8272 delta — the EIP-7623 calldata cost over `rlp(recent_root_references)` plus `ADDRESS_GAS + n * REFERENCE_GAS` — and is zero when no reference is declared, so a reference-free frame tx costs exactly the EIP-8141 figure. It counts as a **mandatory** cost: it is added to `total_gas_limit`, and finalization charges it outside the EIP-7623 floored term (see divergence 11). |

## Divergences from the draft spec

1. **`RECENTROOTREFLOAD` at `0xB5`, not `0xB4`.** The spec's Constants table assigns `0xB4`, which collides with EIP-8141's shipped `SIGPARAM = 0xB4`. ethrex uses the next free byte `0xB5`. Flag upstream.
2. **TXPARAM index `0x0F`** (not `0x0D`). The spec is internally inconsistent — its Constants table says `0x0F`, its summary table says `0x0D`. ethrex uses `0x0F` (Constants table is authoritative). An upstream fix is warranted.
3. **`RECENT_ROOT_ADDRESS = 0x…8272`** — the spec leaves it `TBD`; ethrex uses the `0x…<EIP>` convention.
4. **`RECENT_ROOT_CODE` handled natively** — the spec leaves the bytecode `TBD`; rather than invent bytecode, ethrex handles the 64-byte write (`salt ‖ root`, value 0, static-revert, direct-call-only) as a VM-level special case (see below).
5. **`source_id = keccak256(caller ‖ salt)`** — spec-conformant, not a divergence. EIP-8272 §Root sources defines `source_id = keccak256(source_address ‖ salt)`, and its Specification preamble fixes the encodings: "Addresses are 20 bytes", salts are 32. The preimage is therefore 52 bytes, with the address unpadded. The write side derives it from `msg.sender` and the call's salt, so a namespace is caller-authenticated (nobody can write into another caller's) and salt-differentiated; a referencing transaction declares the same `source_id` in its envelope.
6. **Native write gas = flat `RECENT_ROOT_WRITE_GAS` (22100)** — the spec's gas schedule is TBD with the bytecode. Priced as a cold created-slot SSTORE (20000 + 2100); flat pricing slightly over-charges ring-entry overwrites (the safe direction). Failed calls revert with the forwarded gas returned.
7. **`DELEGATECALL`/`CALLCODE`/7702-delegation to the predeploy revert** — the spec says such calls "MUST NOT write"; ethrex picks revert over no-op-success (conservative, and closest to bytecode running against a foreign storage context).
8. **Write journaling follows plain storage semantics** — a write inside a reverting frame rolls back with it, exactly as a real bytecode `SSTORE` would. (Contrast EIP-8250 keyed-nonce consumption, whose spec explicitly mandates revert-survival.)
9. **Top-level EOA transactions sent directly `to = 0x…8272` do not write** — the native handler intercepts frame targets and CALL-family invocations (any contract can write, from any tx type), but not the initial call frame of a plain EOA transaction, which lands on the empty-code account as a no-op success. Use a frame or a contract call to write.
10. **Beacon slot source: EL-derived when the CL doesn't forward it (EIP-7843 dependency).** `env.slot_number` (EIP-7843 `SLOTNUM`) — which the reference-validity window and the native-write slot key on — is meant to come from the CL via `PayloadAttributesV4.slot_number` on `engine_forkchoiceUpdatedV4`. The Hegotá devnet's CL (Lighthouse v8.0.0-rc.1) drives ethrex over `forkchoiceUpdatedV3`, which has no slot field, so `header.slot_number` is `None` and `env.slot_number` would be `0` — leaving every root write committed to slot 0 and no reference ever able to validate (EIP-8272 non-functional e2e). ethrex adds a `ChainConfig` knob **`derivedSlotTime`** (+ `genesisTimestamp`, `secondsPerSlot`) that, once active *and only when the CL supplies no slot*, derives it from the block timestamp: `slot = (block_timestamp − genesis_timestamp) / seconds_per_slot` — exact for slot-aligned PoS timestamps (a missed slot still advances the counter and produces no block). A CL-supplied slot always wins (`ChainConfig::effective_slot_number` prefers `header.slot_number`), so ethrex is forward-compatible with an EIP-7843-aware CL over V4 **with no further change**; the derivation is a single-EL devnet fallback, not the spec mechanism. Gated on a *future* timestamp (new-fork decoupling) so pre-knob blocks keep slot 0 and re-execute identically — the write/reference state is slot-keyed, so an un-gated change to already-produced blocks would be a state-root mismatch. Deployed on the Hegotá devnet 2026-07-08 and proven e2e (a native write committed to the timestamp-derived slot, not slot 0). **Prover caveat:** the Amsterdam SSZ proving reconstruction (`guest-program/src/l1/program.rs`) reads the payload slot verbatim and does *not* apply this derivation, so the `ProgramInput`/witness must carry the derived slot before proving is enabled on a knob-active chain (fail-safe unprovability today, no prover on the devnet; the general RLP "Direct" proving path already mirrors the derivation via the witness `ChainConfig`).

11. **Calldata charge mixes two EIP-8141 revisions, and reference gas is mandatory.** EIP-8272 §Gas accounting restates the whole EIP-8141 formula with `recent_root_calldata = rlp(tx.signatures) ‖ rlp(tx.frames) ‖ rlp(recent_root_references)`, charged as one byte string. That restatement is written against a superseded EIP-8141 revision: current EIP-8141 charges the calldata cost over the *data fields only* (each `frame.data`, and each signature's `signer`/`msg`/`signature`), with no RLP framing. ethrex follows each EIP where it is current — the data-field model for frames and signatures, `rlp(recent_root_references)` for the references — rather than reverting EIP-8141 to match EIP-8272's copy of it. Reference bytes are also kept out of `calldata_tokens`/`calldata_floor_gas`, since EIP-8272 does not restate the floor, and the reference gas is charged as a mandatory cost rather than inside the floored term: the floor is 64 gas per data byte against at most 16 for `data_cost`, so a floored term would silently absorb the reference charge even though the warming it prepays happens unconditionally. Flag upstream — EIP-8272's gas section needs rebasing onto current EIP-8141, which would also settle whether reference bytes are floorable.

## Consensus core (implemented)

The full consensus path is wired; the interim reject-all gate is gone.

- **Reference validity** (`execute_frame_tx`, before the frame loop): each reference must satisfy `1 ≤ current_slot − slot ≤ 8191` (`current_slot` from EIP-7843 `env.slot_number`, checked in U256, never `block.timestamp`) and `RECENT_ROOT_ADDRESS[storage_key] == entry_hash`. An invalid reference invalidates the transaction — and on import the block — before any frame executes. `entry_hash` commits to the **raw** slot, so an entry overwritten by an aliasing newer slot (same `slot mod 8192`) can never satisfy a stale reference; this closes the forged-roots soundness hole, and `RECENTROOTREFLOAD` now serves only verified roots.
- **Hash derivation** (`RecentRootReference::{entry_hash, storage_key}` in ethrex-common): `entry_hash = keccak256(keccak256("RECENT_ROOT_ENTRY") ‖ source_id ‖ uint64_be(slot) ‖ root)`, `storage_key = keccak256(keccak256("RECENT_ROOT_STORAGE") ‖ source_id ‖ uint64_be(slot mod 8192))`. One definition shared by the validity check, the native write, and the mempool policy — a natively written root always validates its own reference.
- **Access warming and BAL**: the predeploy address and every reference's storage key are warmed in the validity pass (the per-reference intrinsic gas prepaid this). The pass performs real storage reads rather than merely declaring access-list entries, so per EIP-7928 each key is recorded in the block access list as a **read** (`storage_reads`, never a change) under the transaction's own `block_access_index`. Recording happens only after the whole pass succeeds: a failed reference invalidates the transaction and the block with it, leaving nothing to record.
- **Predeploy install** (`install_recent_root_code`): nonce 1, empty code, balance preserved; installed at the Hegota gate from both `prepare_block` and `apply_system_calls`, so the account exists before any tx executes in the first Hegota block.
- **Native write**: a frame targeting the predeploy (empty code → default-code path) or any CALL-family invocation (intercepted in `generic_call`) with exactly 64 bytes `salt ‖ root` and zero value commits the current slot's entry under `source_id = keccak256(caller ‖ salt)` (20-byte address, 32-byte salt). Static contexts, delegate-style calls, and malformed calls revert. Last-write-wins follows from storage-write ordering.
- **Mempool/builder policy** (`validate_transaction`): admission-time rejection of too-new (`slot ≥ head_slot + 1`), expired (window exceeded), and uncommitted-root references, asserted explicitly against head state (the mempool's validation-prefix simulation never reaches `execute_frame_tx`, so the storage assertion is duplicated there by design). The policy runs *after* static validation and signature authentication, since it performs one head-state storage read per reference: ahead of them, a single unauthenticated `MAX_TX_SIZE` transaction could declare thousands of references and force a keccak-random storage lookup for each. References are re-validated only at admission; head-change eviction is deferred. Reference failures are split into transient and permanent (`FrameTxRecentRootNotReferenceable` vs `FrameTxRecentRootInvalid`) because block building evicts a frame tx on any non-nonce-mismatch failure: a root written in slot `S` is unreferenceable until `S + 1`, so a build landing in the slot the tx was admitted against must keep it pooled rather than drop it permanently.

## ⚠ Remaining / flagged for devnet validation

- **Cross-client interop** on the Hegotá devnet: the `source_id` derivation (divergence #5), the write gas convention (#6), and the hash byte layouts need a second client / spec ratification before any public network relies on them. Any mismatch is a hard fork on the first reference-carrying transaction.
- **Head-change recheck/eviction** of admitted reference-carrying txs (admission-only today).
- **CL-provided slot** (divergence #10): the spec-faithful path is an EIP-7843-aware CL forwarding the beacon slot over engine V4; the devnet's Lighthouse does not, so ethrex derives it EL-side behind the `derivedSlotTime` knob. Also fold the derived slot into the `ProgramInput`/witness before enabling proving on a knob-active chain.
- **`SLOTNUM` is not a banned validation-prefix opcode.** EIP-8141 §Banned Opcodes bans `NUMBER`, `TIMESTAMP`, `PREVRANDAO`, `BASEFEE` and friends because a validation prefix branching on them can pass at admission and fail at inclusion. EIP-8272 makes the beacon slot load-bearing, which gives `SLOTNUM` (EIP-7843) exactly that property, yet it is absent from the list — which predates EIP-7843. ethrex follows the list as written rather than banning it locally, since a local ban would reject transactions other clients admit. Flag upstream.
- Upstream spec gaps to flag: `RECENT_ROOT_CODE` bytecode + gas, `source_id` derivation, opcode byte (`0xB4` collision), TXPARAM index inconsistency, the `SLOTNUM` ban above, and EIP-8272's gas section still being written against a superseded EIP-8141 revision (divergence 11).
