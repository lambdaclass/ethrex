# EIP-8272: Recent Roots for Frame Transactions

> **Spec target:** ethereum/EIPs `EIPS/eip-8272.md` @ commit `5e32ce9abb` (2026-10-08,
> ethereum/EIPs#12443), which carries recent-root references in a canonical `VERIFY` frame,
> pins `RECENT_ROOT_CODE`, and deploys the contract with a keyless transaction instead of
> installing it at activation. The contract is described [below](#recent_root_code).

Implementation notes for EIP-8272 in ethrex. It builds on [EIP-8141](./eip-8141.md) frame
transactions and on EIP-7843's `SLOTNUM`, and activates with them at `Fork::Hegota`.

## Overview

EIP-8272 lets a frame transaction prove that a recent root, such as a privacy pool's commitment
root, is committed on chain without its validation code reading third-party storage. It has two
halves:

- **Write.** Any contract calls `RECENT_ROOT_ADDRESS` with `salt || root`. The contract stores an
  entry for `source_id = keccak256(caller || salt)` at the current slot, in a ring of 8,192 slots
  per source.
- **Reference.** A transaction carries a **recent root verifier frame**: a `VERIFY` frame to
  `RECENT_ROOT_ADDRESS` whose data is 1 to 16 packed `(source_id, slot, root)` tuples. The frame
  runs the contract's validation operation, which reverts unless every tuple is stored and recent.
  A reverting `VERIFY` frame invalidates the transaction, so a transaction that includes the frame
  is valid only while its roots are.

The EIP adds no opcode, no `TXPARAM` index and no envelope field. Application code reads the frame
back with EIP-8141's `FRAMEPARAM` and `FRAMEDATALOAD`.

## How to use it

1. **Write a root.** From the source contract, call `0x8272D9679689Ea2f307140CdF9002D27dC00Ffff`
   with exactly 64 bytes of calldata, `salt || root`, and no value. The write needs state gas for
   the slot it fills the first time.
2. **Wait one slot.** A root written during slot `S` becomes referenceable from slot `S + 1`. It
   stays referenceable while `current_slot - S <= 8191`.
3. **Reference it.** Put the verifier frame first, or second behind an expiry verifier frame:

   ```text
   mode = VERIFY, flags = 0, target = RECENT_ROOT_ADDRESS, value = 0, limits.state = 0
   data = source_id (32) || uint64_be(slot) (8) || root (32)     repeated 1 to 16 times
   ```

4. **Check it in validation.** The account's `VERIFY` frame should confirm, through `FRAMEPARAM`,
   that frame 0 targets `RECENT_ROOT_ADDRESS` in `VERIFY` mode with flags 0, has `limits.state`
   0, valid data length and status 1. It should then bind the tuple it read with `FRAMEDATALOAD`
   to whatever it authorizes.

The EIP's reference vector, with `current_slot = 2`:

```text
source_address = 0x0000000000000000000000000000000000000001, salt = 0x00…00
source_id      = 0xb9382d35273c75a50631a3e84d3c75ec9266e2b18c35a627e16cdbf26a18ca85
slot = 1, root = 0x00…02
entry_hash     = 0x0a0d1254c851be5a133b4c9a9e300f5602fc0f43dbe65aa6a66930d4ca0a51b8
storage_key    = 0x5f027aa1cbe2df279bf6518edd4b44ea5409fd800189ec35224e10ab05e574c3
```

With `storage[storage_key] = entry_hash`, the 72-byte validation calldata succeeds.

## Architecture

```text
Frame classification (crates/common/types/transaction.rs)
  Frame::is_recent_root_verifier: VERIFY, target RECENT_ROOT_ADDRESS, flags 0, value 0,
                                  limits.state 0,
                                  len(data) a non-zero multiple of 72, at most 16 tuples
  RecentRootReference::{from_tuple_bytes, entry_hash, storage_key}
  FrameTransaction::recent_root_verifier_index: frame 0, or frame 1 behind an expiry verifier

Block execution
  the frame is an ordinary VERIFY frame: RECENT_ROOT_CODE runs under STATICCALL semantics,
  reads SLOTNUM and its own storage, and reverts on any failing tuple

Public mempool (crates/blockchain/blockchain.rs, crates/vm/backends/levm/mod.rs)
  structure:  validation_prefix skips the verifier frame; validate_prefix_structure rejects it
              anywhere else (RecentRootFrameMisplaced) and counts its limits.execution toward
              MAX_VERIFY_GAS
  code:       rejected unless the code at RECENT_ROOT_ADDRESS is exactly RECENT_ROOT_CODE
  simulation: current_slot = head.slotNumber + 1; RECENT_ROOT_CODE runs with two permissions,
              SLOTNUM and SLOAD of its own storage, granted only at the top level of that frame
              (ValidationObserver::in_recent_root_frame)
  eviction:   every pending frame transaction is simulated again after each fork-choice update
```

## `RECENT_ROOT_CODE`

The EIP's Bytecode section pins the runtime, the same bytes as ethereum/sys-asm#53
(`bytecode/recent_root/main.hex` at `0ea4d71517`). It selects the operation by calldata length:

| Calldata | Operation |
|---|---|
| exactly 64 bytes, no value | **write**: `storage[storage_key(source_id, S)] = entry_hash(source_id, S, root)`, with `source_id = keccak256(caller \|\| salt)` and `S = SLOTNUM` |
| `n × 72` bytes, `1 <= n <= 16`, no value | **validate**: every tuple must have `slot < SLOTNUM`, `SLOTNUM - slot <= 8191` and a stored entry equal to its entry hash. Any failure reverts. |
| anything else, or any value | revert |

| | |
|---|---|
| Length | 320 bytes |
| `keccak256(RECENT_ROOT_CODE)` | `0xda160390a838ee04013b2ff3abf4decc9aa3cc6c2f59dd90ca176c2b850be4e3` |

The VM tests run both operations through the EVM, including the EIP's reference vector, the
8,191-slot window, wrong roots, sources and slots, malformed lengths, and writes from a static
context.

## Deployment

The recent root contract is an ordinary contract. Its keyless deployment transaction creates it at
`0x8272D9679689Ea2f307140CdF9002D27dC00Ffff`, and a chain can also allocate it in genesis with
nonce 1. Activation changes no state. Until the contract is deployed, the address has no code, so
a recent root verifier frame runs the protocol default code, which reverts in a `VERIFY` frame
with flags 0, and the transaction is invalid; the public mempool rejects it because the code is
not `RECENT_ROOT_CODE`. [EIP-8141 § Contract Deployment](./eip-8141.md#contract-deployment) lists
all three frame contracts.

## Mempool

- **Shape first.** The frame's position and data length are checked by `validate_prefix_structure`,
  before any state is read. A matching frame anywhere other than first, or second behind an expiry
  verifier, is rejected. A second matching frame fails shape matching.
- **Code.** A transaction with a verifier frame is rejected unless the code at
  `RECENT_ROOT_ADDRESS` is exactly `RECENT_ROOT_CODE`. Only then does the frame get its two
  simulation permissions.
- **Window and storage.** The simulation runs `RECENT_ROOT_CODE` at
  `current_slot = head.slotNumber + 1`, the earliest slot of the next payload. A tuple for the
  current slot or later, one older than 8,191 slots, or one whose entry is not stored reverts the
  frame, which rejects the transaction.
- **Gas.** The frame's `limits.execution` counts toward `MAX_VERIFY_GAS`. The simulation charges
  the cold access to `RECENT_ROOT_ADDRESS` at frame entry exactly as execution does, so a frame one
  gas short is rejected at admission rather than failing in a block.
- **Introspection.** The simulation records each completed prefix frame the way execution does, so
  account validation that reads the verifier frame's status through `FRAMEPARAM` sees it.
- **Eviction.** After every fork-choice update, `revalidate_frame_txs_after_block` simulates
  every pending frame transaction again at the new head. A slot advance that ages a tuple out, or
  a reorg onto a branch without the written root, evicts the transaction.

## Design decisions

- **The contract is the predicate.** The EIP lets a client evaluate the frame directly instead of
  executing `RECENT_ROOT_CODE`, provided gas, receipts and warm sets come out identical. ethrex
  executes the code. Admission and block execution then share one definition of the window and the
  entry check, and there is no second implementation to keep in step.
- **Dependency tracking is a full rescan.** The EIP asks clients to index pending transactions by
  `(storage_key, entry_hash)` and by expiry slot. ethrex re-simulates every pending frame
  transaction after every fork-choice update instead. That meets the recheck requirement at a
  cost proportional to the number of pending frame transactions, which the one-per-sender rule
  bounds.
- **No admission margin.** The EIP says clients SHOULD NOT admit a transaction whose oldest
  reference is about to expire, with the margin left to the node. ethrex admits anything inside the
  window, and the next revalidation evicts it once it ages out.
