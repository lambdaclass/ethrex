Can a payment leave nothing behind?

On Ethereum, receiving a payment writes permanent state: the first ETH to an address creates a ~120-byte account leaf forever; the first ERC-20, a storage slot. A one-shot payment needs none of that — only a value, a recipient, and double-spend protection.

The core idea: a UTXO is a one-shot payment object. Its existence lives in append-only history — a log plus a per-block openings root you prove against — and its consumption is a single bit in a packed bitfield. Gas lives inside the frame's conservation rule, so a recipient can spend while holding zero ETH. That is EIP-8312's UTXO frame, built on EIP-8141 frame transactions — and this demo runs it for real on an ethrex PoC devnet.

You'll watch a zero-ETH recipient spend, stealth payments consolidate into one frame, a payroll run that leaves three bytes of permanent state, and a sponsor get repaid without trusting anyone.

EIP-8312, explained

A UTXO is an opening — (source, value, recipient) — plus a protocol-assigned global index. It is created by depositing to the vault system contract at 0x…8312, spent whole, and never partially.

Rule 1 · Store consumption, prove existence. A “can this still be spent?” check answers two questions: did it exist? and was it used? Bitcoin answers both with presence in the UTXO set, forcing every unspent object into state. EIP-8312 splits them: existence is proven from history against per-block openings roots; only the “used” fact — one bit, 256 flags per 32-byte word — stays in state. The permanent cost moves from creation to consumption.
Rule 2 · Declare transitions, don't execute. A spend is a signed, value-conserving transition declared as inspectable data, not code. “Does this conserve value?” and “does this output repay me?” are answered by reading the frame — which is what makes self-funded spends and trustless sponsorship a clean primitive instead of a relayer workaround.

The spend frame carries actors, inputs, utxo_outs, account_outs, change_index, payer and fee caps. Conservation: Σ inputs ≥ Σ outputs + max_cost — gas is inside the rule, so a zero-ETH recipient can spend. Spent bits are the replay protection; a UTXO is spendable from the block after its creation.

How it works

1 · Createcall UTXO_VAULT (0x…8312) with value + recipient; the vault assigns a global index and emits UtxoCreated
→
2 · Commitat block end the client hashes each opening into the block's openings root (ring of 8192; sealed batches of 8192 roots)
→
3 · Spend frameactors sign inputs, outputs, change, payer, fee caps; VERIFY proves openings + unset bits + conservation
→
4 · Settlespent bits flip journal-externally; outputs become new UTXOs or account credits; the fee comes from the consumed value

The spend, as declared data (RLP)

actorsaddresses backing the spend, each with a scheme-tagged signature over the spend hash (secp256k1, P-256 passkeys, PQ later)
inputs[index, creation_block] signed; source, recipient, value and Merkle path supplied as witness, read from the proven opening
utxo_outsnew UTXOs to create (recipient, value)
account_outscredits back into the account model — the escape hatch
change_indexone output, signed with value 0, receives the remainder after the actual fee — like Bitcoin change
payerempty = self-funded (the UTXO pays its own gas); an address = sponsored, repaid by a signed output
fee capsmax_fee_per_gas · max_priority_fee_per_gas · max_gas_limit, all signed

Where it doesn't fit

  • Already-funded accounts doing ordinary transfers. If the recipient keeps an account anyway, a plain transfer is simpler — UTXOs add nothing.
  • Contract-account recipients. UTXO ownership is key-only: no signature verifies to a contract's address, so a UTXO sent to one (including counterfactual CREATE2 accounts) is unspendable by construction.
  • Recurring, stateful relationships. Balances you reuse, allowances, DeFi positions — the object is deliberately one-shot; account_outs is the way back.
  • Tokens (for now). EIP-8312 is ETH-only. A token extension is sketched in the research post, but token UTXOs can't pay ETH gas and always need a sponsor.
  • History availability. Existence lives in logs and openings roots: wallets must keep openings provable, and under history expiry the openings need a retention story.
