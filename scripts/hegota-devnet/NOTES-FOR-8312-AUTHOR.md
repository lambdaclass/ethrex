# EIP-8312 on the Hegotá Devnet — Notes for the Spec Author

ethrex has implemented EIP-8312 (UTXO Frame) on top of its EIP-8141 frame-transaction
stack and deployed it to a private devnet, where the full deposit → spend cycle runs
end to end. This note collects what we found: places where two conforming clients
could diverge, economic properties we think are unintended, composition rules the
draft leaves open, and the deviations we had to make.

- **Spec read:** `nerolation/EIPs` `EIPS/eip-8312.md` @ commit
  `a5da3f608c6dfbf353bea264054d99fc164ab10c` (2026-07-11), plus the
  ethresear.ch thread "Native UTXOs on Ethereum".
- **Status:** implemented and live-tested on a 3-EL devnet (three independent ethrex
  instances in consensus). Self-funded spends, sponsored spends, the openings-root
  commitment, the spent bit, and settlement all work; batch-path spends are
  implemented but not yet exercised on a chain older than `BATCH_SIZE` blocks.
- **What we did NOT implement:** token-carrying openings (the draft defers them),
  and UTXO frames sharing a transaction with EIP-7906 POST_TX frames (we forbid the
  combination pending a ruling — see §3.6).

## What the live deployment measured

Every figure below is from receipts on our devnet, not from the draft's estimates:

| Flow | Gas | Permanent state |
|---|---|---|
| Vault deposit (create one UTXO) | 36,334 | none |
| Spend (1 input, depth-1 proof, 1 account out + change) | 56,094 | one spent bit |
| Full cycle | 92,428 | ~0.3 B |
| Plain transfer to a fresh account, same chain | 204,600 | ~120 B account leaf |

The draft's ≈36,500 deposit estimate is accurate. The full cycle costs ~2.2× less
than a single fresh-account transfer, matching the draft's "half the gas" claim, and
a UTXO recipient has no account leaf at all (verified: `nonce = 0`, `balance = 0`
for an address that had just been paid).

We also confirmed the headline claim directly: an address holding **zero wei**
successfully spent its UTXO, paying a third party, with the fee taken from the
payment itself.

## 1. Ambiguities where two conforming clients can split

These are all cheap to fix and worth addressing before more implementations start.

1.1. **`spend.payer` has two encodings for one meaning.** Constraints allow `len(spend.payer) in (0, 20)` with the comment "empty (written payer == 0) means self-funded", then branch on `if spend.payer == 0:`. Twenty zero bytes passes the length check: one implementer canonicalizes `0x00…00` to "self-funded", another reads it as sponsor `address(0)` — which passes `spend.payer != UTXO_VAULT` and then can never satisfy the final `payer == spend.payer` check, so the same bytes are valid on one client and invalid on the other. Suggestion: define self-funded as `len(spend.payer) == 0`, add `assert spend.payer != address(0)` for the 20-byte form, and phrase every downstream test as a length test.

1.2. **`tx_gas_limit` in Execution step 2 is undefined.** A frame transaction has at least two derivable gas limits (the sum of frame gas limits, and the transaction gas limit including the EIP-7623 calldata floor that `max_cost` is built from). The fee-cap check `assert tx_gas_limit <= spend.max_gas_limit` decides transaction validity, so the readings diverge consensus. Suggestion: define it explicitly as the quantity whose product with `max_fee_per_gas` forms the maximum cost (the same value `TXPARAM(0x06)` is built from).

1.3. **The `GAS_NEW_ACCOUNT_STATE` return has no defined gas dimension.** The gas table charges it "to the state-gas dimension"; the settlement comment says the return "reduces the frame's gas used", and the fee is computed "after the returns above". Whether the return reduces `actual_fee` (and therefore `change_value` and the state root) is readable both ways. Also unpinned: whether block-level EIP-8037 accounting uses the pre- or post-return figure, and whether the return interacts with the refund quotient or the EIP-7623 floor. Suggestion: state the dimension, that the return reduces the fee, that block accounting uses the post-return figure, and that the return is exempt from refund-cap/floor clipping.

1.4. **"exact decoding, no trailing bytes" does not require canonical RLP.** If lenient decodings (non-minimal integers, non-minimal lengths) are accepted, a relayer can re-encode `frame.data` into different bytes that decode to the same spend and the same `spend_hash` — so all signatures stay valid while `frame_data_cost`, and hence the fee taken from the change output, grows; and clients that disagree on strictness split on validity. Suggestion: "Decoding MUST be strict canonical RLP: minimal integer encodings, exact list arities, no trailing bytes; any violation makes the transaction invalid," and note that `spend_hash` is defined over the canonical encoding.

1.5. **The openings-tree leaf set is not bound to an operation, and the natural implementation is forgeable.** "Let `leaves` be the leaf of every UTXO created in block `N`" never defines "created" operationally. The only creation artifacts the draft exposes are logs, and the natural implementation (mirroring EIP-6110's deposits-from-receipts) scans block logs by topic. Any contract can emit `LOG3(UTXO_CREATED_TOPIC, source, recipient, index‖value)` with arbitrary values: an implementation that does not pin the emitter address folds a forged leaf into the openings root, and the forged "UTXO" is spendable out of the vault's pooled balance the next block — breaking vault solvency outright. Suggestion: define `leaves` normatively as the ordered sequence of index assignments performed by (a) the vault deposit path and (b) settlement, with `source`/`recipient`/`value` taken from the assigning operation; add a note that any receipt-derived implementation MUST filter `log.address == UTXO_VAULT` and MUST NOT trust log payloads.

1.6. **The empty-block zero-root write must be stated as mandatory.** For a block creating no UTXOs, writing `merkle_root([]) = 0x00…` over the ring slot is a *clearing* write. An implementation that "optimizes" it away passes every short-range test and diverges at the first ring wrap, 8,192 blocks later; a stale slot also silently grants a second full ring window to old creations. Suggestion: say the ring-slot write happens every block unconditionally, and add the (correct) rationale that the zero sentinel is safe because a leaf is a keccak of 80 bytes and can never be zero.

1.7. **`account_exists` "follows the existence rule of EIP-8037" hangs a consensus-critical refund on an unrestated cross-reference.** "Present in the state trie" and "non-empty per EIP-161" disagree on an existing-but-empty account; the resulting 183,600-gas difference changes the fee, the change value, and the state root. Suggestion: restate the predicate inline in one sentence and keep the EIP-8037 citation as provenance.

1.8. **The vault-sender envelope carve-outs are incomplete as specified.** The Specification waives exactly two things (the sender nonce check, the `sender_approved` precondition of `APPROVE(APPROVE_PAYMENT)`). But the vault carries runtime code, so EIP-3607 as ordinarily applied rejects every vault-sender transaction; the absence of an envelope signature (and therefore of sender authentication) appears only in the Rationale; and how intrinsic gas is fronted before the payer resolves at frame execution is unstated. Suggestion: the "When `tx.sender == UTXO_VAULT`" list should normatively enumerate every waived envelope rule.

1.9. **Access-list and visibility semantics of the frame's native vault accesses are unspecified.** Whether step 3's root reads and spent-bit writes warm the transaction's EIP-2929 access list is gas-visible to later frames in the same transaction (a subsequent `SLOAD` of the spent word costs 100 vs 3,000 depending on the choice), which flows into the fee, the change value, and the state root. Separately, the text asserts the spent bit's *durability* but never its *visibility* to subsequent frames. Suggestion: one sentence each — e.g. the native accesses do not mutate the access list (consistent with "charged at the cold rate unconditionally"), and the set bit and updated `SLOT_NEXT_INDEX` are immediately visible to subsequent frames.

1.10. **Prose vs pseudocode on the vault-sender nonce.** "The sender nonce check is skipped" sits against `assert tx.nonce == 0`. Suggestion: "the envelope `nonce` field MUST be zero (static well-formedness); the comparison against the sender account's state nonce is skipped and no nonce is incremented."

## 2. Economic design

2.1. **For vault-sender spends, the signed fee cap is the fee, and spends never expire.** Because re-wrapping is permissionless and a cap-maxed wrap pays the proposer strictly more, every observer rationally re-wraps mempool spends at the signed caps — the change output is *always* drained to the cap, not "at most". "Actors should sign tight caps" is structurally unavailable: caps need basefee headroom to stay includable, and `max_gas_limit` must budget the larger batch-path witness that anyone may substitute (the Witness-refresh property), so the headroom is exactly the extractable surplus. And with no validity horizon ("a signed spend can be kept valid indefinitely"), a spend signed during a fee spike is a perpetual standing order; the only cancel path is racing a self-spend of the same input. Suggestions: (a) an optional signed `min_change_value` (or `max_total_fee` in wei) folded into conservation — `assert spent_value >= signed_out + max_cost + min_change_value` — bounds the loss exactly while leaving fee selection and witness refresh free, and preserves "settlement cannot fail"; (b) an optional signed `valid_until` block (0 = none); (c) rewrite the Envelope-malleability paragraph to state plainly that the signed priority cap is the *expected* fee for vault-sender transactions. Related: EIP-8141's expiry-verifier frame cannot substitute (the self-funded shape is single-frame, and in any vault-sender transaction an envelope frame is submitter-strippable) — worth a sentence.

2.2. **The spent-bit charge is "exact on average" only when everything is eventually spent.** Bits are allocated in creation order, but only spends write state, and the Motivation itself expects most UTXOs never to be spent. At spend fraction `f`, fresh 64-byte words per spend ≈ `(1-(1-f)^256)/(256f)` — equal to the charged 1/256 only at `f = 1`, and ~92× it at `f = 0.01`. Adversarially, spending stride-256 indices writes one fresh word per spend for 383 gas each: a burst of state growth ~256× what the state-gas dimension believes it authorized (sustained rate bounded by creation volume ÷ 256). Suggestion: reserve `97,920` per input and return it at settlement when the spent word was already non-zero — the exact reserve-and-return mechanism this EIP already defines for `GAS_NEW_ACCOUNT_STATE`, and cheap here because the frame reads the word anyway. A second, smaller mismatch: `GAS_UTXO_FRAME` is derived from one `SLOT_NEXT_INDEX` update per frame, but settlement performs one per `utxo_out` (and none when there are none); fold the counter update into `GAS_UTXO_OUT` or state that the difference is intentional.

2.3. **`MAX_UTXO_VERIFY_GAS` accounting is ambiguous, and as written caps account outputs at one per transaction.** If the full `utxo_frame_gas` counts (it includes the 183,600 reserve per account output, a state-dimension quantity that is mostly returned and involves no verification CPU), then two fresh-account outputs ≈ 415k exceed the 400k bound: a consensus-valid payout spend can never be relayed. The "roughly twenty inputs" sizing holds only with a single actor and with `frame_data_cost` excluded — neither stated. Suggestion: define exactly which components count (dimensions, data cost, per-signature costs); consider discounting the refundable reserve; and state that nodes reject on the statically computable budget *before* running any signature or Merkle work, so admission cost is bounded ahead of the expensive part.

2.4. **Signature-list padding.** Nothing restricts `tx.signatures` on a vault-sender transaction to the entries the frames require; a re-wrapper can append junk entries, inflating per-signature gas at cap-level price out of the change output. Suggestion: for `tx.sender == UTXO_VAULT`, require every signature entry to be consumed by some frame's actor requirement.

2.5. **Mempool interoperability.** "Keep at most one pending transaction per index, with replacement subject to the node's fee bump rules" leaves open: the common case of the *same* signed spend under a different wrap (identical spend hash, different tx hash — is it a replacement, measured against which fee?); overlapping-but-unequal index sets; multi-conflict replacements (bump over each, the max, or the sum? atomic eviction?); and any bound on pending vault-sender transactions, which share one sender and so escape all per-sender pool limits. Suggestion: specify a minimum interoperable rule (e.g. a replacement MUST pay a higher effective priority fee than every transaction it conflicts with and evicts all of them; identical-spend re-wraps are the expected replacement form), and note the need for an implementation-defined bound on pending vault-sender transactions.

2.6. **Bundling weakens the Mass-invalidation claim as stated.** The claim holds per frame, but an N-spend sponsored bundle is jointly invalidated by any single input being spent elsewhere (one cheap self-funded spend voids the whole bundle's admission work, repeatably), and a sponsored transaction's *transaction-level* validity does depend on third-party state through the sponsor's `APPROVE` code. Suggestion: scope the claim to a frame's own checks and add bundler guidance in Security Considerations.

## 3. Composition with the frame-transaction family

3.1. **Frame mode 3 is already allocated.** EIP-7906 assigns POST_TX `mode = 3`, and this draft's "the static constraint `assert frame.mode < 3` of EIP-8141 becomes `assert frame.mode < 4`" is written against base EIP-8141, so the two drafts collide on any chain running both. Our implementation resolves it locally by giving UTXO mode 5 and leaving POST_TX at 3 (mode 4 stays reserved for EIP-8288's deferred DEP_VERIFY): POST_TX is already live, so renumbering it would break signed transactions and tooling, and — because EIP-8312 activates on its own timestamp — would make mode resolution activation-dependent at every consumer, permanently. We would rather match the spec's number, so this needs an upstream resolution: ideally a frame-mode registry in EIP-8141 that dependent EIPs claim numbers from, with 8312 and 7906 assigned distinct values.

3.2. **The sponsored vault-sender flow does not type-check against EIP-8141's validation-prefix shapes.** All four canonical shapes require every prefix VERIFY frame's resolved target to equal `tx.sender`. With `tx.sender == UTXO_VAULT`, the pay frame would execute the vault's deposit code — which reverts on non-deposit calldata and never calls `APPROVE` — so a vault-sender sponsored transaction has no recognizable prefix and is never admissible. The `sender_approved` waiver fixes the APPROVE precondition but not the shape rules. Suggestion: define the additional shape this EIP implicitly needs (it already adds one for self-funded spends): for `tx.sender == UTXO_VAULT`, a single VERIFY frame with scope `APPROVE_PAYMENT` whose resolved target equals the common `spend.payer` of the transaction's UTXO frames, with no execution-approval frame.

3.3. **The sponsorship recipe in the Rationale is exploitable as written.** "A sponsor inspects the UTXO frame's data with `FRAMEDATALOAD`, checks for an output paying itself at least its cost, and only then approves payment" — `FRAMEDATALOAD` returns any frame's raw data regardless of mode, so a DEFAULT frame whose calldata decodes like a spend with an output paying the sponsor drains a sponsor that follows the recipe, one max-cost at a time. Suggestion: Security Considerations should state the minimal safe check — verify the inspected frame's *mode* is UTXO (via the frame-parameter introspection), verify the decoded `spend.payer` equals the sponsor, and only then compare repayment against `TXPARAM(0x06)` — and the spec should state its dependency on EIP-8141's cross-frame introspection semantics, without which the sponsorship design is void.

3.4. **`ATOMIC_BATCH_FLAG` is used normatively but EIP-8250 is not in `requires`.** The placement constraint references 8250's flag, and step 3 leans on 8250's consumed-nonce durability model. Suggestion: add 8250 to `requires`, or make the constraint conditional on 8250 being active and keep the journal-external semantics self-contained. Related: EIP-8250 makes nonce keys a structural envelope requirement; the vault-sender envelope needs a defined shape under 8250 (presumably: no nonce keys, exempt from the 1..16 rule) — currently only derivable by inference.

3.5. **The durability sentence and the invalidity rule read as contradictory.** "Spent-bit writes … a later frame failure cannot undo them" vs "If any check fails, the transaction is invalid": a later UTXO frame's failed check is literally a later frame failure, and it absolutely undoes earlier spent bits (the transaction is never included). The two regimes — a sibling frame's *revert* that leaves the transaction valid (bits and settlement stand) vs any *invalidating* failure (the whole transaction is discarded) — are only recoverable by inference. One scoping sentence in step 3 and in the Double-spending paragraph fixes it.

3.6. **Composition with EIP-7906's whole-body revert is undefined.** Can an assertion-frame body revert roll back journal-external spent bits, and does settlement still run? We forbid UTXO+POST_TX co-residency in v1 for lack of an answer. Suggestion: state the intended semantics or explicitly delegate the composition to 7906.

3.7. **The account-output transfer log is priced but not emitted in the pseudocode.** `GAS_UTXO_ACCOUNT_OUT = 9000` includes `TRANSFER_LOG_COST` (1,756), implying settlement's account credits emit EIP-7708 transfer logs, but the settlement pseudocode shows only balance mutations. Say it (and define the zero-value-transfer case).

3.8. **EIP-7928 (block access lists) representation is unstated** for the three unusual write classes this EIP introduces: spent bits that survive a failed sibling frame, settlement-time writes, and the end-of-block root writes. On BAL-carrying chains these choices are consensus-visible. A short compatibility note would prevent divergent implementations.

3.9. **The end-of-block operation needs a definition and a position.** "The client performs a system operation" — its gas exemption, infallibility, and its ordering relative to other end-of-block operations (withdrawals, request dequeues) are unstated; the ordering is observable through access lists and same-account interactions. Suggestion: define the operation (protocol-level storage write, no gas, cannot fail, unconditional every block) and pin its position in the block's end-of-block sequence.

3.10. Smaller composition items: statically forbid SENDER-mode frames and execution-scope flags in vault-sender transactions (they are guaranteed-dead at runtime; a static rule is cheaper and makes "the vault can never act" normative); pin the frame-receipt semantics of a UTXO frame (status is always success, since failure invalidates the transaction; state whether the receipt's gas reflects the settlement-time reserve returns); and state whether the blob asymmetry is intentional (only vault-sender transactions forbid blobs; a sponsor-as-sender transaction may carry them, uncapped by any spend field).

## 4. Ecosystem and wallet operability

4.1. **The data-availability assumption behind spendability should be stated.** Batch witnesses are derivable from state only transiently: the batch tree's leaves are the ring roots, which begin to be overwritten the block after the batch seals. After that, both the `siblings` (the creation block's full leaf set) and the `batch_siblings` exist only in history. Under EIP-4444-style history expiry, a dormant UTXO becomes unspendable without out-of-protocol archives — value can be permanently locked by losing a witness, an availability asymmetry a plain account balance does not have. Suggestion: a Security Considerations subsection naming the retention assumption, recommending wallets persist openings and witnesses at receipt time and upgrade ring proofs to batch proofs promptly; optionally consider double-buffering the ring (`RING_SIZE = 2 × BATCH_SIZE`) so batch witnesses stay state-derivable for a full extra batch.

4.2. **Settlement can mint a zero-value UTXO, which the deposit path explicitly forbids.** `change_value` can be exactly zero; if `change_index` names a `utxo_out`, settlement emits `UtxoCreated` with `value = 0`, consumes an index, and adds a leaf — an object class the vault code was designed to exclude, surfacing as phantom payments to scanning wallets. If the change is a zero credit to a nonexistent account, the 183,600 reserve is forfeited for state that is never written (the return is conditioned on existence only). Suggestion: skip settlement outputs whose settled value is zero (no log, no index, no leaf, no transfer, reserve returned), or explicitly bless zero-value change UTXOs and warn indexers.

4.3. **Outputs may name `UTXO_VAULT`.** A `utxo_out` to the vault is a live unspent claim that can never be spent (no signature can resolve to the vault); an `account_out` to the vault is a self-transfer that converts input value into inert vault surplus. The draft forbids the vault only as payer. Suggestion: `assert out.recipient != UTXO_VAULT` for both output lists (and optionally in the vault deposit code), or state the burn is intentional.

4.4. **The change recipient is not required to be an actor.** The change output receives the residual — often the bulk of the input value plus all unspent fee headroom — yet nothing ties its recipient to `actors`; a single mangled address silently misdirects it. Suggestion: require `outs[change_index].recipient ∈ spend.actors` (a deliberate third-party payment can be a signed non-change output), or at least recommend change-to-self in Security Considerations.

4.5. **Consider putting `index` in the free fourth topic.** Every post-receipt wallet operation (spent-bit check, witness fetch, dedupe) is keyed by index, but `eth_getLogs` cannot filter on data. `UtxoCreated(address indexed source, address indexed recipient, uint64 indexed index, uint256 value)` costs 375 more gas (`GAS_UTXO_OUT` 2012 → 2387) and makes the primary lookup key filterable.

4.6. Smaller items: recommend standard node RPCs for openings/proof/spent-bit serving and for wrapping a bare `(spend, signatures)` into a vault-sender envelope — proofs are trustlessly verifiable (a served witness either folds to the committed root or fails), so the spec can say third-party serving is safe, and the zero-ETH recipient's submission path currently has no standard form; soften or qualify "stealth payments" (no derivation scheme is specified, and the `topics[2]` discovery scan is exactly what stealth addresses negate — cite a companion like ERC-5564); add a Rationale sentence for the `source = actors[0] / UTXO_VAULT` attribution rule, which currently exists only as a pseudocode side effect.

## 5. Editorial

- `RING_SIZE == BATCH_SIZE` is normative in effect (the gap-free ring→batch upgrade depends on it) but stated only in the Rationale; `len(batch_siblings) in (0, 13)` hardcodes `log2(BATCH_SIZE)`. Use one constant or assert the relationship.
- Backwards Compatibility says "No existing transaction type or opcode changes behavior," but the draft changes the frame type's validity rule (mode table) and adds envelope carve-outs; rephrase as "only turns previously-invalid transactions valid."
- `max_cost` is defined only by pointer to `TXPARAM(0x06)`; give its arithmetic. The bare `payer` execution variable (vs `spend.payer`) should be introduced ("let `payer` be the transaction's payer as defined by EIP-8141, initially unset").
- Duplicate recipients within one frame's `account_outs` double-charge the reserve (both existence checks run before any transfer); dedupe the reserve by recipient within a frame, or forbid duplicates. Note the cross-frame behavior ("a frame's checks see the effects of frames settled before it") is correct and should not change.
- The per-frame settlement loop reads the transaction-level `fee` — well-defined only because a nonzero fee implies a single frame (self-funded); say so beside the pseudocode.
- The index counter is bounded on the spend side (`index < 2**64`) but unbounded on the creation side (vault code and settlement both increment freely; `to_bytes(8, "big")` is undefined at 2^64). Close the asymmetry and state the slot-layout non-collision invariant it implies.
- State activation semantics for a pre-existing account at `0x8312`: balance preserved as inert surplus (solvency unaffected — conservation bounds outflows), nonce handling, and that its storage MUST be empty at activation.
- **Test vectors** would be the cheapest disambiguator for §1: `spend_hash` preimages, the 80-byte leaf encoding, `merkle_root` with zero/odd leaf counts, full spend RLP examples (self-funded, sponsored, batch-path witness), and one worked settlement gas-return computation.

## Verified and found exactly right

For balance: all seven gas constants re-derive exactly from EIP-2780/8037/8038 primitives (including the 48-gas keccak of the 80-byte leaf and ⌈97,920/256⌉ = 383); `GAS_UTXO_ACCOUNT_OUT = 9000` decomposes precisely into cold access + value cost + transfer-log cost; the published vault runtime (76 bytes) decodes exactly to the geas listing, enforces exactly the three prose conditions, and its jump target is the only JUMPDEST; `UTXO_CREATED_TOPIC` matches its event signature; the ring→batch upgrade window is tight at both edges and the fixed 13-level batch path is complete for all time; leaf/inner-node domain separation holds (80- vs 64-byte keccak preimages) and the zero sentinel is unforgeable; the slot regions cannot collide; strictly-increasing indices plus journal-external bits close intra-frame, cross-frame, and cross-transaction double spends; `change_value` cannot underflow; the vault stays solvent under the payer-fronting flow; and a builder cannot steal a spend — `spend_hash` covers all outputs and `change_index`, so extraction is bounded to the fee surface discussed in §2.1.
